# TechSprout School LMS — Cloudinary Media Architecture Specification

> **Phase Status:** P2.0 Architecture Freeze  
> **Applicability:** Media Storage Abstraction, Cloudinary Integration, Video Delivery, and PostgreSQL Asset Metadata.  
> **Prerequisites:** P1 Cloudinary Service & Asset Migration (Completed).  
> **Scope:** Architecture Freeze only.

---

## 1. Architectural Overview & Design Principles

The media subsystem provides centralized, secure, and performant asset ingestion, transformation, and delivery for the TechSprout School LMS:

1. **Storage Provider Abstraction:** Application code references the generic `media` entity in PostgreSQL, abstracting provider-specific storage mechanics (`storage_provider = 'CLOUDINARY'`).
2. **Strict Credential Isolation:** Cloudinary API secrets (`CLOUDINARY_API_SECRET`, `CLOUDINARY_API_KEY`) remain strictly encapsulated within the NestJS API. The frontend web app and mobile clients only have access to `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`.
3. **Optimized Ingestion Pipeline:** Avoid overloading the Node.js API runtime with large video uploads by using **signed direct client uploads** for videos, while using **authenticated proxy uploads** for compact image assets.
4. **Metadata Synchronization:** Every uploaded asset is persisted as a relational record in PostgreSQL, establishing referential integrity with courses and lessons.
5. **Audited Deletion:** Media deletion cleans up binary assets from Cloudinary and handles database foreign key references.

## 2. Ingestion Workflows

### Flow A: Direct-to-Cloudinary Signed Client Upload (Large Files & Video Assets)

For video assets (course promotional videos and lesson lectures up to 100MB), clients bypass the API server's memory by uploading directly to Cloudinary using cryptographically signed authorization parameters generated by the backend:

```
┌─────────┐                ┌────────────┐               ┌────────────┐               ┌────────────┐
│ Client  │                │ NestJS API │               │ Cloudinary │               │ PostgreSQL │
└───┬─────┘                └─────┬──────┘               └─────┬──────┘               └─────┬──────┘
    │                             │                           │                            │
    │ 1. Request Signed Params    │                           │                            │
    │    (folder, file_type)      │                           │                            │
    ├────────────────────────────>│                           │                            │
    │                             │ 2. Compute HMAC Signature │                            │
    │                             │    using API Secret       │                            │
    │                             │                           │                            │
    │ 3. Return Signed Params     │                           │                            │
    │    (timestamp, signature,   │                           │                            │

    │<────────────────────────────┤                           │                            │
```

### Flow B: API-Proxied Image Upload (Images & Thumbnails <= 10MB)

For thumbnails and category icons, the client sends a `multipart/form-data` request directly to the NestJS API:
1. `POST /api/v1/media/upload/image` receives file buffer via Multer.
2. Server validates MIME type and file size.
3. Streamed via `CloudinaryService.uploadStream()` using Node.js stream pipelining.
4. On Cloudinary confirmation, a `media` row is inserted into PostgreSQL.
5. Emits `MEDIA_IMAGE_UPLOADED` audit event.
6. Returns `MediaResponseDto` to client.

## 3. Database Schema & Media Entity

PostgreSQL stores technical metadata and delivery URLs; Cloudinary hosts physical binaries and handles CDN edge distribution.

```typescript
export const media = pgTable(
  'media',
  {
    id: uuid('id').defaultRandom().primaryKey(),
    storageProvider: varchar('storage_provider', { length: 50 }).default('CLOUDINARY').notNull(),
    storageKey: varchar('storage_key', { length: 255 }).notNull(), // Cloudinary public_id
    publicUrl: text('public_url').notNull(),                      // CDN HTTPS delivery URL
    originalFilename: varchar('original_filename', { length: 255 }).notNull(),
    mimeType: varchar('mime_type', { length: 100 }).notNull(),
    fileSize: integer('file_size').notNull(),                      // In bytes
    durationSeconds: integer('duration_seconds'),                  // Video duration (seconds)
    metadata: text('metadata'),                                    // JSON stringified technical parameters
    createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
    updatedAt: timestamp('updated_at', { withTimezone: true }).defaultNow().notNull(),
  },
  (table) => [
    uniqueIndex('media_storage_key_uq').on(table.storageKey),
    index('media_storage_provider_idx').on(table.storageProvider),
  ]
);
```

### Metadata Payload Specification
The `metadata` column stores technical specifications as a JSON string:

## 4. Conventional Folder Hierarchy

All assets in Cloudinary are strictly organized under the `techsprout/` namespace:

| Asset Category | Target Folder | Resource Type | Max Size | Allowed MIME Types |
|---|---|---|---|---|
| **Course Thumbnails** | `techsprout/images/courses` | `image` | 10 MB | `image/jpeg`, `image/png`, `image/webp` |
| **Category Icons** | `techsprout/images/categories` | `image` | 5 MB | `image/jpeg`, `image/png`, `image/webp`, `image/svg+xml` |
| **Instructor Avatars** | `techsprout/images/instructors` | `image` | 5 MB | `image/jpeg`, `image/png`, `image/webp` |
| **Site Assets** | `techsprout/images/site` | `image` | 10 MB | `image/jpeg`, `image/png`, `image/webp`, `image/svg+xml` |
| **Course Promo Videos**| `techsprout/videos/courses` | `video` | 100 MB | `video/mp4`, `video/webm`, `video/quicktime` |
| **Lesson Lectures** | `techsprout/videos/lessons` | `video` | 100 MB | `video/mp4`, `video/webm`, `video/quicktime`, `video/x-matroska` |
| **Lesson PDFs** | `techsprout/raw/documents` | `raw` | 25 MB | `application/pdf` |

## 5. Deletion Lifecycle & Referential Integrity

Deleting media must ensure both database referential integrity and cloud storage cleanup:

1. **Dependency Check:** Before deleting a `media` record, the service checks whether it is referenced by:
   - Any course as `thumbnail_media_id`.
   - Any lesson as `media_id`.
2. **Referential Rule:** If an active course or lesson references the media, deletion is **rejected with `409 Conflict` (`MEDIA_IN_USE`)** unless the caller specifies `force = true`, which cascades `SET NULL` on referencing courses/lessons.
3. **Cloudinary Asset Cleanup:**
   - Calls `cloudinary.uploader.destroy(storageKey, { resource_type: type })`.
   - If Cloudinary reports deletion success or `not_found`, the PostgreSQL row is deleted.
   - If Cloudinary returns a network error, the transaction fails and the database row is retained to prevent orphaned cloud assets.
4. **Audit Action:** Logs `MEDIA_DELETED` with `targetType: 'MEDIA'`, `targetId: media.id`, and `storageKey`.

## 6. Security & Authorization

1. **Authentication:** All media upload and deletion endpoints require an authenticated session (`AuthGuard`).
2. **Role Boundaries:**
   - Image upload for courses: Restricted to `@Roles('admin', 'instructor')`.
   - Video upload for lessons: Restricted to `@Roles('admin', 'instructor')`.
   - Category icons: Restricted to `@Roles('admin')`.
   - Media deletion: Restricted to `@Roles('admin')` or the instructor who uploaded the media.
3. **Secret Isolation:**
   - `CLOUDINARY_API_SECRET` is never transmitted to the client.
   - Signed upload signatures expire after **15 minutes** (controlled by the `timestamp` parameter).
