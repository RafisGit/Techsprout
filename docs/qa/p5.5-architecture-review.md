## 3. Reconciliation of Key Architecture Corrections

### Correction 1 — Zero DB Locks During External SSLCommerz HTTP Calls
- **Initial Risk**: A proposal where admin approval executes a database transaction, calls SSLCommerz synchronously, and finalizes records within the same transaction would exhaust PostgreSQL connection pool threads under gateway latency or network delays.
- **Reconciled Architecture**:
  - Implemented as a strict two-phase flow matching P5 `RefundsService.initiateOrRetryRefund`.
  - Phase 1: Short DB transaction (< 10ms) acquires locks, verifies `order.status === 'PAID'`, updates `refund_requests.status = 'APPROVED'`, inserts/prepares `refunds` row (`status = 'PENDING'`), and commits. **All locks are released.**
  - Phase 2: HTTP call to SSLCommerz `initiateRefund` executes with **zero** open database transactions.
  - Phase 3: Short DB transaction records provider reference or failure.
  - Phase 4: Atomic finalization occurs only upon authoritative confirmation via query settlement or IPN.

### Correction 2 — Clean Separation of Refund Request State from Provider State
- **Initial Risk**: Conflation of student application state with payment gateway state (e.g. introducing ambiguous terms like `APPROVAL_PENDING`).
- **Reconciled Architecture**:
  - `refund_requests` state machine: `PENDING` -> `APPROVED` | `REJECTED`.
  - `refunds` operation state machine: `PENDING` -> `PROCESSED` | `FAILED`.
  - An approved request awaiting external resolution is cleanly represented by `refund_requests.status = 'APPROVED'` and `refunds.status = 'PENDING'`.

### Correction 3 — Order Status Transitions Only Upon Authoritative Completion
- **Initial Risk**: Marking an order as `REFUNDED` immediately when an admin clicks "Approve".
- **Reconciled Architecture**:
  - Admin approval initiates an external refund operation; `orders.status` remains `PAID`.
  - `orders.status` moves to `REFUNDED`, `enrollments.status` moves to `CANCELLED`, and `invoices.status` moves to `REFUNDED` **only** when `RefundsService.atomicFinalizeRefund` executes upon confirmed gateway settlement.
  - Historical invoice snapshots remain strictly immutable.

### Correction 4 — Uniqueness of Refund Requests
- **Policy Selected**: **Option B (Only One Active Request per Order)**.
- **Enforcement**: Partial unique index in PostgreSQL:
  ```sql
  CREATE UNIQUE INDEX "refund_requests_active_order_uq" ON "refund_requests" ("order_id")
  WHERE "status" IN ('PENDING', 'APPROVED');
  ```
  This allows students whose requests were legitimately rejected (e.g. wrong category selected) to re-apply if still within policy limits, while strictly preventing duplicate active submissions.

### Correction 5 — Explicit Resolution of Refund Policy
- **Audit Finding**: Neither `terms-and-condition/page.tsx` nor the P5 codebase establishes an authoritative 7-day or 20% threshold as an immutable business rule.
- **Reconciled Action**: Classified as **`PRODUCT DECISION REQUIRED`**. Recommended default of 7 calendar days (168 hours) from `order.paidAt` and < 20% progress is documented as an engineering proposal awaiting executive sign-off.

### Correction 6 — Server-Authoritative Eligibility Verification
- **Validation**: Zero trust placed in client input. When `POST /orders/:id/refund-request` is invoked, the backend independently verifies:
  1. Authenticated student identity (`req.user.id === order.studentId`).
  2. Order exists and has status `PAID`.
  3. `order.payableCents > 0`.
  4. Elapsed time from `order.paidAt` <= Policy Window.
  5. Associated `enrollment.status === 'ACTIVE'`.
  6. Course progress calculated via `LearningService.calculateProgress` < Maximum Threshold.
  7. No existing request with status `PENDING` or `APPROVED`.

### Correction 7 — Exact Relational Scoping
- **Path Enforced**:
  `refund_request` -> `orders` -> `order_items` -> `courses` -> `enrollments`.
  Queries explicitly match `studentId` and `courseId` to ensure the exact enrollment cancelled corresponds to the course purchased in that specific order.

### Correction 8 — Preservation of Existing Admin Direct Refund
- **Audit Finding**: P5 already implements `POST /api/v1/admin/orders/:id/refund`.
- **Reconciled Action**: The direct admin refund route remains active and unchanged for operational emergencies. Both the student-approved route and the direct route share `RefundsService.initiateOrRetryRefund`.

### Correction 9 & 10 — PDF Invoices & Security
- **Correction**: Replaced misleading "dependency-free" terminology with a concrete evaluation of `pdfkit`.
- **Security**: IDOR strictly prevented; `invoice.studentId === req.user.id` or `req.user.role === 'admin'` required. Rate-limited via NestJS throttler.
- **Tax/VAT**: Explicitly classified as **`TAX/VAT BREAKDOWN REQUIRES PRODUCT/ACCOUNTING DECISION`**. Renders subtotal, discount, and payable amount without synthetic tax lines.

### Correction 11 — Streaming CSV Export
- **Architecture**: Admin-only endpoint `GET /api/v1/admin/finance/export` utilizing Node.js streams to pipe CSV chunks directly to response, prepended with UTF-8 BOM (`\uFEFF`) and RFC 4180 escaping. Capped at 90 days or 10,000 rows.

### Correction 12 — Order History Architecture
- **Audit Finding**: Backend `GET /api/v1/orders` already implements student order querying with stable sorting (`desc(orders.createdAt)`).
- **Frontend Need**: Implement `/orders` (history list) and `/orders/[orderId]` (order details with refund CTA).

### Correction 13 & 14 — State Transitions & Concurrency
- Consolidated state matrix established across Order, Payment, Refund Request, Refund Operation, Invoice, and Enrollment.
- 8 specific race conditions evaluated with row-level locks (`FOR UPDATE`) and database constraints.

### Correction 15 — Audit Logging
- Reuses existing `audit_logs` table via `AuditService.record()` for all P5.5 lifecycle events. Zero credentials or payment secrets logged.

### Correction 16 — Certificate Interaction
- Confirmed that P5 `RefundsService.atomicFinalizeRefund` already updates `certificates.status = 'REVOKED'` with `revocationReason = 'Order refunded'`.

### Correction 17 — Coupon Interaction
- Consumed coupon redemptions remain in `CONSUMED` status upon refund. No automated coupon re-crediting is introduced.

### Correction 18 — Backward-Compatible Migration Strategy
- DDL is strictly additive: `refund_requests` table and enums. 0 changes to existing P5 tables or rows.
