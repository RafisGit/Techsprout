## 1. Objective

Implement the student-facing refund request workflow and API:
1. Evaluate student refund eligibility server-side strictly against authoritative order, enrollment, curriculum, and timeline records.
2. Provide secure endpoints for students to create and track refund requests without initiating immediate payment gateway refunds (creates `PENDING` request tickets only).
3. Enforce strict server-authoritative policies adhering to approved Product Decisions PD-1 through PD-5.
4. Provide safe DTO projections that never expose internal administrative, reviewer, or payment provider details to students.
5. Provide seamless frontend integration on the student order detail page (`/orders/[orderId]`) with real-time server eligibility evaluation, modal submission form, and lifecycle status banners.
6. Provide comprehensive automated unit, integration, and security tests.

## 2. Scope & Boundaries

### In-Scope (Completed)
- **Student Eligibility Evaluation**:
  - Validates order ownership (`order.studentId === req.user.id`).
  - Validates order status is `PAID` with non-null `order.paidAt`.
  - Enforces 7-calendar-day / 168-hour refund window calculated in UTC from `order.paidAt` (PD-1).
  - Enforces strict `< 20%` course progress calculated server-side from student's completed lessons in the purchased course (PD-2).
  - Enforces single active request per order (`PENDING` or `APPROVED`); allows resubmission if previous request was `REJECTED` and order remains within policy (PD-3).
  - Verifies exact course enrollment match and `ACTIVE` enrollment status.
- **Student Refund Request Endpoints**:
  - `POST /api/v1/refund-requests` (with `orderId`, `reasonCategory`, `reasonDetail`).
  - `GET /api/v1/refund-requests` (paginated, with optional `status` filter, scoped strictly to `req.user.id`).
  - `GET /api/v1/refund-requests/:id` (student-safe detail with IDOR protection).
  - `GET /api/v1/orders/:id/refund-eligibility` (pre-flight server-authoritative eligibility evaluation).
  - `POST /api/v1/orders/:id/refund-request` (order-scoped refund request submission).
- **Student-Safe DTO & Projections**:
  - `StudentRefundRequestDto` containing only safe fields (`id`, `requestNumber`, `orderId`, `status`, `reasonCategory`, `reasonDetail`, `courseProgressAtRequest`, `rejectionReason`, `createdAt`, `reviewedAt`).
  - Strips all administrative internals: `adminNotes`, `reviewedBy`, `reviewedByName`, `refundId`, and provider payloads are never leaked to students.
- **Concurrency & Transaction Integrity**:
  - Atomic database transactions with row-level locking (`FOR UPDATE`) on the target order row.
  - Handled concurrent submissions, concurrent state changes (order marked refunded during creation), and duplicate active requests via database partial unique index `refund_requests_active_order_uq`.
  - Zero external HTTP calls or gateway interactions during student submission; no DB lock held across external network.
- **Audit Logging**:
  - Emits `REFUND_REQUEST_SUBMITTED` events through `AuditService.record()` capturing actor, request correlation, order ID, course ID, reason category, and progress without sensitive secrets.
- **Frontend Integration**:
  - Integrated into `/orders/[orderId]` order details view.
  - Queries server eligibility via `fetchOrderRefundEligibility(orderId)`.
  - Status display for `PENDING` (under administrative review), `APPROVED` (processing with payment gateway), `REJECTED` (with public reason and resubmit affordance), and `REFUNDED` orders.
  - Modal form with reason category dropdown (`COURSE_CONTENT_MISMATCH`, `TECHNICAL_ISSUES`, `ACCIDENTAL_PURCHASE`, `PERSONAL_REASONS`, `OTHER`), trimmed detail textarea (10–1000 chars), validation errors, and mutation states.
- **Automated Tests**:
  - 30 comprehensive API tests in `apps/api/src/test/student-refund-requests.spec.ts`.
  - 10 comprehensive Web tests in `apps/web/src/__tests__/student-refunds.spec.ts`.

## 5. Policy Enforcement & Boundary Matrix

| Policy Rule | Specification | Boundary Test Cases | Enforcement |
|:---|:---|:---|:---|
| **PD-1: Refund Window** | Exactly 168 hours (7 days) from `order.paidAt` in UTC | 167h 59m (ACCEPTED), 168h 00m (ACCEPTED), 168h 01m (REJECTED: `REFUND_WINDOW_EXPIRED`) | Server-side UTC delta check against `order.paidAt` |
| **PD-2: Course Progress** | Strictly `< 20%` course progress | 0% (ACCEPTED), 19% (ACCEPTED), 20% (REJECTED: `REFUND_PROGRESS_LIMIT_EXCEEDED`), 21% (REJECTED), 100% (REJECTED) | Server-side calculation from `lesson_completions` vs curriculum lessons |
| **PD-3: Request Multiplicity** | Exactly one active request per order (`PENDING` or `APPROVED`) | Concurrent duplicate submission (REJECTED: `REFUND_REQUEST_ALREADY_ACTIVE`), Resubmission after `REJECTED` (ACCEPTED if within policy) | Partial unique index `refund_requests_active_order_uq` + transactional check |
| **Order Status** | Must be `PAID` with non-null `paidAt` | `PENDING` order (REJECTED), `CANCELLED` order (REJECTED), `REFUNDED` order (REJECTED), `PAID` without `paidAt` (REJECTED) | State validation inside transaction |
| **Enrollment Integrity** | Must match exact course from order item with `ACTIVE` status | Inactive enrollment (REJECTED: `ENROLLMENT_INELIGIBLE`), Unenrolled student (REJECTED) | Relational lookup `orders -> order_items -> enrollments` |
| **Input Validation** | Category must be valid enum; detail 10–1000 characters trimmed | 9 characters (REJECTED: `VALIDATION_ERROR`), 10 characters (ACCEPTED), 1000 characters (ACCEPTED), 1001 characters (REJECTED) | Zod schema validation + DB check constraint |

## 6. Concurrency & IDOR Protections

1. **Transaction Isolation & Row Locking**:
   - `RefundRequestsService.createRefundRequest` executes within an atomic PostgreSQL transaction.
   - Executes `SELECT ... FROM orders WHERE id = :orderId FOR UPDATE` to serialize concurrent requests for the same order and guarantee `order.status` cannot change concurrently.
2. **Double-Submission & Race Protection**:
   - Database partial unique index `refund_requests_active_order_uq` acts as a fail-safe backstop against race conditions, preventing two concurrent threads from inserting duplicate active requests.
3. **Student IDOR Protection**:
   - Every request verifies `order.studentId === authenticatedUserId` and `request.studentId === authenticatedUserId`.
   - Unauthorized attempts to inspect another student's order or refund request return 403 Forbidden with generic safe error messages.

## 7. Audit Logging

Every successful refund request creation generates an immutable audit record:
- **Action**: `REFUND_REQUEST_SUBMITTED`
- **Actor**: Student ID (`req.user.id`)
- **Target Entity**: `refund_requests` (`data.id`)
- **Metadata Recorded**:
  - `orderId`: Order ID
  - `courseId`: Course ID
  - `enrollmentId`: Enrollment ID
  - `requestNumber`: Request number
  - `reasonCategory`: Reason category
  - `courseProgressAtRequest`: Progress percentage at request time
  - `payableCents`: Authoritative order amount
  - Correlation tracking: `ip`, `userAgent`, `requestId`
- **Zero Sensitive Data**: No passwords, tokens, session cookies, or payment gateway credentials logged.
