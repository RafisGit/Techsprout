## 1. Security Architecture Overview

Phase 6.1 implements the zero-trust authorization model designed in ADR-P6-001 to eliminate Insecure Direct Object References (IDOR) across all course authoring and media assets.

The core defense mechanism is `ResourceOwnershipGuard`, a NestJS guard that works in conjunction with the `@RequireOwnership(resourceType, idParamKey)` decorator.

### Key Security Principles

1. **Contextual Traversal:** Permissions are not evaluated on isolated IDs alone. For hierarchical assets (Modules, Lessons, Quizzes, Questions, Options), the guard traverses parent relationships all the way up to the parent Course record to verify that `course.instructorId === req.user.id`.
2. **Superuser Isolation:** Superusers (`req.user.role === 'admin'`) bypass instructor-level ownership checks to perform administrative management.
3. **Fail-Closed Default:** If an entity is not found, an `ApiException` with HTTP 404 NOT_FOUND is raised. If an authenticated user's ID does not match the resource's owner, an `ApiException` with HTTP 403 FORBIDDEN is raised, and an audit trail entry is persisted.
4. **Server-Side Identity Binding:** The client cannot supply or alter ownership metadata such as `uploader_id`. All identities are extracted directly from the verified session context (`req.user.id`).

## 2. Resource Authorization Matrix

| Resource Type     | Decorator                                   | Traversal Query                                                                                                                                                                      | HTTP 403 Condition                                  |
| ----------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **Course**        | `@RequireOwnership('course', 'id')`         | `SELECT instructorId FROM courses WHERE id = :id`                                                                                                                                    | `instructorId !== req.user.id`                      |
| **Module**        | `@RequireOwnership('module', 'id')`         | `SELECT courses.instructorId FROM modules JOIN courses ON modules.course_id = courses.id WHERE modules.id = :id`                                                                     | `courseInstructorId !== req.user.id`                |
| **Lesson**        | `@RequireOwnership('lesson', 'id')`         | `SELECT courses.instructorId FROM lessons JOIN modules ON lessons.module_id = modules.id JOIN courses ON modules.course_id = courses.id WHERE lessons.id = :id`                      | `courseInstructorId !== req.user.id`                |
| **Quiz**          | `@RequireOwnership('quiz', 'id')`           | `SELECT courses.instructorId FROM quizzes JOIN modules ON quizzes.module_id = modules.id JOIN courses ON modules.course_id = courses.id WHERE quizzes.id = :id`                      | `courseInstructorId !== req.user.id`                |
| **Quiz Question** | `@RequireOwnership('quizQuestion', 'id')`   | `SELECT courses.instructorId FROM quiz_questions JOIN quizzes ON ... JOIN modules ON ... JOIN courses ON ... WHERE quiz_questions.id = :id`                                          | `courseInstructorId !== req.user.id`                |
| **Quiz Option**   | `@RequireOwnership('quizOption', 'id')`     | `SELECT courses.instructorId FROM quiz_question_options JOIN quiz_questions ON ... JOIN quizzes ON ... JOIN modules ON ... ## 3. IDOR Penetration Testing Evidence

Testing conducted via automated test suite `apps/api/src/test/p6-resource-ownership.spec.ts`:

### Scenario A — Cross-Instructor Course Mutation

- **Test:** Instructor 1 attempts `PATCH /admin/courses/:course2Id` owned by Instructor 2.
- **Payload:** `{ title: "Tampered Course Title" }`
- **Result:** HTTP 403 Forbidden. Course record unmodified in database.
- **Audit:** `UNAUTHORIZED_RESOURCE_ACCESS_ATTEMPT` recorded for `actorId = instructor1.id`, `targetType = COURSE`, `targetId = course2Id`.

### Scenario B — Cross-Instructor Module Creation

- **Test:** Instructor 1 attempts `POST /admin/courses/:course2Id/modules` on a course owned by Instructor 2.
- **Result:** HTTP 403 Forbidden. Module not created.

### Scenario C — Cross-Instructor Lesson Mutation

- **Test:** Instructor 1 attempts `PATCH /admin/lessons/:lesson2Id` residing inside a module of Instructor 2's course.
- **Result:** HTTP 403 Forbidden.

### Scenario D — Cross-Instructor Quiz / Question / Option Mutation

- **Test:** Instructor 1 attempts `PATCH /admin/quizzes/:quiz2Id`, `PATCH /admin/questions/:q2Id`, `PATCH /admin/options/:opt2Id` owned by Instructor 2.
- **Result:** HTTP 403 Forbidden across all levels.

### Scenario E — Cross-Instructor Media Overwrite

- **Test:** Instructor 1 attempts `POST /media/replace` targeting `media2.storageKey` uploaded by Instructor 2.
- **Result:** HTTP 403 Forbidden. Cloudinary replacement bypassed, database media unchanged.

### Scenario F — Student Privilege Escalation

- **Test:** Student account attempts to access protected `@RequireOwnership` instructor endpoints.
- **Result:** HTTP 403 Forbidden (`Access denied: insufficient permissions`).

### Scenario G — Superuser Administration Bypass

- **Test:** Admin superuser executes `PATCH /admin/courses/:course1Id` and `PATCH /admin/courses/:course2Id`.
- **Result:** HTTP 200 OK across both courses.

## 4. Notification Subsystem Security

### User Scoping & IDOR Prevention

1. `GET /api/v1/notifications`: Always scopes SQL query with `WHERE user_id = req.user.id`.
2. `GET /api/v1/notifications/unread-count`: Always scopes SQL query with `WHERE user_id = req.user.id AND is_read = false`.
3. `PATCH /api/v1/notifications/:id/read`: Checks `notification.userId === req.user.id`. Unauthorized access attempts return HTTP 403 Forbidden and record `UNAUTHORIZED_NOTIFICATION_ACCESS` in `audit_logs`.
4. `PATCH /api/v1/notifications/read-all`: Updates only rows matching `user_id = req.user.id`.

### Mass Assignment Hardening

The endpoint `PATCH /api/v1/notifications/preferences` accepts `updateNotificationPreferencesSchema` which enforces Zod `.strict()`.

- If a client attempts to submit malicious fields such as `userId`, `role`, `isVerified`, or `createdAt`, validation fails immediately with HTTP 400 Bad Request.
- Service implementation updates only whitelisted boolean fields: `emailCourseUpdates`, `emailPromotions`, and `inAppAll`.

## 5. External I/O and Transaction Security

### Invariant: Zero External Network I/O in Database Transactions

- Checked: Payments (`payments.service.ts`), Orders (`orders.service.ts`), Refunds (`refunds.service.ts`), Refund Requests (`refund-requests.service.ts`), Enrollments (`enrollments.service.ts`), and Certificates (`certificates.service.ts`).
- Verification: Database transactions only write state to PostgreSQL.
- Post-Commit Dispatch: Events are dispatched via `this.outboxService.emit(...)` strictly after transaction completion.
- Network Calls: Calls to SSLCommerz, Resend, and Redis are strictly executed outside transactions.

## 6. Audit Trail Compliance

All security violations generate structured entries in `audit_logs`:

- **Event Actions:** `UNAUTHORIZED_RESOURCE_ACCESS_ATTEMPT`, `UNAUTHORIZED_NOTIFICATION_ACCESS`.
- **Context Recorded:** Actor User ID, Target Resource Type, Target Resource ID, Client IP, User-Agent, Correlation Request ID (`X-Request-Id`), and Timestamp.
- **Zero Secrets Logged:** Passwords, payment tokens, API keys, and session cookies are completely excluded from log payloads.
