## 4. Metric Semantics & Data Integrity Audit

A comprehensive review of metric semantics was performed against the database schema, business logic, and actual Drizzle SQL queries.

### 4.1 Investigation of `completedCertificatesCount`
- **Initial Finding / Question:** WP-05 documentation colloquially described `completedCertificatesCount` as "the number of courses with 100% completion".
- **Code Audit:** In `apps/api/src/modules/analytics/analytics.service.ts` (lines 660–666):
  ```typescript
  const [certResult] = await this.db
    .select({ count: count(certificates.id) })
    .from(certificates)
    .where(
      and(
        eq(certificates.studentId, studentId),
        eq(certificates.status, 'ACTIVE')
      )
    );
  ```
- **Semantic Determination:** The backend query queries the **authoritative `certificates` table** for records where `status = 'ACTIVE'`. It does **not** merely count courses where progress equals 100%. If a student completes a course but certificate issuance failed or was revoked, it is not counted. Conversely, if a certificate is active, it is counted.
- **Resolution:** The implementation strictly and accurately represents **issued active certificates**. No code modification was required. The documentation narrative is formally reconciled in this release gate report.

### 4.2 Other Metric Semantics Audit
| Metric Field | Underlying Query / Logic | Semantic Behavior & Privacy Safeguards |
|---|---|---|
| **Unique Learners vs. Enrollments** | `countDistinct(enrollments.studentId)` vs `count(enrollments.id)` | Distinct count prevents inflating learner count when a single student enrolls in multiple courses. |
| **Completion Rate** | `(completedCount / totalEnrollments) * 100` | Clamped to [0, 100] with fallback to 0% when total enrollments is zero (zero-division defense). |
| **Quiz Pass Rate** | `(passedAttempts / totalAttempts) * 100` | Calculated strictly from submitted attempts where `passed = true`. In-progress attempts are excluded. |
| **Review Turnaround Time** | `avg(course_reviews.reviewed_at - course_reviews.submitted_at)` | Averages completed review durations. Pending reviews do not distort turnaround metrics. |
| **Date Boundaries & UTC** | Grouped by `date_trunc('day'/'week'/'month', ...)` in UTC | Consistent ISO-8601 UTC date formatting across backend time series and frontend chart axes. |
| **Small-Cohort Privacy** | Instructor Course Analytics | Aggregate KPIs for small courses (<5 learners) do not disclose PII in aggregated view; individual records are only visible in the authenticated roster table where the instructor has legitimate educational interest. |
| **Admin Metrics Scope** | Platform Overview | Aggregates platform-wide counts, top-performing courses, and category distributions without exposing individual student PII or passwords. |

## 6. Migration 0008 Safety & Compatibility Assessment

- **Migration File:** `apps/api/src/database/migrations/0008_analytics_foundation.sql`
- **Migration Journal:** `apps/api/src/database/migrations/meta/_journal.json` (entry `0008_analytics_foundation`, version 7, tag `0008_analytics_foundation`)
- **Statements in Migration:**
  ```sql
  CREATE INDEX IF NOT EXISTS "enrollments_course_enrolled_at_idx" ON "enrollments" USING btree ("course_id","enrolled_at");
  CREATE INDEX IF NOT EXISTS "enrollments_status_enrolled_at_idx" ON "enrollments" USING btree ("status","enrolled_at");
  CREATE INDEX IF NOT EXISTS "lesson_progress_lesson_status_idx" ON "lesson_progress" USING btree ("lesson_id","status");
  CREATE INDEX IF NOT EXISTS "quiz_attempts_quiz_passed_idx" ON "quiz_attempts" USING btree ("quiz_id","passed");
  ```
- **Safety Assessment Findings:**
  1. **Locking Behavior Accurately Documented:** The migration executes inside a transaction via Drizzle. Ordinary PostgreSQL `CREATE INDEX` acquires `SHARE` locks on the target tables (`enrollments`, `lesson_progress`, `quiz_attempts`), permitting concurrent `SELECT` reads but briefly blocking write operations (`INSERT`, `UPDATE`, `DELETE`) until transaction commit. This is accurately documented across planning documents.
  2. **Index Scope:** Only 4 secondary btree indexes are introduced to optimize composite joins and filtering. Zero table additions, zero column alterations, zero column deletions.
  3. **Zero Telemetry Tables:** Telemetry tables (e.g. `learning_events`) and event dispatch remain deferred to Phase 7.
  4. **Live Execution Prohibition:** Migration 0008 was **not executed** against any live database during WP-06.
