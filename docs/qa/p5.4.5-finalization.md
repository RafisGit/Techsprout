## 3. Backend Finance APIs Added

To establish the minimum backend foundation required by P5.4.5 without duplicating pre-existing endpoints:

### A. Authoritative Finance Summary API
- **Endpoint:** `GET /api/v1/admin/finance/summary`
- **Controller:** `AdminFinanceController` (`apps/api/src/modules/finance/admin-finance.controller.ts`)
- **Service:** `FinanceService.getFinanceSummary()`
- **Guards:** `@UseGuards(RolesGuard)`, `@Roles('admin')`
- **Authoritative Aggregations (SQL):**
  - `totalGrossVolumeCents`: Sum of `payable_cents` for finalized orders with status `PAID` or `REFUNDED`. (Failed/pending/cancelled orders excluded).
  - `totalDiscountCents`: Sum of `discount_cents` represented by finalized orders (`PAID` or `REFUNDED`).
  - `totalRefundCents`: Sum of `amount_cents` from `refunds` where status is `PROCESSED`. (Pending/unconfirmed refunds excluded).
  - `totalNetRevenueCents`: `totalGrossVolumeCents - totalRefundCents`.
  - `totalPaidOrdersCount`: Count of orders with status `PAID`.
  - `totalRefundedOrdersCount`: Count of orders with status `REFUNDED`.
  - `totalPendingOrdersCount`: Count of orders with status `PENDING` or `PAYMENT_PROCESSING`.
  - `totalCancelledOrdersCount`: Count of orders with status `CANCELLED`.
  - `currency`: `'BDT'`.

### B. Admin Orders Explorer API
- **Endpoint:** `GET /api/v1/admin/orders`
- **Controller:** `AdminOrdersController` (`apps/api/src/modules/orders/admin-orders.controller.ts`)
- **Service:** `OrdersService.listAdminOrders(query)`
- **Guards:** `@UseGuards(RolesGuard)`, `@Roles('admin')`
- **Query Filters:** `status`, `search` (orderNumber, student email, student name via SQL ILIKE), `startDate`, `endDate`, `page`, `limit`.
- **Response:** `PaginatedOrdersData` containing `OrderListItemDto[]` with student snapshot data and financial totals.
- **Detail Endpoint:** `GET /api/v1/admin/orders/:id` for full administrative inspection.

### C. Safe Reconciliation Scanner API
- **Endpoint:** `GET /api/v1/admin/reconciliation`, `POST /api/v1/admin/reconciliation/scan`
- **Controller:** `AdminReconciliationController` (`apps/api/src/modules/finance/admin-reconciliation.controller.ts`)
- **Service:** `FinanceService.scanReconciliation(query, actorId)`
- **Guards:** `@UseGuards(RolesGuard)`, `@Roles('admin')`
- **Safe Rules vs Ambiguous Cases:**
  - `GATEWAY_VALIDATED_INTERNAL_PENDING`: Payment is `VALIDATED` while order is `PENDING`/`PAYMENT_PROCESSING`. If amounts and currency match: `autoResolvable: true`. In non-dryRun, transitions order to `PAID`, consumes coupon, creates enrollment and invoice, and logs audit record.
  - `PAID_WITHOUT_ENROLLMENT`: Order is `PAID` but enrollment is missing. `autoResolvable: true`. In non-dryRun, safely inserts active enrollment and logs audit record.
  - `AMOUNT_MISMATCH`: Payment amount != Order payable amount. Marked `autoResolvable: false` (Ambiguous! Never auto-resolved, flagged for manual review).
  - `CURRENCY_MISMATCH`: Payment currency != Order currency. Marked `autoResolvable: false` (Ambiguous! Never auto-resolved).

## 4. Finance Dashboard

- **Route:** `/admin/finance` (`apps/web/src/app/admin/finance/page.tsx`)
- **Sub-Navigation:** `FinanceSubNav` provides fluid navigation between Overview (`/admin/finance`), Orders Explorer (`/admin/finance/orders`), and Reconciliation (`/admin/finance/reconciliation`).
- **KPI Cards:**
  - **Gross Volume:** BDT formatted total payable volume before refunds.
  - **Total Discounts:** BDT formatted savings from coupons.
  - **Net Revenue:** BDT formatted Net Revenue (`Gross Volume - Confirmed Refunds`).
  - **Total Refunds:** BDT formatted provider-confirmed refunds.
  - **Lifecycle Counts:** Paid Orders, Pending Orders, Refunded Orders, Cancelled Orders.
- **Formatting:** All currency values formatted via `formatBDT()` in integer minor units (poisha / 100), with commas and 2 decimal places (e.g. `BDT 125,000.00`). No floating-point accumulation; USD is never displayed.

  - **Security Guarantee:** Provider store passwords and credentials are never exposed. Admins cannot client-mutate payment status.

## 6. Refund Administration

- **Modal Trigger:** Available on paid orders in both the Orders table and the Order Detail modal.
- **Strict Warning UX:**
  - Displays order number, student email, course title, and locked refund amount in BDT.
  - Informs admin that refunds are full-refund-only, derived by the server, asynchronous via SSLCommerz, and that processed refunds are permanent and terminal.
  - Non-editable amount: No amount input field is provided in the UI; the server dictates the full payable total.
  - Collects mandatory refund justification reason (minimum 5 characters).
- **State Distinctions:**
  - `PENDING` with provider reference: Displays "Awaiting Settlement" with a "Check Status" button calling `POST /api/v1/admin/refunds/:id/query`.
  - `PENDING` without provider reference: Displays "Manual Review Required" warning callout with actions to link reference or mark failed.
  - `FAILED`: Displays "Failed" with a "Retry" button calling `POST /api/v1/admin/orders/:id/refund`.
  - `PROCESSED`: Displays "Settled / Processed" with no further mutation actions (terminal state).

## 7. Reconciliation UI

- **Route:** `/admin/finance/reconciliation` (`apps/web/src/app/admin/finance/reconciliation/page.tsx`)
- **Tab 1 — Refund Operations:**
  - Table of all refunds with status filters.
  - For ambiguous refunds missing provider references:
    - **Link Provider Reference Dialog:** Accepts authoritative provider refund reference ID and executes `POST /api/v1/admin/refunds/:id/reconcile` with `LINK_PROVIDER_REFERENCE`.
    - **Mark Failed Dialog:** Accepts failure reason and executes `POST /api/v1/admin/refunds/:id/reconcile` with `MARK_FAILED`, keeping order in `PAID` status and allowing clean administrative retry.
- **Tab 2 — Automated Discrepancy Scanner:**
  - On-demand "Run Discrepancy Scan" button with a "Dry Run" toggle.
  - Summary metrics: total orders scanned, discrepancies detected, and auto-resolved count.
  - Detailed discrepancy listing showing order number, discrepancy type, description, and resolution policy badge (`Safe Auto-Resolve` vs `Manual Review Required`).
  - Guarantees that ambiguous cases (`AMOUNT_MISMATCH`, `CURRENCY_MISMATCH`) are never auto-resolved by the frontend or backend.

## 9. RBAC & Security

1. **Server-Side Enforcement:**
   - Every backend endpoint (`admin/finance/*`, `admin/orders/*`, `admin/reconciliation/*`, `admin/coupons/*`, `admin/refunds/*`) is protected by `RolesGuard` and `@Roles('admin')`.
   - Verified via automated API tests that unauthenticated requests receive `401 Unauthorized` and student requests receive `403 Forbidden`.
2. **Client-Side Authorization:**
   - Admin layouts and finance/coupon pages verify `currentUser?.role === 'admin'`.
   - Non-admin users are greeted with a standard Access Denied (403 Forbidden) shield card with a return-to-dashboard CTA.
   - Admin navigation tabs for Finance and Coupons are conditionally visible only to `admin` users.
3. **Data Protection:**
   - Gateway store passwords, store IDs, and provider credentials are never returned in DTOs or exposed to the browser.
   - Payment status cannot be altered directly by clients; state transitions are strictly governed by backend gateway callbacks and reconciliation services.

## 12. Performance Considerations

- **SQL Aggregations:** `FinanceService.getFinanceSummary()` executes 3 grouped/aggregated SQL queries (`SUM`, `COUNT`) directly in PostgreSQL. No unbounded sets of orders or refunds are loaded into Node.js memory.
- **Pagination Everywhere:** All order, payment, refund, and coupon queries enforce default pagination (`page`, `limit`), preventing unbounded memory usage.
- **Query Invalidation:** React Query handles surgical cache invalidations on mutations without requiring full-page reloads.

## 17. Known Limitations

- Multi-currency: Techsprout currently operates exclusively with Bangladeshi Taka (BDT). Foreign currencies (USD, EUR) are disallowed at both the schema and gateway integration layers.
- Partial Refunds: In accordance with the frozen P5 architecture, partial refunds are not supported; refund operations are full-refund only.
