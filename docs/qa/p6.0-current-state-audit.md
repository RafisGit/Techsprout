## 3. Discrepancies Between Repository and Master Handoff

During the repository audit, three key discrepancies were identified between documentation assumptions and the codebase:

1. **Instructor Access to Admin Navigation vs Admin Overview:**
   - *Handoff / Doc Assumption:* `AdminNav` allows instructors to view the management area.
   - *Repository Reality:* `apps/web/src/components/admin/AdminNav.tsx` shows `Overview` (`/dashboard/admin/overview`) to all users with `show: true`. However, `apps/web/src/app/dashboard/admin/overview/page.tsx` contains an explicit guard: `if (!user || user.role !== 'admin') return <403 Forbidden>`. When an authenticated instructor clicks "Overview", they immediately receive an HTTP 403 Access Denied banner.
   - *Resolution:* Documentation must recognize this as an unresolved information architecture bug.

2. **Course Deletion Status Rule:**
   - *Handoff / Doc Assumption:* Courses can be archived by instructors.
   - *Repository Reality:* In `apps/api/src/modules/courses/courses.service.ts`, `archive`, `publish`, and `unpublish` are decorated with `@Roles('admin')`. Instructors can ONLY delete a course if `status === 'DRAFT'`. Once a course is published, the instructor cannot unpublish or archive their own course without an administrator.
   - *Resolution:* This represents a deliberate administrative curation model, but confirms that instructors lack lifecycle autonomy.

3. **Media Table Asset Scoping:**
   - *Handoff / Doc Assumption:* Media management is role-protected for admin and instructor.
   - *Repository Reality:* In `apps/api/src/database/schema/media.ts`, the table contains only `storage_key`, `public_url`, and metadata, with no `user_id` or `uploader_id`. In `media.controller.ts`, `@Roles('admin', 'instructor')` can upload media, but assets cannot be filtered or authorized by instructor identity. An instructor could theoretically attach any uploaded `mediaId` to their lessons.
   - *Resolution:* Requires an architectural fix in P6 database modeling.

## 4. Current Architecture Strengths

1. **Deterministic Financial Safety:** The P5 and P5.5 payment and refund architectures are exceptional. Non-blocking two-phase commits ensure that external gateway timeouts never lock database rows or cause stranded states.
2. **Server-Authoritative Evaluation:** Quizzes and learning progress cannot be spoofed by the client. Quiz grading is entirely computed on the backend without answer key exposure.
3. **Clean Drizzle ORM Relational Mapping:** PostgreSQL schemas have strict foreign keys, cascading deletion where appropriate, and unique constraints that enforce business invariants at the database level.
4. **Contract-Driven Monorepo:** `@techsprout/contracts` guarantees end-to-end type safety between NestJS and Next.js, dramatically reducing API integration bugs.
