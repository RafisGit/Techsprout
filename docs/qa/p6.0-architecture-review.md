## 1. Architectural Scope & Principles

Phase 6 must extend the existing production-stabilized architecture (NestJS + PostgreSQL + Drizzle ORM + Redis/BullMQ + Next.js 16) without replacing or destabilizing verified invariants from P1–P5.5.

### Core Architectural Invariants:
1. **Financial Immutability:** No changes to the two-phase payment and refund state machines, monetary minor-unit calculations (`moneyCents`), or invoice snapshot models.
2. **Non-Blocking External IO:** All outbound communications (emails, SMS, webhooks, heavy analytics calculations) must execute asynchronously outside database transactions via BullMQ workers.
3. **Fail-Safe Authorization:** Role-based checks (`RolesGuard`) must be strictly reinforced with contextual Resource Ownership Guards to eliminate Insecure Direct Object References (IDOR).
4. **Lean Evolution:** Avoid premature adoption of separate analytics warehouses (BigQuery/ClickHouse) or microservices. Maintain clean modular monolith boundaries within NestJS.

## 2. RBAC & Resource Ownership Architecture

### 2.1 The Problem: Role-Level Authorization Insufficiency
In the current system:
- `@Roles('admin', 'instructor')` permits any user with the instructor role to access administrative endpoints.
- Ownership checks are scattered across individual service methods (`verifyCourseOwnership`, `resolveModuleOwnership`, `resolveLessonOwnership`, `resolveQuizOwnership`).
- If an endpoint or developer forgets to invoke the service-level check, an instructor could modify another instructor's modules, lessons, or quizzes.
- The `media` table currently lacks an `uploader_id` or `tenant_id`, making asset isolation impossible.

### 2.2 Proposed Solution: Multi-Level Contextual Authorization Guard
We propose introducing a declarative `ResourceOwnershipGuard` combined with a hierarchical ownership resolution mechanism:

```text
HTTP Request
     │
     ▼
[ AuthGuard ] ────────────► Sets req.user (id, role)
     │
     ▼
[ RolesGuard ] ───────────► Verifies required role ('admin' | 'instructor' | 'student')
     │
     ▼
[ ResourceOwnershipGuard ]─► Admin: BYPASS (Institutional Superuser)
     │                       Instructor: Enforces Ownership Chain:
     │                         - Course: course.instructorId === req.user.id
     │                         - Module: module.course.instructorId === req.user.id
     │                         - Lesson: lesson.module.course.instructorId === req.user.id
     │                         - Quiz:   quiz.module.course.instructorId === req.user.id
     ▼
Controller Handler
```

### 2.3 Proposed Entity: `instructor_profiles`
To support rich instructor identities, public attribution, and future payout configurations:
- Table: `instructor_profiles`
- Foreign Key: `user_id` -> `users.id` (1-to-1, Unique, Cascade Delete)
- Fields: `headline` (varchar 150), `bio` (text), `website_url` (varchar 255), `social_links` (jsonb), `payout_account_details` (jsonb encrypted/restricted), `is_approved` (boolean default false), `created_at`, `updated_at`.

## 3. Event & Notification Architecture

### 3.1 Transactional Decoupling via Domain Events
Currently, business mutations execute synchronously. To prevent external provider latency (e.g., SMTP or Resend HTTP calls) from impacting transaction performance or payment callbacks, we propose a decoupled event pipeline:

```text
Domain Operation (e.g., Order Settled, Refund Approved, Certificate Issued)
     │
     ▼ (Within DB Transaction or Immediate Post-Commit)
[ Domain Event Emitter / Outbox ]
     │
     ▼ (Enqueues Job)
[ Redis / BullMQ Queue: "techsprout-notifications" ]
     │
     ▼ (Worker Consumption with Exponential Backoff)
[ Notification Worker ]
     ├── 1. Check User Notification Preferences
     ├── 2. Persist In-App Record (`notifications` table)
     ├── 3. Render Template (Email / Future SMS)
     └── 4. Transmit via Provider (e.g., Resend / SendGrid / Postmark)
             │
             ├── On Success: Update `notification_deliveries` -> 'DELIVERED'
             └── On Failure: Retry (3 attempts) -> DLQ (`notification_deliveries` -> 'FAILED')
```

### 3.2 Proposed Notification Entities:
1. **`notifications` (In-App Inbox):**
   - `id` (uuid, PK)
   - `user_id` (uuid, FK users.id, Cascade)
   - `title` (varchar 200)
   - `message` (text)
   - `category` (enum: 'TRANSACTIONAL', 'ACADEMIC', 'SYSTEM')
   - `action_url` (text nullable)
   - `is_read` (boolean default false)
   - `read_at` (timestamp with tz nullable)
   - `created_at` (timestamp with tz default now)
   - Indexes: `(user_id, is_read, created_at desc)`

2. **`notification_preferences`:**
   - `id` (uuid, PK)
   - `user_id` (uuid, FK users.id, Unique, Cascade)
   - `email_marketing` (boolean default false)
   - `email_course_updates` (boolean default true)
   - `email_transactional` (boolean default true - non-editable)
   - `in_app_all` (boolean default true)
   - `updated_at` (timestamp with tz)

3. **`notification_deliveries` (Audit Trail):**
   - `id` (uuid, PK)
   - `notification_id` (uuid, FK notifications.id nullable)
   - `channel` (enum: 'EMAIL', 'IN_APP', 'SMS')
   - `recipient` (varchar 255)
   - `provider_message_id` (varchar 255 nullable)
   - `status` (enum: 'PENDING', 'SENT', 'FAILED', 'BOUNCED')
   - `error_message` (text nullable)
   - `attempt_count` (integer default 1)
   - `delivered_at` (timestamp with tz nullable)

## 4. Learning Analytics Architecture

### 4.1 Evaluation of Options:
- **Option A (Query Transactional Tables Directly):**
  - *Pros:* Zero new entities, zero migration cost.
  - *Cons:* Transactional rows (`lesson_progress`, `enrollments`) only show the latest snapshot. No historical engagement curve, drop-off heatmap, or daily active learner count can be calculated.
- **Option B (Append-Only PostgreSQL `learning_events` Model):**
  - *Pros:* Highly structured, records full behavioral history, low operational complexity, runs entirely within existing Render PostgreSQL and NestJS runtime, perfectly prepares data for future AI recommendation models.
  - *Cons:* Table size grows over time; requires periodic archiving or indexing partitions after 1M+ rows.
- **Option C (External Analytics Warehouse — BigQuery / ClickHouse / Snowflake):**
  - *Pros:* Infinite scale, fast analytical aggregations.
  - *Cons:* Huge architectural overkill, significant hosting cost, operational maintenance burden, and distributed consistency challenges for TechSprout's current scale.

### 4.2 Recommendation: Option B (PostgreSQL Append-Only `learning_events`)
Introduce a lean, append-only table to record significant learning milestones:
- Table: `learning_events`
- `id` (uuid, PK)
- `user_id` (uuid, FK users.id)
- `course_id` (uuid, FK courses.id)
- `module_id` (uuid, FK modules.id nullable)
- `lesson_id` (uuid, FK lessons.id nullable)
- `event_type` (enum: 'COURSE_OPENED', 'LESSON_STARTED', 'VIDEO_CHECKPOINT', 'LESSON_COMPLETED', 'QUIZ_ATTEMPTED', 'CERTIFICATE_EARNED')
- `metadata` (jsonb — stores checkpoint position, score, device type)
- `occurred_at` (timestamp with tz default now)
- Indexes: `(user_id, occurred_at desc)`, `(course_id, event_type, occurred_at desc)`

## 5. Course Publication Lifecycle Revision

Currently, courses transition directly: `DRAFT -> PUBLISHED -> ARCHIVED` (Admin only).
To support decentralized instructors without risking catalog quality, the lifecycle should expand:

```text
┌─────────┐   Instructor Submits    ┌───────────┐   Admin Approves   ┌───────────┐
│  DRAFT  ├────────────────────────►│ IN_REVIEW ├───────────────────►│ PUBLISHED │
└────┬────┘                         └─────┬─────┘                    └─────┬─────┘
     ▲                                    │ Admin Rejects                  │
     └────────────────────────────────────┘                                │
                          Admin Archives                                   │
                                ┌──────────────────────────────────────────┘
                                ▼
                         ┌──────────┐
                         │ ARCHIVED │
                         └──────────┘
```

1. **`DRAFT`:** Editable by course instructor.
2. **`IN_REVIEW`:** Content locked. Admin review queue shows changes and validation checklist.
3. **`PUBLISHED`:** Live on public catalog. Minor edits allowed, major changes require re-review.
4. **`ARCHIVED`:** Removed from discovery, preserved for enrolled learners.

## 6. Frontend Information Architecture Segregation

The frontend routing must be cleanly partitioned into three dedicated role spaces:

```text
/ (Public Marketing & Catalog)
 ├── /courses (Public Search & Filter)
 ├── /courses/[slug] (Landing Page)
 ├── /checkout/[slug] (Checkout & Gateway Initiation)
 └── /verify/[code] (Certificate Verification)

/ (Student Workspace)
 ├── /dashboard (Personalized Learning Overview, Enrolled Stats, Resume CTA)
 ├── /my-courses (Enrolled Courses, Progress Bars, Filters)
 ├── /learn/[courseSlug]/[lessonId] (Classroom Player, Video, Q&A, Notes)
 ├── /orders (Order History, Invoice Download, Refund Modal)
 └── /notifications (Student Notification Center)

/instructor (Dedicated Instructor Portal — NEW)
 ├── /instructor/overview (Teaching KPI Cards, Active Learners, Recent Questions)
 ├── /instructor/courses (My Courses, Course Status Badges, Create Course CTA)
 ├── /instructor/courses/[id]/curriculum (Course Builder, Modules, Lessons, Quizzes)
 ├── /instructor/courses/[id]/analytics (Student Progress Funnel, Video Drop-off)
 └── /instructor/discussions (Pending Student Questions, Reply Modal)

/admin (Institutional Management Portal)
 ├── /admin/overview (System KPIs, Revenue, Conversion, User Growth)
 ├── /admin/courses (All Courses, Review Queue, Publish/Unpublish Overrides)
 ├── /admin/categories (Catalog Taxonomies)
 ├── /admin/finance (Revenue KPI, Settlement, Reconciliation, CSV Export)
 ├── /admin/finance/refund-requests (Refund Adjudication Queue)
 └── /admin/users (Role Management, Instructor Approvals)
```
