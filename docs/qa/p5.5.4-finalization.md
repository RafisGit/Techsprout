## 1. Objective

Implement the administrative review queue and adjudication workflow for student refund requests:
1. Provide platform administrators with centralized visibility into student refund applications (`/admin/finance/refund-requests`).
2. Offer comprehensive search, status filtering (`PENDING`, `APPROVED`, `REJECTED`), date range filtering, and server-side pagination.
3. Deliver operational detail views highlighting historical progress snapshots vs. real-time curriculum progress, student identity, and order/invoice context.
4. Enforce strict RBAC authorization protecting administrative endpoints and UI.
5. Provide atomic, concurrency-safe adjudication actions (`reject` with mandatory explanation; `approve` review-stage transition without premature provider refund execution).
6. Record append-only audit logs for all administrative adjudication events.

## 6. RBAC & Security Verification

- **Role Guard**: Controller is decorated with `@UseGuards(RolesGuard)` and `@Roles('admin')`.
- **Authentication**: Requires authenticated session cookie or bearer token (`@ApiBearerAuth()`, `@ApiCookieAuth()`).
- **Student Shielding**: Students attempting to call admin queue endpoints receive HTTP 403 Forbidden.
- **Unauthenticated Access**: Requests without session receive HTTP 401/403.
- **Frontend Protection**: If `currentUser.role !== 'admin'`, the UI renders an "Access Denied" ShieldAlert state.
- **Sensitive Data Isolation**: Gateway credentials, payment keys, and customer passwords are never exposed in admin projections.

## 7. Concurrency & Collision Handling

1. **Simultaneous Decision Collision**:
   - If two administrators open the same pending request and attempt simultaneous decisions (e.g. approve vs. reject), both operations execute within atomic transactions with row locks (`SELECT ... FOR UPDATE`).
   - The first transaction commits its status transition.
   - The second transaction detects `status !== 'PENDING'` and throws HTTP 409 `REFUND_REQUEST_ALREADY_REVIEWED`.
2. **Direct Refund Interleaving**:
   - If an order is refunded via direct admin refund (`POST /api/v1/admin/orders/:id/refund`) while a refund request is pending, an approval attempt locks the order row, observes `order.status === 'REFUNDED'`, and rejects the approval with HTTP 400 `ORDER_NOT_REFUNDABLE`.
3. **Active Provider Refund Collision**:
   - If a provider refund operation already exists in `refunds` for the order with status `PENDING` or `PROCESSED`, approval is rejected with HTTP 409 `REFUND_ALREADY_PENDING` / `REFUND_ALREADY_PROCESSED`.

## 8. Audit Logging

Every adjudication action generates an immutable audit record:
- **`REFUND_REQUEST_APPROVED`**:
  - `actorId`: Admin User ID
  - `targetType`: `refund_request`
  - `targetId`: Request UUID
  - `metadata`: `orderId`, `requestNumber`, `adminNotes`
- **`REFUND_REQUEST_REJECTED`**:
  - `actorId`: Admin User ID
  - `targetType`: `refund_request`
  - `targetId`: Request UUID
  - `metadata`: `orderId`, `requestNumber`, `rejectionReason`, `adminNotes`
