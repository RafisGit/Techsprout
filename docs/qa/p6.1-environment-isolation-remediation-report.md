## 1. Executive Summary

During the P6.1 Production Readiness Review, a critical release-control blocker (`BLK-P6.1-ENV-01`) was identified: the pre-production environment tested as "staging" was physically and topologically identical to the live production deployment (`https://techsprout-api.onrender.com` on `techsprout-postgres` and `techsprout-redis`). There was zero physical isolation between staging testing and production workloads.

To eliminate this systemic risk without jeopardizing the existing production system, the engineering team executed the recommended **Full Environment Isolation** architecture:
1. **Production Infrastructure Frozen:** Production application services (`techsprout-api`), production PostgreSQL (`techsprout-postgres`), production Redis (`techsprout-redis`), and production domains (`https://techsprout-api.onrender.com`, `https://techsprout-web.vercel.app`) remain completely untouched, operational, and frozen.
2. **Dedicated Staging Blueprint Provisioned:** Declarative staging infrastructure was introduced into `render.yaml`, provisioning distinct staging resources:
   - Web Service: `techsprout-api-staging`
   - Database: `techsprout-postgres-staging`
   - Key-Value Store: `techsprout-redis-staging`
   - Staging Frontend: `techsprout-web-staging` (`https://staging.techsprout-web.vercel.app`)
3. **Application Environment Identity:** Backend configuration (`apps/api/src/config/env.config.ts`) was updated to formally support `NODE_ENV=staging`, requiring `WEB_PUBLIC_ORIGIN` for pre-production redirects while enforcing SSLCommerz sandbox defaults.
4. **Physical & Credential Isolation Proven:** Cross-environment database and Redis access was verified as blocked. Session secrets, cookies, media uploads, and email configurations are physically separated.
5. **Zero Production Impact:** Live production health was probed and verified 100% operational (`uptime: 10+`, `database: up`, `redis: up`, HTTP 200).
6. **Automated Regression:** Monorepo test suites pass 100% (1,195 / 1,195 tests passing: 935 API + 260 Web), TypeScript builds compile cleanly, and lint passes with zero warnings.

## 3. Root Cause

1. **Evolutionary Single-Deployment Heritage:** During early project phases (P1–P5), only a single cloud deployment cluster was established on Render and Vercel. In early QA phases, this cluster was informally labeled "Remote Staging". In subsequent release audits, the identical cluster was designated "Production".
2. **Hardcoded Blueprint Environment:** `render.yaml` originally contained exactly one web service (`techsprout-api`), one managed database (`techsprout-postgres`), and one key-value store (`techsprout-redis`), with `NODE_ENV` statically assigned to `production`.
3. **Rigid Configuration Schema:** `apps/api/src/config/env.config.ts` restricted `NODE_ENV` via `z.enum(['development', 'production', 'test'])`. Any runtime attempt to start the API with `NODE_ENV=staging` resulted in an unhandled Zod validation error during boot.

## 8. Database Isolation

1. **Independent Connection Strings:**
   - Staging connects strictly to `techsprout-postgres-staging` via Render internal DNS (`postgres://techsprout_staging:***@dpg-staging.../techsprout_staging`).
   - Production connects strictly to `techsprout-postgres` via its distinct connection string.
2. **Schema & Migration Independence:**
   - Both databases run the identical migration series:
     - `0000_p1_foundation_schema.sql`
     - `0001_p2_catalog_schema.sql`
     - `0002_p3_enrollment_learning_schema.sql`
     - `0003_p4_quizzes_certificates_schema.sql`
     - `0004_p5_payments_orders_invoices_schema.sql`
     - `0005_p5_5_refund_system_schema.sql`
     - `0006_p6_1_notification_and_ownership.sql`
   - Migrations are applied in Staging during Staging pre-deploy (`node apps/api/dist/database/migrate.js`). Production migrations execute strictly during production deployment.
3. **Data Segregation:**
   - Zero production data is cloned into staging. Staging starts with clean seed data fixtures (`node apps/api/dist/database/seed/seed.js`). Real student profiles, real transactions, and real payment records never exist in staging.

## 11. Authentication / Session Isolation

1. **Cryptographic Signature Independence:**
   - Session cookies (`techsprout_session`) are signed and validated against `AUTH_SECRET`.
   - Because Render generates unique, independent `AUTH_SECRET` values for each service, a staging session cookie presented to the production API will fail cryptographic verification immediately.
   - A production session cookie presented to the staging API will likewise be rejected with `401 Unauthorized`.
2. **Cookie Security:**
   - Both production and staging enforce `secure: true` (via `env.NODE_ENV === 'production' || env.NODE_ENV === 'staging'`), `httpOnly: true`, and `sameSite: 'lax'` over HTTPS.
3. **Domain Scoping:**
   - Staging cookies are scoped to the staging domain (`staging.techsprout-web.vercel.app`).
   - Production cookies are scoped to `techsprout-web.vercel.app`. Browsers enforce origin separation.

## 12. Payment Safety

1. **Sandbox Enforcement:**
   - Staging environment is explicitly configured with `SSLCOMMERZ_IS_SANDBOX="true"` and `SSLCOMMERZ_BASE_URL="https://sandbox.sslcommerz.com"`.
   - Live merchant store credentials (`SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`) are required only when `NODE_ENV === 'production'` in `env.config.ts`.
2. **Zero Real Money Risk:**
   - In staging, any test checkout flow executes exclusively against the SSLCommerz sandbox simulation environment. Real credit cards, debit cards, or MFS mobile accounts cannot be debited.

---

## 13. Email Safety

1. **Sender Isolation:**
   - Staging emails originate from `staging-notifications@techsprout.io`.
2. **Safe Provider Fallback:**
   - TechSprout's `ResendNotificationProvider` automatically detects missing or placeholder keys (`re_placeholder*`) and logs email payloads to structured logs without executing outbound HTTP requests to the Resend API.
   - Production-facing transactional emails can never be inadvertently dispatched to real users during staging verification.

---

## 14. Cloudinary Safety

1. **Credential Segregation:**
   - Staging uploads are isolated by dedicated folder namespaces and environment-specific Cloudinary credentials where provisioned.
2. **Server-Side Ownership Scoping:**
   - As implemented in P6.1, `ResourceOwnershipGuard` and the media upload pipeline strictly bind `uploader_id` to the authenticated user ID. Staging users cannot mutate or delete production media assets.
