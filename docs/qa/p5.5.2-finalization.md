## 1. Phase Objective

The objective of P5.5.2 is to implement the student-facing Order History capability:
1. Provide a student order history list view (`/orders`).
2. Provide a detailed student order view (`/orders/[orderId]`).
3. Integrate seamless navigation for desktop and mobile without breaking existing behavior.
4. Uphold strict authoritative data presentation (no client price/discount recalculations, standardized BDT formatting).
5. Enforce server-side IDOR security and safe unauthorized/not-found states.
6. Connect invoice viewing where supported by P5, while keeping student refund requests strictly non-functional placeholders pending P5.5.3.

## 6. Security & IDOR Verification

- **Authoritative Data**: The frontend performs zero financial math; `subtotalCents`, `discountCents`, `payableCents`, and `currency` are rendered directly from backend responses.
- **Server-Side Ownership**: Orders are scoped by the backend session; client query parameters cannot be used to escalate privilege.
- **Safe Error Presentation**: If an order belongs to another student, the backend rejects with 403 Forbidden or 404 Not Found. The UI displays a safe, generic "Unable to Load Order" message with a return-to-orders CTA. No internal IDs, database stacks, or foreign student records are leaked.

## 7. Responsive UX & Accessibility

- **Responsive Design**:
  - Desktop: Full tabular summary with hover states, direct navigation buttons, and structured summaries.
  - Mobile & Tablet: Fluid card-based layouts, wrapped tags, responsive touch targets (min 44px), and collapsible drawers.
- **Accessibility**:
  - Status indicators combine icon, color, and textual labels (`Paid`, `Pending Payment`, `Refunded`, etc.) so meaning is not conveyed by color alone.
  - Buttons and interactive elements include explicit `aria-label` or descriptive text.
  - Tab navigation and pagination buttons support full keyboard interaction and visible focus rings.
