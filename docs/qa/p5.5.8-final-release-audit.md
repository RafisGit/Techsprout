## 5. END-TO-END PAYMENT FLOW

The complete purchase and checkout lifecycle was verified against specifications:
1. **Course Discovery & Selection:** Student navigates catalog, views published paid course (`BDT 1,000.00`).
2. **Order Creation:** `POST /api/v1/orders` creates order with server-authoritative pricing (discounts applied via validated coupons). Status set to `PENDING`.
3. **Session Initiation:** `POST /api/v1/payments/initiate` interacts with SSLCommerz to create hosted session `EasyCheckOut`. Order transitions to `PAYMENT_PROCESSING`.
4. **Gateway Execution:** Student completes sandbox payment via Mobile Banking (bKash test simulator). Gateway calls IPN / callback redirect.
5. **Authoritative Validation:** Backend queries SSLCommerz validation API to confirm amount, currency (`BDT`), and status (`VALID`).
6. **Atomic Settlement:**
   - Order transitions to `PAID`.
   - Payment transitions to `VALIDATED`.
   - Student Enrollment created with status `ACTIVE`.
   - Immutable snapshot invoice generated (`TSP-INV-YYYY-XXXXXXXXX`) with status `PAID`.
7. **Scoping Guarantee:** Exactly one enrollment is created for the purchased course ID; no cross-course or duplicate enrollment is permitted.

## 6. FAILED & CANCELLED PAYMENTS

1. **User Cancellation:**
   - Gateway redirects to `/orders/:id/cancelled`.
   - Order marked `CANCELLED`.
   - Zero enrollments created; zero invoices generated.
2. **Gateway Payment Failure:**
   - Gateway redirects to `/orders/:id/failure` or IPN reports `FAILED`.
   - Order transitions to `FAILED`.
   - Zero enrollments created; zero invoices generated.
3. **Failed Initiation Recovery:**
   - If gateway session creation fails (network or provider error), order rolls back from `PAYMENT_PROCESSING` to `PENDING`.
   - Prevents orders from being permanently wedged in transient processing states.

## 8. REFUND REQUEST WORKFLOW (STUDENT SELF-SERVICE)

1. **Eligibility Enforcement:**
   - `GET /api/v1/orders/:id/refund-eligibility`: Evaluates:
     - Order status must be `PAID`.
     - Order age must be $\le 7$ calendar days.
     - Student course progress must be $< 20\%$.
     - Certificate must not have been issued.
     - No existing active (`PENDING` or `APPROVED`) refund request may exist.
2. **Student Submission:**
   - `POST /api/v1/orders/:id/refund-request`: Captures reason category and detail ($\ge 10$ characters).
   - Records frozen `course_progress_at_request`.
   - Sets status to `PENDING`.
3. **Data Sanitization:**
   - Student API returns `StudentRefundRequestDto`.
   - Admin internal fields (`adminNotes`, `reviewedBy`, reviewer names, `refundId`, gateway transaction details) are completely stripped from student view.

1. **Review Dashboard:**

## 10. REFUND EXECUTION & PROVIDER SETTLEMENT

1. **Execution Lifecycle:**
   - Approved requests enter discovery queue (`GET /api/v1/admin/refund-requests/approved-unprocessed`).
   - Admin triggers execution (`POST /api/v1/admin/refund-requests/:id/execute`).
   - Dispatches through existing authoritative `RefundsService.initiateOrRetryRefund`.
2. **Network Decoupling:**
   - Database transaction verifies prerequisites and commits before making outbound HTTP calls to SSLCommerz.
   - **Zero DB locks are held open during external gateway latency.**
3. **Atomic Finalization:**
   - Upon provider success confirmation, `RefundsService.atomicFinalizeRefund` executes atomically:
     - `refunds.status` $\to$ `PROCESSED`
     - `orders.status` $\to$ `REFUNDED`
     - `invoices.status` $\to$ `REFUNDED`
     - Exact course `enrollment.status` $\to$ `CANCELLED`
     - Course `certificate.status` $\to$ `REVOKED` (if any existed)
     - `refund_requests.refund_id` $\to$ linked to `refunds.id`.
4. **Idempotence & Duplicate Defense:**
   - If executed repeatedly, returns existing processed refund without duplicate gateway calls.
   - Database unique index `refunds_order_id_uq` makes second refund creation structurally impossible.

### Consolidated State Machine Transition Matrix

| Subsystem | State | Allowed Next Transitions | Strictly Forbidden Transitions |
|---|---|---|---|
| **Order** | `PENDING` | `PAYMENT_PROCESSING`, `CANCELLED` | `PAID`, `REFUNDED` |
| | `PAYMENT_PROCESSING` | `PAID`, `FAILED`, `PENDING` (rollback) | `REFUNDED` |
| | `PAID` | `REFUNDED` | `PENDING`, `PAYMENT_PROCESSING`, `FAILED` |
| | `REFUNDED` | *Terminal* | `PAID`, `PENDING`, `FAILED` |
| | `CANCELLED` | *Terminal* | `PAID`, `REFUNDED` |
| | `FAILED` | *Terminal* | `PAID`, `REFUNDED` |
| **Payment** | `INITIATED` | `PENDING`, `VALIDATED`, `FAILED` | `REFUNDED` directly |
| | `VALIDATED` | *Terminal (Recorded)* | `FAILED`, `PENDING` |
| **Refund** | `PENDING` | `PROCESSED`, `FAILED` | *No premature completion* |
| | `FAILED` | `PENDING` (retry) | `PROCESSED` directly |
| | `PROCESSED` | *Terminal* | `PENDING`, `FAILED` |
| **Refund Request** | `PENDING` | `APPROVED`, `REJECTED` | *No self-approval* |
| | `APPROVED` | Linked to `refunds.id` upon settlement | `PENDING`, `REJECTED` |
| | `REJECTED` | *Terminal (Resubmission creates NEW row)* | `APPROVED` directly |
| **Invoice** | `PAID` | `REFUNDED` | `PENDING`, `CANCELLED` |
| | `REFUNDED` | *Terminal* | `PAID` |
| **Enrollment** | `ACTIVE` | `CANCELLED` (upon refund) | `COMPLETED` if refunded |
| | `CANCELLED` | *Terminal* | `ACTIVE` |

## 15. CONCURRENCY & RACE CONDITION AUDIT

1. **Concurrent Refund Approval:**
   - Evaluated: Two admins clicking Approve simultaneously.
   - Defense: SQL condition `WHERE id = :id AND status = 'PENDING'`. First transaction commits; second gets zero affected rows and throws `409 Conflict`.
2. **Concurrent Refund Execution:**
   - Evaluated: Multiple workers executing the same approved request.
   - Defense: Unique index `refunds_order_id_uq`. Exactly one refund insert succeeds; the competing transaction detects the existing record and reuses it safely.
3. **Simultaneous Direct Admin Refund vs. Student Refund Request:**
   - Evaluated: Admin initiates direct refund while student request is approved.
   - Defense: Direct refund finalization automatically executes `UPDATE refund_requests SET refund_id = :refundId WHERE order_id = :orderId`, linking both cleanly.
4. **Concurrent PDF Generation & CSV Streaming:**
   - Evaluated: High-volume concurrent downloads.
   - Defense: Fully stateless, pure streaming into distinct Node.js streams without shared mutable buffers.
