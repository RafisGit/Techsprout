## 1. Objective

Deliver the highest-risk financial phase of P5.5: executing approved student refund requests through the authoritative, frozen Phase 5 refund engine:
1. Discover `APPROVED` student refund requests requiring gateway settlement without filtering out legitimate non-`PAID` or already-settled orders.
2. Integrate discovered requests into the existing `RefundsService.initiateOrRetryRefund` engine without building a synthetic second refund engine or leaking gateway HTTP logic into student modules.
3. Establish safe, deterministic handling for all order states (`PAID`, `REFUNDED`, `PENDING`, `CANCELLED`, `FAILED`).
4. Re-use existing failed refund rows in-place, reuse existing pending refund operations, and link existing processed refund operations without violating the `ONE ORDER -> AT MOST ONE REFUND ROW -> AT MOST ONE AUTHORITATIVE PROVIDER OPERATION` invariant.
5. Guarantee strict concurrency safety where parallel workers executing the same approved request converge on exactly one refund row, one gateway call, and one atomic finalization.
6. Enforce that zero database locks are held during external SSLCommerz HTTP communications.
7. Safely associate `refund_requests.refund_id = refunds.id` and ensure provider completion reaches the authoritative `RefundsService.atomicFinalizeRefund` path.

- **Bi-directional Linkage in P5 Refunds Engine**:
  - `RefundsService.initiateOrRetryRefund`: Automatically attaches `refund_requests.refund_id = refunds.id` when initiated.

## 5. Approved-Request Discovery

The discovery query strictly follows the rule established in P5.5.4 Financial Safety Reconciliation:
```sql
SELECT rr.*
FROM refund_requests rr
JOIN orders o ON rr.order_id = o.id
WHERE rr.status = 'APPROVED'
  AND rr.refund_id IS NULL
ORDER BY rr.reviewed_at ASC
LIMIT :limit;
```
- **Rationale**: Direct admin refunds can cause an order to transition to `REFUNDED` while its student refund request remains `APPROVED` and `refund_id IS NULL`. Filtering by `orders.status = PAID` would conceal such requests, leaving them orphaned forever.
- Discovery yields all approved requests requiring resolution; case dispatch then inspects the live authoritative state.

---

## 6. Direct-Refund Race Handling

When a direct admin refund races with a student-request execution or precedes it:
1. `orders.status` is already `REFUNDED`.
2. Discovery finds the approved request.
3. Case B logic executes:
   - Locates `refunds WHERE order_id = request.order_id`. Exactly one authoritative refund exists.
   - Idempotently links `refund_requests.refund_id = refunds.id`.
   - Records audit event `REFUND_REQUEST_LINKED_TO_DIRECT_REFUND`.
   - Zero gateway calls are made. Zero duplicate refund records are created.

---

## 7. FAILED / PENDING / PROCESSED Handling

- **FAILED Refund Operation**:
  - Does NOT insert a second refund row (preventing duplicate key constraint failures on `refunds_order_id_uq`).
  - Calls `RefundsService.initiateOrRetryRefund`, which reuses the existing failed refund row in place, preserves `refunds.id` and `refundNumber`, resets provider error fields, and initiates a clean gateway attempt.
  - Records audit event `REFUND_REQUEST_FAILED_OPERATION_RETRIED`.
- **PENDING Refund Operation**:
  - Does NOT initiate another gateway refund attempt.
  - Attaches `refund_requests.refund_id = refunds.id`.
  - Defers to existing P5 reconciliation / query logic (`RefundsService.queryRefundStatus`).
  - Records audit event `REFUND_REQUEST_PENDING_OPERATION_REUSED`.
- **PROCESSED Refund Operation**:
  - Does NOT call the payment gateway.
  - Attaches `refund_requests.refund_id = refunds.id`.
  - Returns the existing settled refund DTO.
  - Records audit event `REFUND_REQUEST_LINKED_TO_EXISTING_REFUND`.

## 8. Concurrency Guarantees

- **Parallel Worker Convergence**: Tested with two worker processes executing the exact same approved refund request concurrently (`Promise.all([execute(), execute()])`):
  - Exactly one refund record created in the database.
  - Exactly one provider initiation HTTP request sent to SSLCommerz.
  - The second execution catches concurrent initiation / database uniqueness constraint and attaches safely to the existing refund operation.
  - Both workers return identical refund DTOs with the same refund ID.
- **Parallel Finalization Idempotency**: Multiple concurrent calls to `RefundsService.atomicFinalizeRefund` execute safely and idempotently without duplicate record transitions or double counting.
- **Single Active Request Invariant**: Database constraint `refund_requests_active_order_uq` ensures at most one active request exists per order.

---

## 9. Transaction Boundaries

Strict adherence to the Zero-Lock Network Rule:
1. **Short Transaction 1 (Identification / Creation)**:
   - Validates order, payment, and request relationships.
   - Inserts or reuses refund record in `PENDING` state.
   - Commits transaction immediately.
2. **External Gateway Call (Zero Locks)**:
   - Makes outbound HTTPS call to `SSLCommerzClient.initiateRefund`.
   - No database connections, row locks, or transactions held.
3. **Short Transaction 2 (State Persistence)**:
   - Persists provider refund reference or error details.
   - Commits transaction immediately.
4. **Finalization Transaction (Authoritative Atomic Finalization)**:
   - Executes inside `RefundsService.atomicFinalizeRefund` when settlement confirmed.
   - Mutates `refunds.status -> PROCESSED`, `orders.status -> REFUNDED`, `invoices.status -> REFUNDED`, `enrollments.status -> CANCELLED`, `certificates.status -> REVOKED`.
   - Commits atomically.

## 10. Provider Interaction

- **Gateway URL**: Configured SSLCommerz Sandbox endpoint (`https://sandbox.sslcommerz.com`).
- **Initiation Payload**: Sent via `ISSLCommerzClient.initiateRefund` containing `bank_tran_id`, `refund_amount`, `refund_remarks`, `refe_id`.
- **Ambiguity & Timeout Handling**: Network timeouts or transient connection drops leave `refunds.status = PENDING`. The system does NOT automatically retry or spawn a second refund operation.
- **Status Query**: Resolves pending operations via `ISSLCommerzClient.queryRefund` checking settlement status.

## 11. Reconciliation Behavior

- Fully integrated with existing P5 reconciliation engine.
- Reconciling a pending refund via `RefundsService.queryRefundStatus` transitions the refund to `PROCESSED` upon gateway settlement and triggers `atomicFinalizeRefund`.
- Automatically links any unlinked approved student refund requests associated with that order.

---

## 12. Finalization Behavior

Authoritative finalization occurs exclusively through `RefundsService.atomicFinalizeRefund`:
- `refunds.status`: `PENDING -> PROCESSED`
- `orders.status`: `PAID -> REFUNDED`
- `invoices.status`: `PAID -> REFUNDED`
- `enrollments.status`: `ACTIVE -> CANCELLED`
- `certificates.status`: `ACTIVE -> REVOKED` (with revocation reason)
- Exact scoping: Only the enrollment and certificate belonging to the refunded order's student and course are cancelled/revoked. Other enrollments remain completely unaffected.

## 13. Audit Logging

All administrative executions and links are recorded via `AuditService.record()`:
- `REFUND_REQUEST_REFUND_INITIATED`: New provider refund initiated from student request.
- `REFUND_REQUEST_FAILED_OPERATION_RETRIED`: Existing failed operation retried in place.
- `REFUND_REQUEST_PENDING_OPERATION_REUSED`: Existing pending operation attached.
- `REFUND_REQUEST_LINKED_TO_DIRECT_REFUND`: Attached to already-completed direct admin refund.
- `REFUND_REQUEST_LINKED_TO_EXISTING_REFUND`: Attached to already-processed refund.
- `REFUND_REQUEST_ORDER_STATE_INVALID`: Recorded when execution attempted on non-refundable order.
- `REFUND_REQUEST_RELATIONSHIP_MISMATCH`: Recorded when student/order/course relationship fails validation.
- **Zero Secrets Rule**: Store passwords, secret keys, and credentials are strictly excluded from audit payloads.
