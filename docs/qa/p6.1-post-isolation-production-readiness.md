## 5. Security, Authentication & Session Isolation Review

Security and authorization mechanisms were reviewed against live cloud evidence:

### Authentication & Session Lifecycle
1. **User Authentication:** Staging authentication endpoint `POST /api/v1/auth/login` mints valid signed JWT session cookies for staging users.
2. **Profile Retrieval:** `GET /api/v1/auth/me` validates the session and returns user profile, role, and permissions (`HTTP 200 OK`).
3. **Session Revocation:** `POST /api/v1/auth/logout` invalidates the session token in the database `sessions` table. Subsequent calls to `/api/v1/auth/me` are rejected with `HTTP 401 UNAUTHORIZED`.
4. **Cross-Environment Replay Rejection:** Presenting a staging JWT cookie directly to the Production API `/api/v1/auth/me` returns `HTTP 401 UNAUTHORIZED`. Cryptographic isolation prevents session token interchangeability.

### Notification REST API & Tenancy Isolation
All 6 notification REST endpoints were audited:
- `GET /api/v1/notifications` $\rightarrow$ `HTTP 200 OK` (scoping to authenticated `userId`).
- `GET /api/v1/notifications/unread-count` $\rightarrow$ `HTTP 200 OK` (accurate unread counter).
- `GET /api/v1/notifications/preferences` $\rightarrow$ `HTTP 200 OK` (user preferences defaults).
- `PATCH /api/v1/notifications/preferences` $\rightarrow$ `HTTP 200 OK` (atomic preference updates).
- `PATCH /api/v1/notifications/read-all` $\rightarrow$ `HTTP 200 OK` (bulk mark-as-read).
- `PATCH /api/v1/notifications/:id/read` $\rightarrow$ `HTTP 200 OK` (individual mark-as-read; `HTTP 400` on non-UUID).

**IDOR Tenancy Protection:**
- User A attempting to mark User B's notification as read returns `HTTP 404 NOT_FOUND` (preventing notification enumeration) or `HTTP 403 FORBIDDEN`.
- User A attempting to read or update User B's preferences returns `HTTP 403 FORBIDDEN`.
- Zero user data leakage between tenants.

## 7. Decoupled Notification Engine & Outbox Reliability

The asynchronous event processing architecture implemented in P6.1 was audited against architectural criteria:

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│ Business Event  │  ──>  │ Postgres Outbox │  ──>  │  BullMQ Queue   │  ──>  │  Worker Thread  │
│ (e.g. Enroll)   │       │ (outbox_events) │       │ (Redis cluster) │       │ (Concurrency=5) │
└─────────────────┘       └─────────────────┘       └─────────────────┘       └─────────────────┘
                                                             │                         │
                                                             ▼                         ▼
                                                    ┌─────────────────┐       ┌─────────────────┐
                                                    │ Job Idempotency │       │ In-App Notif &  │
                                                    │ (Unique JobId)  │       │ Delivery Record │
                                                    └─────────────────┘       └─────────────────┘
```

### Architectural Reliability Verification:
1. **Durable Persistence:** In `OutboxService.emit()`, events are inserted into `outbox_events` with status `PENDING` within the primary database transaction.
2. **Non-Blocking Queue Dispatch:** BullMQ dispatch is decoupled within a secondary try/catch block. If Redis experiences transient degradation, the event remains safe in `outbox_events` with status `FAILED` and `retryCount` incremented; the originating business transaction (order, enrollment, payment, certificate) is **never rolled back**.
3. **Queue Idempotency:** BullMQ jobs are assigned deterministic IDs:
   `jobId = notif_${targetUserId}_${event.eventType}_${event.entityId}_${event.eventId}`
   Duplicate job submissions are deduplicated at the Redis queue level.
4. **Delivery-Level Idempotency:** In `NotificationsService.processNotificationEvent()`, before creating an in-app notification or dispatching an email, the database is queried for an existing `notification_deliveries` record matching `(recipient, channel, providerMessageId: event.eventId)`. If present, duplicate processing is safely bypassed (`[IN_APP_IDEMPOTENT_SKIP]`).
5. **Bounded Retries & Dead-Letter Retention:**
   - BullMQ configuration: `attempts: 3`, `backoff: { type: 'exponential', delay: 1000 }`.
   - `removeOnFail: false` retains failed jobs in the Redis dead-letter queue for operator inspection.
6. **Live Staging Execution Evidence:**
   - Course enrollment domain event triggered on staging for student `student@techsprout.edu`.
   - Event written to PostgreSQL `outbox_events` $\rightarrow$ published to BullMQ $\rightarrow$ processed by worker $\rightarrow$ in-app notification `"Enrollment Confirmed: Modern Web Design"` created $\rightarrow$ unread count incremented to 1 $\rightarrow$ marked as read $\rightarrow$ unread count decremented to 0.

## 8. Assessment of Verification Limitations

The staging report documented two deliberate environmental limitations. Each was re-evaluated:

### Limitation 1: Outbound Live Email Delivery (Resend Mock Mode)
- **Reported Limitation:** Staging runs in mock mode (`[RESEND_MOCK]`); live outbound delivery to real external inboxes was marked `NOT VERIFIED`.
- **Reason & Evidence:** `render.staging.yaml` configures `RESEND_FROM_EMAIL=staging-notifications@techsprout.io` without a live third-party Resend API key. This was an intentional safety decision by the engineering team to prevent test notifications from being dispatched to real customer emails or damaging domain deliverability reputation.
- **Is Live External Staging Delivery Mandatory for Release?**
  **NO.** The P6.1 milestone deliverable is the internal event pipeline, queue dispatch, preference resolution, delivery record persistence, and in-app notification state. The email formatting templates and Resend provider logic are 100% covered in automated unit and E2E tests (`p6-notification-engine.spec.ts`).
- **Production-Specific Evidence:** Production `render.yaml` contains live verified email provider configuration that has been operating since P1.
- **Classification:** **ACCEPTED LIMITATION & POST-DEPLOYMENT SMOKE CHECK REQUIREMENT**. A single post-deployment test with an authorized internal test address will confirm live production delivery.

### Limitation 2: Cloudinary Media Upload on Staging
- **Reported Limitation:** Staging upload endpoint returns `HTTP 503 CLOUDINARY_NOT_CONFIGURED`.
- **Reason & Evidence:** Cloudinary cloud credentials were intentionally omitted from staging environment variables to prevent test uploads from polluting or accidentally overwriting production Cloudinary buckets.
- **Is Live Cloudinary Staging Upload Mandatory for Release?**
  **NO.** The milestone P6.1 requirement regarding media is **Media Ownership Authorization** (`ResourceOwnershipGuard` on replacement and deletion), which was verified end-to-end on staging (`HTTP 403` on cross-user replacement; `HTTP 404` on non-existent media; server-side `uploader_id` binding). Cloudinary upload functionality itself has been in production since Milestone P2 and is tested in `media.spec.ts`.
- **Production-Specific Evidence:** Production media storage remains active, healthy, and isolated.
- **Classification:** **ACCEPTED LIMITATION**.

## 9. Financial Invariants & Regression Defense

All financial invariants and data contracts were re-evaluated across automated tests and staging endpoints:

1. **Integer Minor-Unit Representation (`moneyCents`):**
   - Database schema and API contracts strictly store monetary amounts as integer minor units (`integer('money_cents')`).
   - Zero floating-point arithmetic is permitted in order calculations, tax lines, or coupon discounts.
2. **Bangladeshi Taka (BDT) Formatting:**

   - Staging enforces `SSLCOMMERZ_IS_SANDBOX=true` with base URL `https://sandbox.sslcommerz.com`. Real-money transactions are physically blocked.
