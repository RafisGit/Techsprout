## 2. Refund State Machine

The database enum `refund_status` (`PENDING`, `PROCESSED`, `FAILED`) is preserved and strictly governed:

```
[ PAID Order ]
      │
      ▼
Initiate Refund
      │
      ├──> Provider returns "success" / "processing" ──> Status: PENDING (persists provider_refund_ref)
      │                                                        │
      ├──> Provider returns "failed" ───────────────────> Status: FAILED (order remains PAID)
      │                                                        ▲
      └──> Network Timeout / 5xx ───────────────────────> Status: PENDING (provider_refund_ref = null, MANUAL_REVIEW_REQUIRED)
                                                               │
                                       ┌───────────────────────┴───────────────────────┐
                                       │                                               │
                           Admin Reconciles: MARK_FAILED              Admin Reconciles: LINK_PROVIDER_REFERENCE
                                       │                                               │
                                       ▼                                               ▼
                                Status: FAILED                             Status: PENDING (with ref)
                               (order remains PAID)                                    │
                                                                                       ▼
                                                                           Query Provider Status
                                                                                       │
                                                       ├──> Query returns "processing" ──> Status: PENDING
                                                       │
                                                       ├──> Query returns "failed" ──────> Status: FAILED (order remains PAID)
                                                       │
                                                       ├──> Query returns "cancelled" ───> Status: FAILED (order remains PAID)
                                                       │
                                                       └──> Query returns "refunded" ────> Status: PROCESSED (Atomic Finalization)
```

- **PENDING**: Refund operation initiated or awaiting settlement. Order remains `PAID`, enrollment remains `ACTIVE`, certificate remains `ACTIVE`.
- **FAILED**: Authoritatively rejected by provider during initiation or query, or administratively marked failed during reconciliation. Order remains `PAID`, enrollment remains `ACTIVE`, certificate remains `ACTIVE`. Can be retried by admin.
- **PROCESSED**: Terminal state entered **only** when SSLCommerz status query returns `status === 'refunded'`. Triggers atomic local finalization.

## 3. SSLCommerz Initiation / Query Integration

### Initiation Protocol (HTTP GET)
- **Endpoint:** `/validator/api/merchantTransIDvalidationAPI.php`
- **Method:** `GET`
- **Parameters:**
  - `bank_tran_id`: Derived from validated payment row.
  - `refund_trans_id`: Stable correlation ID (`TSP-REF-` + 22 chars uppercase, exactly 30 characters).
  - `refund_amount`: Formatted string decimal (e.g., `'2500.00'`), derived from `order.payableCents`.
  - `refund_remarks`: Admin-provided reason string.
  - `refe_id`: Internal order identifier.
  - `store_id` & `store_passwd`: Injected server-side from environment configuration; never exposed in DTOs or logs.
  - `format`: `'json'`.

### Query Protocol (HTTP GET)
- **Endpoint:** `/validator/api/merchantTransIDvalidationAPI.php`
- **Method:** `GET`
- **Parameters:**
  - `refund_ref_id`: Gateway refund reference identifier (`providerRefundRef`).
  - `store_id` & `store_passwd`: Server-side credentials.
  - `format`: `'json'`.

## 4. Retry and Idempotency Model

- **Full-Refund-Only Invariant:** Refund amount is strictly `order.payableCents`. No client-supplied amounts are accepted.
- **Single Refund Row Per Order:** Enforced by PostgreSQL schema constraint `UNIQUE(refunds.order_id)`.
- **Row Identity Survival:**
  - When retrying a `FAILED` refund, the existing refund row is updated from `FAILED` $\rightarrow$ `PENDING`.
  - The primary key `id` and unique `refund_number` are preserved identically.
  - Never creates a second refund row.
- **Stable Correlation Identifier:**
  `refund_trans_id = "TSP-REF-" + order.id.replace(/-/g, '').slice(0, 22).toUpperCase()` (exactly 30 characters).
  This ID is treated as an audit correlation identifier, **not** as a provider-side idempotency guarantee.

## 5. Timeout / Reconciliation Behavior

- When gateway initiation experiences a network timeout, socket hangup, or 5xx response:
  - The refund row remains `PENDING`.
  - `provider_refund_ref` remains `null`.
  - Order remains `PAID`, enrollment remains `ACTIVE`, certificate remains `ACTIVE`.
  - The operation is classified as `REFUND_MANUAL_REVIEW_REQUIRED`.
  - Subsequent automated retry attempts are rejected with `409 Conflict (REFUND_MANUAL_REVIEW_REQUIRED)`.
  - **Zero automated duplicate requests are sent to the gateway.**

## 6. Manual Reconciliation Endpoint

- **Endpoint:** `POST /api/v1/admin/refunds/:id/reconcile`
- **Access:** Admin-only (`Roles('admin')`, server-side RBAC, cookie/bearer session).
- **Supported Actions:**
  1. `LINK_PROVIDER_REFERENCE`:
     - Allowed only when `refund.status === 'PENDING'` and `refund.provider_refund_ref === null`.
     - Persists verified `providerRefundRef`.
     - Does **not** change order state or finalize refund.
     - Enables subsequent status query endpoint to query provider for settlement.
  2. `MARK_FAILED`:
     - Allowed when refund is in ambiguous `PENDING` state with `provider_refund_ref === null`.
     - Transitions refund to `FAILED`, recording admin reasoning in audit logs.
     - Preserves order as `PAID`, enrollment as `ACTIVE`, certificate as `ACTIVE`.
     - Allows subsequent clean retry if desired.

## 7. Atomic Finalization

Finalization occurs **only** when SSLCommerz status query returns `status === 'refunded'`.

Executed within a short PostgreSQL transaction:
1. `SELECT ... FROM orders WHERE id = :orderId FOR UPDATE`
2. Validate order status is still non-terminal (`PAID`).
3. `SELECT ... FROM refunds WHERE id = :refundId FOR UPDATE`
4. Validate refund is still `PENDING` and belongs to this order.
5. Identify exact payment, enrollment, and certificate records.
6. Mutate records atomically:
   - `refunds`: `status = 'PROCESSED'`, `processed_at = NOW()`
   - `orders`: `status = 'REFUNDED'`, `updated_at = NOW()`
   - `invoices`: `status = 'REFUNDED'`, `updated_at = NOW()`
   - `enrollments`: `status = 'CANCELLED'`, `updated_at = NOW()`
   - `certificates`: `status = 'REVOKED'`, `revoked_at = NOW()`, `revocation_reason = 'Order refunded'`, `updated_at = NOW()`
7. Commit transaction and log audit events.

## 8. Enrollment & Certificate Targeting Safety

- **No Broad Queries:** The codebase strictly prohibits un-scoped updates (e.g. `UPDATE certificates SET status = 'REVOKED' WHERE status = 'ACTIVE'`).
- **Exact Certificate Targeting:**
  The certificate revocation query scopes directly by `certificates.id = :exactCertId` (and verifies `certificates.enrollmentId = :exactEnrollmentId`).
- **Exact Enrollment Targeting:**
  Only the specific enrollment corresponding to `(studentId, courseId)` from the refunded order is cancelled.
- **Unrelated Records Preserved:**
  Active certificates and enrollments belonging to the same student for different courses (e.g., Course B) remain strictly `ACTIVE`.
- **Permanent Terminal Revocation:**
  Revoked historical certificate snapshots (`studentName`, `courseTitle`, `certificateNumber`, `issuedAt`) are never modified or reactivated.
