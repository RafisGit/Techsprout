## 1. Executive Summary

TechSprout LMS Phase 6.1 establishes the foundational security and event-driven communication infrastructure required by all Phase 6 capabilities while strictly preserving the integrity and stability of P1–P5.5 systems.

Specifically, P6.1 successfully delivers:
1. **Pillar A — Decoupled Event & Notification Infrastructure:** A durable domain event model, transactional outbox persistence pattern, BullMQ asynchronous notification queue (`techsprout-notifications`, concurrency 5, exponential backoff, dead-letter retention, offline standby), Resend transactional email provider abstraction, transactional email templates, in-app notification center REST APIs (`/api/v1/notifications`, `/preferences`), multi-channel delivery tracking (`notification_deliveries`), and a responsive frontend notification center.
2. **Pillar B — Contextual Resource Authorization (ADR-P6-001):** A zero-trust `ResourceOwnershipGuard` enforcing multi-hop ownership chains across Courses, Modules, Lessons, Quizzes, Questions, Options, and Media. Media ownership scoping was established via schema migration (`uploader_id` on `media`). Administrative superusers can bypass ownership checks, unauthorized instructor mutation attempts are rejected with HTTP 403 Forbidden, and all violation attempts are recorded in `audit_logs`.

All critical financial invariants (BDT integer `moneyCents`, SSLCommerz idempotency, post-commit transaction guarantees) remain untouched. External network I/O is strictly isolated outside database transactions.

## 2. Implementation Scope

P6.1 implementation strictly adheres to the scope boundary defined in P6.0:
- **Domain Event Vocabulary & Contracts:** Strongly typed events (`OrderPlaced`, `OrderPaid`, `RefundRequested`, `RefundApproved`, `RefundRejected`, `RefundSettled`, `EnrollmentCreated`, `CourseSubmittedForReview`, `CourseApproved`, `CourseRejected`, `LessonCompleted`, `QuizPassed`, `CertificateIssued`).
- **Transactional Outbox Engine:** `outbox_events` table persisting domain events durably within business units of work, dispatched downstream asynchronously.
- **Asynchronous Notification Worker:** BullMQ queue `techsprout-notifications` with worker concurrency 5, retry backoff (3 attempts with exponential delay), dead-letter preservation (`removeOnFail: false`), and transparent synchronous fallback in offline environments.
- **Transactional Email Dispatch:** Pluggable `EmailProvider` interface, production-ready `ResendEmailProvider`, and responsive transactional HTML/plaintext templates.
- **In-App Notification Engine:** Notifications schema (`notifications`), preferences schema (`notification_preferences`), multi-channel deliveries schema (`notification_deliveries`), and authenticated REST endpoints (`GET /notifications`, `GET /notifications/unread-count`, `PATCH /notifications/:id/read`, `PATCH /notifications/read-all`, `GET/PATCH /notifications/preferences`).
- **Contextual Resource Ownership Guard:** `@RequireOwnership(resourceType, idParamKey)` and `ResourceOwnershipGuard` with parent-chain resolution:
  - Course: `course.instructorId === req.user.id`
  - Module: `module -> course.instructorId === req.user.id`
  - Lesson: `lesson -> module -> course.instructorId === req.user.id`
  - Quiz: `quiz -> module -> course.instructorId === req.user.id`
  - Quiz Question: `question -> quiz -> module -> course.instructorId === req.user.id`
  - Quiz Option: `option -> question -> quiz -> module -> course.instructorId === req.user.id`
  - Media: `media.uploaderId === req.user.id` (legacy null uploaders permitted)
- **Frontend Notification Center:** Accessible `NotificationBell` header component with unread badges, popover dropdown list, mark-as-read, mark-all-as-read, empty/loading/error states, and deep linking.

## 6. Notification Architecture

```text
BUSINESS ACTION (e.g. Order / Payment / Refund)
      │
      ▼
DATABASE TRANSACTION (PostgreSQL)
      │
      ├─ Commit Business State
      └─ Write Event to outbox_events (Durable)
      │
      ▼ (Post-Commit)
OutboxService.dispatchDomainEvent()
      │
      ▼
BullMQ Queue: techsprout-notifications
      │
      ▼ (Concurrency = 5, Exponential Backoff)
NotificationQueueService Worker
      │
      ▼
NotificationsService.processNotificationEvent()
      │
      ├─ Check Idempotency (providerMessageId = eventId)
      ├─ Evaluate User Preferences (notification_preferences)
      │
      ├─ Channel: IN_APP
      │    ├─ Check user.inAppAll
      │    ├─ Insert into notifications
      │    └─ Insert into notification_deliveries (channel='IN_APP', status='DELIVERED')
      │
      └─ Channel: EMAIL
           ├─ Check category preference (emailOrderUpdates / emailCourseUpdates)
           ├─ Dispatch via ResendEmailProvider
           └─ Record in notification_deliveries (channel='EMAIL', status='DELIVERED' | 'FAILED')
```

## 7. Idempotency

Idempotency is enforced at multiple layers:
1. **BullMQ Job Deduplication:** Job ID format is deterministic:  
   `notif_${targetUserId}_${eventType}_${entityId}_${eventId}`. BullMQ deduplicates simultaneous identical job dispatches.
2. **Delivery Deduplication:** Prior to creating an in-app notification or dispatching an email, `NotificationsService` queries `notification_deliveries` by `(recipient, channel, provider_message_id)`. If a delivery record already exists for the event, processing is safely skipped and logged as `[IN_APP_IDEMPOTENT_SKIP]` / `[EMAIL_IDEMPOTENT_SKIP]`.
3. **Outbox Deduplication:** `outbox_events` uses unique constraints on `event_id` to prevent duplicate persistence of the same event.

---

## 8. Retry Behavior

- **Retryable Errors:** Network timeouts, transient Resend 5xx errors, transient Redis disconnects. BullMQ retries the job up to 3 times with exponential backoff (`delay: 1000ms`, exponential factor).
- **Non-Retryable Errors:** Malformed payloads, invalid recipients, unmapped events, permanent provider rejections (e.g. 4xx). These fail immediately without exhausting queue resources and are logged as non-retryable.
- **Dead-Letter Retention:** Failed jobs are retained with `removeOnFail: false` to allow operational inspection and manual replay.

---

## 9. Security Verification

- **Cross-User Notification Scoping:** Users can only query and mutate their own notifications. Requests targeting another user's notification ID return HTTP 403 Forbidden with audit logging.
- **Mass Assignment Protection:** DTOs strictly control client-submitted fields. `updateNotificationPreferencesSchema` enforces `.strict()`, rejecting requests containing `userId`, `role`, or system status.
- **Uploader Scoping:** `media.uploader_id` is assigned strictly server-side from `req.user.id`. Clients cannot pass or alter `uploaderId`.
- **Audit Trails:** All unauthorized resource access attempts and cross-user notification access attempts generate entries in `audit_logs` with `actorId`, `action: 'UNAUTHORIZED_RESOURCE_ACCESS_ATTEMPT'`, `targetType`, `targetId`, and request metadata.
