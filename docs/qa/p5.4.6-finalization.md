## 2. End-to-End Checkout Verification

The complete checkout lifecycle was verified across all core user journeys:
`Course → Coupon → Order → Payment → SSLCommerz → Invoice → Enrollment → Certificate → Refund → Reconciliation → Admin Finance`

- **Scenario A — Free Course Checkout:**
  - Directly fulfills via `POST /api/v1/enrollments` with course price = 0.
  - Generates immediate active enrollment without invoking the payment gateway or creating empty payment transactions.
- **Scenario B — Paid Course without Coupon:**
  - Evaluates authoritative course price (`courses.price`).
  - Creates order in `PENDING` status.
  - Initiates SSLCommerz payment session returning signed gateway redirect URL.
  - Rejects browser return query parameters as untrusted.
  - Confirms order becomes `PAID` exclusively through authoritative server-side callback verification (`POST /api/v1/payments/sslcommerz/success`).
  - Concurrently creates immutable invoice snapshot and activates student enrollment.
- **Scenario C — Partial Discount Coupon:**
  - `POST /api/v1/coupons/validate` validates eligibility without mutating coupon counters.
  - Order creation atomically reserves coupon usage and locks discounted payable amount (`order.payableCents`).
  - Gateway session initiation uses strictly persisted `payableCents` (never client-supplied amounts).
  - Post-payment fulfillment consumes coupon reservation and records discount snapshot in invoice.
- **Scenario D — 100% Discount Coupon (Zero-Payable Order):**
  - Order creation with a 100% coupon results in `payableCents = 0`.
  - Gateway initiation bypassed entirely (no SSLCommerz session created).
  - Order transitions directly to `PAID`, coupon status marked `CONSUMED`, invoice generated with `payableCents: 0`, and student enrollment immediately activated.
- **Scenario E — Invalid / Inapplicable Coupon:**
  - Submitting an expired, inactive, usage-exhausted, or course-restricted coupon is rejected with HTTP 400 (`INVALID_COUPON` / `COUPON_USAGE_LIMIT_REACHED`).
  - Order creation aborts cleanly; no unauthorized discount or order row is committed.

## 3. Payment Gateway Boundary Verification

Strict validation boundaries were verified for payment initiation (`POST /api/v1/payments/initiate`):
- **0 Cents:** Allowed via internal zero-payable fulfillment; gateway initiation bypassed.
- **1 – 999 Cents (BDT 0.01 – 9.99):** Immediately rejected with HTTP 400 (`AMOUNT_BELOW_MINIMUM`). Zero outbound HTTP requests dispatched to SSLCommerz.
- **1,000 Cents (BDT 10.00 — Minimum Boundary):** Permitted; successfully initiates gateway session.
- **50,000,000 Cents (BDT 500,000.00 — Maximum Boundary):** Permitted; successfully initiates gateway session.
- **50,000,001 Cents (BDT 500,000.01+):** Rejected pre-gateway with HTTP 400 (`AMOUNT_EXCEEDS_MAXIMUM`). Zero outbound HTTP requests dispatched.

## 4. Payment Return Security Audit

- **Browser Untrusted Return:**
  - Browser query params (`/orders/:id/success?tran_id=...&val_id=...&status=VALID`) are strictly treated as client navigation signals.
  - Client navigation cannot transition orders to `PAID`, create enrollments, or generate invoices.
- **Server Authoritative Callback:**
  - `POST /api/v1/payments/sslcommerz/success` queries SSLCommerz validation API using server credentials.
  - Forged `val_id` or `tran_id` values submitted by clients are rejected with HTTP 400 (`PAYMENT_VALIDATION_FAILED`) when the gateway fails authoritative verification.
- **Amount & Currency Tamper Resistance:**
  - Gateway callback validates that the provider-reported currency (`BDT`) and amount exactly match the persisted `order.payableCents`.
  - Mismatched amounts or currencies abort fulfillment immediately.

## 5. Payment Idempotency & Replay Protection

- **Duplicate Callbacks & Webhooks:**
  - Replaying identical IPN or callback payloads (`val_id`, `tran_id`) returns HTTP 200 with idempotent acknowledgment.
  - Zero duplicate payments, invoices, or enrollments are generated.
- **Concurrent Success Invocations:**
  - Multiple concurrent requests attempting to fulfill the same transaction execute safely under transactional row-level locks (`SELECT ... FOR UPDATE`).
  - Only one execution mutates order state to `PAID`; subsequent threads detect the finalized state and return existing records idempotently.
- **Order Refresh Safety:**
  - Repeatedly loading `/orders/:id/success` triggers idempotent polling against authoritative server state.

## 6. Coupon Concurrency & Consistency

- **Usage Limit Protection:**
  - Tested with `usageLimit: 1` under concurrent order creation requests.
  - PostgreSQL row-level locking on coupon reservation ensures exactly one order succeeds in reserving the coupon.
  - The second concurrent request is rejected with `COUPON_USAGE_LIMIT_REACHED`.
- **Reservation Lifecycle Consistency:**
  - `RESERVED`: Increments reservation counter while decrementing remaining quota.
  - `CONSUMED`: Finalized upon successful payment verification.
  - `RELEASED`: If an order expires or payment is cancelled, the reservation is released back to available inventory.
  - Validation endpoint (`POST /api/v1/coupons/validate`) verified to be 100% read-only with no side effects.

## 7. Refund End-to-End Operation

- **Two-Phase Refund Lifecycle:**
  1. **Initiation (`POST /api/v1/admin/orders/:id/refund`):**
     - Verifies order is `PAID` with non-zero payable cents and valid bank transaction reference.
     - Outbound call to SSLCommerz Refund Initiation API.
     - Upon gateway acceptance, refund status is set to `PENDING` with `providerRefundRef`.
     - Order remains `PAID`, enrollment remains `ACTIVE`, and certificate remains `ACTIVE`.
  2. **Settlement Query (`POST /api/v1/admin/refunds/:id/query`):**
     - Outbound query to SSLCommerz Refund Status API.
     - While status is `processing`, refund remains `PENDING` with zero domain mutation.
     - When status is confirmed `refunded`, atomic finalization executes:
       - `refunds.status` → `PROCESSED`
       - `orders.status` → `REFUNDED`
       - `invoices.status` → `REFUNDED`
       - Associated `enrollment.status` → `CANCELLED`
       - Associated `certificate.status` → `REVOKED` (with revocation reason recorded)

## 8. Refund Failure Handling

- Provider rejection (e.g. card issuer failure, invalid account) transitions refund record to `FAILED`.
- Order status remains `PAID`.
- No premature cancellation of enrollment or revocation of certificates occurs.
- Admin retry reuses the existing singleton refund record and maintains stable `refundNumber`.

---

## 9. Refund Retry Safety & Invariants

- **Singleton Constraint:** Strictly one `refunds` row per order (`UNIQUE(order_id)`).
- **Processed Refunds:** Cannot be retried (`REFUND_ALREADY_PROCESSED`).
- **Pending with Gateway Ref:** Blocks duplicate initiation and directs operator to status query (`REFUND_ALREADY_PENDING`).
- **Pending without Gateway Ref:** Flags operation for manual investigation (`REFUND_MANUAL_REVIEW_REQUIRED`) to prevent automated duplicate disbursement.

## 10. Scoped Finalization Security

- **Strict Relationship Scoping:**
  - Finalization mutates exclusively the specific target order, its single invoice, its enrolled course, and certificates issued under that specific enrollment.
- **Cross-Enrollment Isolation Test:**

  - Refunding Course A cancels Enrollment A and revokes Certificate A.

## 12. Finance Aggregation Correctness

Tested with a mixed dataset of paid, refunded, pending, failed, cancelled, discounted, and zero-payable orders:
- **Gross Volume:** Sum of persisted `payableCents` for finalized paid and refunded orders. Unpaid/failed/pending orders are excluded.
- **Total Discounts:** Sum of persisted `discountCents` from finalized orders.
- **Confirmed Refunds:** Sum of `amountCents` for `PROCESSED` refunds only. Pending or failed refunds are excluded.
- **Net Revenue:** Mathematically verified as `Gross Volume - Confirmed Refunds`.
- **SQL-Side Aggregation:** Computations execute entirely within PostgreSQL aggregate queries (`SUM`, `COUNT`), eliminating in-memory data processing.

---

## 13. Reconciliation Safety — Provider Evidence

Hardened reconciliation scanning logic (`FinanceService.scanReconciliation`):
- `GATEWAY_VALIDATED_INTERNAL_PENDING` is marked `autoResolvable: true` **ONLY** when:
  1. Authoritative gateway status is `VALID`.
  2. Transaction identity (`bank_tran_id` and `val_id`) matches provider record.
  3. Currency matches (`BDT`).
  4. Amount matches persisted `order.payableCents`.
  5. Target order is in `PENDING` status (not `CANCELLED` or `REFUNDED`).
- Any ambiguous condition (missing bank transaction identity, currency mismatch, cancelled order) flags the discrepancy as `autoResolvable: false` (`MANUAL_REVIEW_REQUIRED`).
- Amount match alone is never sufficient for automated resolution.

---

## 14. PAID_WITHOUT_ENROLLMENT Auto-Repair

- Auto-repair executes strictly when:
  - Order status is `PAID`.
  - Positive payment validation evidence exists (or order is legitimate zero-payable).
  - Target course exists in catalog.
  - Target enrollment is verifiably absent.
  - Order is not refunded or cancelled.
- Auto-repair is rejected if order status is `REFUNDED` or `CANCELLED`.

## 27. Defects Discovered & Fixed During Hardening

1. **Defect:** `GATEWAY_VALIDATED_INTERNAL_PENDING` discrepancy scanner flagged orders as auto-resolvable even if provider bank transaction identifiers were missing or target order had been cancelled.  
   **Fix:** Updated `FinanceService.scanReconciliation` to verify matching `bankTranId` and `valId` identity, and explicitly prohibit auto-resolution of `CANCELLED` orders. Regression test added in `p5-hardening.spec.ts`.
2. **Defect:** Missing `bankTranId` or `paymentMethod` assignment during automated reconciliation repair.  
   **Fix:** Updated `executeSafeAutoResolve` to persist `bankTranId` and `paymentMethod` from the validated gateway payment record.
