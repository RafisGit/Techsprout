## 3. Distinction: Source-Code Configuration vs. Directly Observed Runtime Behavior

To preserve absolute engineering rigor, documentation explicitly distinguishes what was verified via static source-code audit from what was observed in the live runtime:

### A. Source-Code Configuration (Audited & Confirmed in Candidate SHA `491b0d0`)
1. **Redis Client:** `apps/api/src/modules/analytics/analytics.cache.service.ts` instantiates `ioredis` with lazy connection and automatic error interception.
2. **Configured TTL:** `apps/api/src/modules/analytics/analytics.service.ts` explicitly sets a **600-second TTL** across all cached endpoints:
   - `getInstructorOverview`: `await this.cacheService.set(cacheKey, result, 600);` (line 207)
   - `getCourseAnalyticsDetail`: `await this.cacheService.set(cacheKey, response, 600);` (line 363)
   - `getAdminOverview`: `await this.cacheService.set(cacheKey, result, 600);` (line 486)
3. **Cache Key Formatting & Scoping:**
   - Instructor Overview: `instructor:analytics:overview:${instructorId}`
   - Course Analytics: `course:analytics:${courseId}:${rangeHash}`
   - Admin Overview: `admin:analytics:overview`
   - Uncached by design: Student personal engagement (live real-time query) and Admin course search (dynamic paginated query).
4. **Resilience / Fail-Open:** Catch blocks in `AnalyticsCacheService` ensure that if Redis throws or disconnects, queries fall back seamlessly to PostgreSQL without crashing user requests.

### B. Directly Observed Runtime Behavior (Staging Limits)
1. **Response Timing is Not Proof:** An initial request measured 485ms and a subsequent request measured 516ms over edge CDN / internet hops. Latency variations over public networks cannot prove a Redis cache hit.
2. **Absence of Cache Diagnostic Headers:** The application REST API returns standard HTTP headers (`cache-control: 'public, max-age=0, must-revalidate'`); it emits zero application diagnostic headers (such as `X-Cache: HIT` or `X-Cache-TTL`).
3. **Silent Cache Hits:** Under normal operation, `AnalyticsCacheService` logs cache errors via `logger.debug()`, but executes cache hits silently without emitting stdout/stderr logs to the container log stream.
4. **Runtime Observation Status:** Because live keyspace inspection was unavailable, runtime cache-hit and TTL execution could not be directly observed.

## 4. Remaining Unresolved Limitation & Infrastructure Boundary

The sole remaining unverified aspect of the P6.3 staging verification package is the live Redis cache behavior:

1. **Render Compute Tier Limitation:** Render Shell is **unavailable on the current Free compute plan**. Interactive web shell terminal access to container instances requires an upgraded paid compute instance (Starter plan and above) and is not provisioned on Free instances.
2. **Private VPC Network Isolation:** Staging Redis (`techsprout-redis-staging`) is configured with `plan: free` and `ipAllowList: []`. It is bound exclusively to Render's internal Oregon private VPC network and has zero external public ports or internet routing.
3. **Firewall Boundary:** External TCP access directly to the Redis port from outside the VPC is blocked by cloud security rules.
4. **Resulting Observability Boundary:** Independent inspection of live Redis key existence (`EXISTS`), TTL countdown (`TTL`), and memory state via `redis-cli` or container shell was safe-blocked and could not be performed from the runner.
5. **Formal Classification:**

## 6. Recommendations for Eventual Follow-Up

Prior to promoting Phase 6.3 to production, engineering leadership and the infrastructure team should consider the following options:

1. **Compute Plan Upgrade (When Feasible):** If direct container shell access is required for operational audits on staging, upgrade `techsprout-api-staging` to Render's Starter compute plan ($7/mo), which enables Render Shell.
2. **Safe Read-Only Inspection One-Liner:** Should container shell access become available, run the following safe, read-only script using container environment variables:
   ```javascript
   node -e '
   const IORedis = require("ioredis");
   const redis = new IORedis(process.env.REDIS_URL);
   (async () => {
     const key = "instructor:analytics:overview:b6630e69-baa4-4dd9-9f3b-2862966e87f8";
     const exists = await redis.exists(key);
     const ttl = await redis.ttl(key);
     const type = await redis.type(key);
     console.log(JSON.stringify({ key, exists, ttl, type }));
     await redis.quit();
   })();'
   ```
   *Guarantees: Queries strictly `EXISTS`, `TTL`, and `TYPE` on the exact target key; never runs `KEYS *`, prints connection strings, or executes destructive commands.*
3. **Optional Non-Intrusive Telemetry (Future Milestone):** In a future maintenance cycle, consider adding non-intrusive response headers (e.g., `X-Cache: HIT|MISS`) in non-production environments to allow external observability without container shell dependencies.
4. **Production Isolation:** Maintain production branch `main`, production databases, and hosting infrastructure 100% frozen until P6.2 production deployment is verified and P6.3 is formally authorized for promotion.
