## 4. Assessment of Redis Observability Limitation & Formal Engineering Waiver

### 4.1 Root Cause & Technical Boundary
- **Compute Plan Restriction:** In `render.staging.yaml`, `techsprout-redis-staging` and `techsprout-api-staging` operate on Render's Free tier (`plan: free`). Interactive container shell access ("Render Shell") requires an upgraded paid compute instance (Starter plan and above) and is not provisioned on Free instances.
- **Network Isolation:** Staging Redis is configured with `ipAllowList: []` and bound strictly to Render's Oregon private VPC network. It has no public IP or external port forwarding.
- **Firewall Policy:** External TCP connections directly to Redis port 6379 from outside Render's private network are blocked by cloud firewall rules.
- **Application Behavior:** `AnalyticsCacheService` emits no diagnostic HTTP headers and only logs cache connection failures via `logger.debug()`. Normal cache operations execute silently to prevent stdout log pollution.

### 4.2 Architecture Safety & Failure Resilience Analysis
- **Fail-Open Resilience:** `AnalyticsCacheService` wraps all Redis read/write operations in `try/catch` blocks. If Redis is unavailable, slow, or disconnected, the service intercepts the error, logs a debug message, and **fails open** to query PostgreSQL directly.
- **Verified Resilience Test:** Automated test `p6-3-security-hardening.spec.ts` test 5.2 explicitly simulated cache failures and verified that requests complete cleanly from database data without user-facing errors.
- **Zero Mutation Impact:** Analytics caching is strictly read-only. Cache operations never write to database tables, never modify financial records, and do not handle user authentication state (which is handled by signed, stateless HttpOnly session JWTs).
- **No Shared State Hazards:** Cache keys are strictly namespaced by entity (`instructor:analytics:overview:${instructorId}`, `course:analytics:${courseId}:${rangeHash}`). Zero key collision risk exists across tenants.

## 5. Database Migration 0008 Safety, Locking & Schema Compatibility

### 5.1 Migration DDL Content
File: `apps/api/src/database/migrations/0008_analytics_foundation.sql`
```sql
CREATE INDEX IF NOT EXISTS "enrollments_course_enrolled_at_idx" ON "enrollments" USING btree ("course_id","enrolled_at");--> statement-breakpoint
CREATE INDEX IF NOT EXISTS "enrollments_status_enrolled_at_idx" ON "enrollments" USING btree ("status","enrolled_at");--> statement-breakpoint
CREATE INDEX IF NOT EXISTS "lesson_progress_lesson_status_idx" ON "lesson_progress" USING btree ("lesson_id","status");--> statement-breakpoint
CREATE INDEX IF NOT EXISTS "quiz_attempts_quiz_passed_idx" ON "quiz_attempts" USING btree ("quiz_id","is_passed");
```

### 5.2 Locking & Concurrency Behavior
- **Transaction Wrap:** Drizzle migrator executes migrations within a database transaction block (`BEGIN` ... `COMMIT`).
- **PostgreSQL Lock Level:** Standard `CREATE INDEX` acquires a `SHARE` lock on the target tables (`enrollments`, `lesson_progress`, `quiz_attempts`).
- **Read Concurrency:** Under a `SHARE` lock, concurrent read queries (`SELECT`) continue to execute without interruption.
- **Write Concurrency & Lock Duration:** Standard `CREATE INDEX` acquires a `SHARE` lock on the target tables that temporarily blocks write operations (`INSERT`, `UPDATE`, `DELETE`) until index creation finishes, while concurrent `SELECT` reads proceed uninterrupted. Actual lock duration is unverified until execution and depends on table size, database load, and storage performance.

### 5.3 Backward & Forward Compatibility
- **100% Additive:** Zero new tables, zero column additions, zero column renames, zero deletions.
- **Backward Compatibility:** If the application is rolled back to P6.2 (`4c17bdc`), the 4 indexes in PostgreSQL remain completely harmless and transparent to P6.2 code, which will naturally utilize them for composite queries. No database rollback is required.
- **Reversibility:** Should explicit index removal be desired:
  ```sql
  DROP INDEX IF EXISTS "enrollments_course_enrolled_at_idx";
  DROP INDEX IF EXISTS "enrollments_status_enrolled_at_idx";
  DROP INDEX IF EXISTS "lesson_progress_lesson_status_idx";
  DROP INDEX IF EXISTS "quiz_attempts_quiz_passed_idx";
  DELETE FROM "drizzle"."__drizzle_migrations" WHERE created_at = 1791800000000;
  ```

## 8. Security Boundaries & Multi-Tenant Enforcement

| Security Vector | Threat Model | Enforcement Mechanism | Verification Result |
|---|---|---|---|
| **Unauthenticated Access** | Anonymous requests to analytics | `JwtAuthGuard` & `RolesGuard` | Returns `HTTP 401 Unauthorized` (`UNAUTHENTICATED`). |
| **Privilege Escalation** | Students attempting instructor/admin endpoints | `@Roles('INSTRUCTOR')`, `@Roles('ADMIN')` | Returns `HTTP 403 Forbidden` (`FORBIDDEN: Access denied`). |
| **Cross-Role Tampering** | Instructors probing admin platform analytics | `@Roles('ADMIN')` | Returns `HTTP 403 Forbidden` (`FORBIDDEN: Access denied`). |
| **Multi-Tenant Ownership** | Instructor accessing competitor course analytics or roster | `CoursesService.verifyCourseOwnership` | Returns `HTTP 403 Forbidden` (`RESOURCE_OWNERSHIP_DENIED`). |
| **Identity Impersonation** | Student attempting to query another student's engagement | Identity derived strictly from JWT `req.user.id` | Queries strictly `studentId = req.user.id`; external ID spoofing impossible. |
| **SQL Injection** | Malicious query patterns in roster search (`' OR 1=1 --`) | Parameterized Drizzle SQL `ilike` queries | Safely sanitized; executes with 0 results and zero SQL syntax leaks. |
| **CSV / DDE Injection** | Malicious student names executing formulas in Excel | Single-quote prefixing (`'`, `=`, `+`, `-`, `@`) | Prefixes formula triggers; prepends UTF-8 BOM (`\uFEFF`). |
| **Session Token Exfiltration** | Client JavaScript reading auth token | Same-origin Next.js BFF proxy with HttpOnly cookie | `document.cookie` cannot access session token; token stripped from client JSON. |
