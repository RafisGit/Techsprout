## 1. Product Vision & Role Alignment

The objective of **Milestone P6.3 (Learning Analytics & Engagement Engine)** is to provide actionable, pedagogical insight to instructors, platform administrators, and students without introducing third-party analytics bloat, external warehouse lock-in, or speculative features.

### Persona Value Propositions:
1. **Instructors:** Need to monitor course health, understand learner drop-off points, assess quiz comprehension, evaluate enrollment velocity across date ranges, and effortlessly search large student rosters.
2. **Platform Administrators:** Need an authoritative, institutional perspective on platform-wide learning engagement, catalog composition, instructor productivity, and review queue responsiveness.
3. **Students:** Need accurate, real-time visibility into their personal course progress, completed certificates, and weekly learning momentum.

### 2.1 Explicit Scope Exclusions & Rationale:
- **Telemetry Collection & Append-Only Event Table (`learning_events`):** **Explicitly deferred to Phase 7.** 100% of required pedagogical metrics (enrollment trends, learner progress, drop-offs, quiz performance) are directly calculable from existing transactional tables (`enrollments`, `lesson_progress`, `quiz_attempts`). Introducing an unverified event ingestion pipeline and a high-write `learning_events` table in P6.3 adds unnecessary write overhead to Render PostgreSQL and database migration risk prior to production verification of P6.2. Event streaming and telemetry are scheduled for Phase 7 alongside AI tutoring and personalized sequence models.
- **Instructor Revenue Dashboards & Payouts:** Explicitly deferred to **Phase 7 (Instructor Monetization)** in `TECHSPROUT-P6.0-SCOPE` and `ADR-P6-003`. TechSprout's financial subsystem operates under single-merchant institutional SSLCommerz settlement. Introducing instructor revenue shares requires split payouts, tax withholding, and mobile financial services (bKash/Nagad) merchant integrations that belong strictly to Phase 7.
- **AI Tutoring & Automated Recommendations:** Deferred to Phase 7. Predictive drop-off models and LLM tutors require structured interaction logs from P6.3 before training or inference can occur.
- **Second-by-Second Video Watch Heatmaps:** High-frequency heartbeat telemetry (every 2-5 seconds) would generate millions of rows per hour, overloading Render PostgreSQL. P6.3 limits analysis to authoritative milestone completions.

## 3. Exhaustive Metric Dictionary & Specification

Every proposed metric is formally specified below, categorized by reliability and data source.

### Legend for Metric Reliability:
- **`DIRECT` (Authoritative):** Derived directly from persistent transactional tables (`enrollments`, `lesson_progress`, `quiz_attempts`). 100% accurate, fully historical, zero estimation.
- **`AGGREGATED` (Derived):** Computed via deterministic mathematical aggregation (averages, medians, ratios, distributions).

---

### Category A: Instructor Portfolio Metrics (`/instructor/dashboard`)

#### MET-INST-01: Total Enrolled Students
- **Business Purpose:** Measures total unique learner reach across the instructor's authored catalog.
- **Intended User & Auth Scope:** `instructor` (strictly scoped to courses where `courses.instructor_id = req.user.id`).
- **Reliability:** `DIRECT`.
- **Exact Calculation:**
  $$\text{Total Unique Students} = \text{COUNT}(\text{DISTINCT } \text{enrollments.student\_id}) \text{ WHERE } \text{courses.instructor\_id} = \text{actor.id}$$
- **Source Tables:** `enrollments` inner-joined with `courses`.
- **Timezone & Date-Range Semantics:** Lifetime cumulative (or filtered by `enrolled_at` between UTC start and end timestamps).
- **Missing Data Handling:** Returns `0` if instructor has no courses or zero enrollments.
- **Expected Data Volume:** 10 to 50,000 learners per instructor.
- **Calculable from Existing Data:** **YES**. Requires zero schema changes.

#### MET-INST-02: Total Course Completions
- **Business Purpose:** Tracks how many students have fully completed any course authored by the instructor.
- **Intended User & Auth Scope:** `instructor` (scoped by `courses.instructor_id`).
- **Reliability:** `DIRECT`.
- **Exact Calculation:**
  $$\text{Completions} = \text{COUNT}(\text{enrollments.id}) \text{ WHERE } \text{enrollments.status} = \text{'COMPLETED'} \text{ AND } \text{courses.instructor\_id} = \text{actor.id}$$
- **Source Tables:** `enrollments` inner-joined with `courses`.
- **Timezone & Date-Range Semantics:** UTC boundary based on `enrollments.completed_at`.
- **Missing Data Handling:** Returns `0` if no completed enrollments exist.
- **Calculable from Existing Data:** **YES**.

#### MET-INST-03: Portfolio Completion Rate
- **Business Purpose:** High-level metric of student course completion effectiveness across the instructor's portfolio.
- **Intended User & Auth Scope:** `instructor` (scoped by `courses.instructor_id`).
- **Reliability:** `AGGREGATED`.
- **Exact Calculation:**
  $$\text{Completion Rate (\%)} = \begin{cases} 
  0 & \text{if Total Enrollments} = 0 \\ 
  \text{ROUND}\left(\frac{\text{Total Completed Enrollments}}{\text{Total Enrollments}} \times 100\right) & \text{otherwise} 
  \end{cases}$$
- **Missing Data Handling:** Zero-division guard: returns `0%` when total enrollments is zero.
- **Calculable from Existing Data:** **YES**.

#### MET-INST-04: Active 30-Day Learners
- **Business Purpose:** Measures recent pedagogical engagement (learners actively accessing material).
- **Intended User & Auth Scope:** `instructor` (scoped by `courses.instructor_id`).
- **Reliability:** `DIRECT`.
- **Exact Calculation:**
  $$\text{Active Learners} = \text{COUNT}(\text{DISTINCT } \text{enrollments.student\_id}) \text{ WHERE } \text{enrollments.last\_accessed\_at} \ge (\text{NOW()} - \text{INTERVAL '30 days'})$$
- **Source Tables:** `enrollments` inner-joined with `courses`.
- **Calculable from Existing Data:** **YES** (`enrollments.last_accessed_at` is updated on lesson views).

### Category B: Course-Level Deep Dive Metrics (`/instructor/courses/[id]/analytics`)

#### MET-CRS-01: Enrollment Growth Trend
- **Business Purpose:** Visualizes daily/weekly student acquisition over selected timeframes (7d, 30d, 90d, custom).
- **Intended User & Auth Scope:** `instructor` (scoped by `courses.instructor_id === actor.id`) and `admin`.
- **Reliability:** `DIRECT`.
- **Exact Calculation:** Grouped by bucketed UTC date:
  $$\text{Bucket Count} = \text{COUNT}(\text{enrollments.id}) \text{ WHERE } \text{enrollments.course\_id} = \text{targetId} \text{ AND } \text{enrolled\_at} \in [\text{start}, \text{end}] \text{ GROUP BY } \text{DATE\_TRUNC}(\text{'day'}, \text{enrolled\_at})$$
- **Timezone & Date-Range Semantics:** Normalized UTC boundaries (`00:00:00.000Z` to `23:59:59.999Z`).
- **Missing Data Handling:** Zero-filled date series (every calendar day within range is present with count `0` if no enrollments occurred).
- **Calculable from Existing Data:** **YES**.

#### MET-CRS-02: Learner Progress Funnel & Distribution
- **Business Purpose:** Identifies what percentage of students are at each stage of course completion to locate drop-off cohorts.
- **Intended User & Auth Scope:** `instructor` (course owner) and `admin`.
- **Reliability:** `AGGREGATED`.
- **Exact Calculation:** Group enrolled students into 5 discrete progress brackets based on calculated percentage:
  - Bracket 1: `0% – 19%` (Just started / At risk)
  - Bracket 2: `20% – 39%` (Early progress)
  - Bracket 3: `40% – 59%` (Midway)
  - Bracket 4: `60% – 79%` (Advanced)
  - Bracket 5: `80% – 99%` (Near completion)
  - Bracket 6: `100%` (Fully completed)
- **Source Tables:** Computed by comparing count of completed `lesson_progress` rows per enrollment against total lessons in course.
- **Calculable from Existing Data:** **YES**.

#### MET-CRS-03: Lesson Completion & Drop-off Hotspots
- **Business Purpose:** Pinpoints specific lessons causing student friction, abandonment, or disengagement.
- **Intended User & Auth Scope:** `instructor` (course owner) and `admin`.
- **Reliability:** `DIRECT`.
- **Exact Calculation:** For each lesson in the course (ordered by module position and lesson position):
  - Total Enrollments in course: $N$
  - Lesson Completers: $C_L = \text{COUNT}(\text{lesson\_progress.id}) \text{ WHERE } \text{lesson\_id} = L \text{ AND } \text{status} = \text{'COMPLETED'}$
  - Lesson Completion Rate: $R_L = \text{ROUND}((C_L / N) \times 100)$
  - Sequential Drop-off: $\Delta_L = R_{L-1} - R_L$ (percentage points lost from previous lesson)
- **Missing Data Handling:** If $N = 0$, rate is $0\%$, drop-off is $0\%$.
- **Calculable from Existing Data:** **YES**.

#### MET-CRS-04: Quiz Performance Summary
- **Business Purpose:** Informs instructors whether their quizzes are too easy, too difficult, or functioning properly.
- **Intended User & Auth Scope:** `instructor` (course owner) and `admin`.
- **Reliability:** `AGGREGATED`.
- **Exact Calculation:** For each quiz in the course:
  - Total Attempts: $\text{COUNT}(\text{quiz\_attempts.id})$
  - Unique Students Attempted: $\text{COUNT}(\text{DISTINCT } \text{quiz\_attempts.student\_id})$
  - Pass Rate: $\text{ROUND}((\text{COUNT}(\text{attempts with is\_passed = true}) / \text{Total Submitted Attempts}) \times 100)$
  - Average Score: $\text{ROUND}(\text{AVG}(\text{quiz\_attempts.percentage}), 1)$
  - First-Attempt Pass Rate: $\text{ROUND}((\text{Passed on attempt 1} / \text{Total students attempting}) \times 100)$
- **Source Tables:** `quiz_attempts` inner-joined with `quizzes` and `modules`.
- **Calculable from Existing Data:** **YES**.

#### MET-CRS-05: Average Completion Velocity (Days to Complete)
- **Business Purpose:** Estimates typical duration required for an active student to finish the course.
- **Intended User & Auth Scope:** `instructor` (course owner) and `admin`.
- **Reliability:** `AGGREGATED`.
- **Exact Calculation:**
  $$\text{Avg Days} = \text{ROUND}(\text{AVG}(\text{EXTRACT}(\text{EPOCH FROM } (\text{completed\_at} - \text{enrolled\_at})) / 86400)) \text{ WHERE } \text{status} = \text{'COMPLETED'}$$
- **Missing Data Handling:** If completed count is $0$, returns `null` or `"N/A"`.
- **Calculable from Existing Data:** **YES**.

### Category C: Learner Roster Search & Filtering Enhancement (`DEF-P6.2-UX-01`)

#### REQ-ROSTER-01: Server-Side Global Roster Search
- **Business Purpose:** Allows instructors and administrators to search any learner by name or email across all pagination pages.
- **Intended User & Auth Scope:** `instructor` (course owner) and `admin`.
- **Input Parameters:**
  - `search`: string, trimmed, max 100 characters (case-insensitive substring match against `users.name` OR `users.email`).
  - `status`: optional enum (`ACTIVE`, `COMPLETED`, `CANCELLED`).
  - `page`: positive integer (default 1).
  - `limit`: integer, 1 to 100 (default 10 on screen, up to 100 on export).
  - `sortBy`: optional (`enrolledAt`, `name`, `progressPercentage`, `lastAccessedAt`).
  - `sortOrder`: `asc` or `desc` (default `desc`).
- **Response Format:** Paginated envelope with `items`, `pagination` (`page`, `limit`, `total`, `totalPages`, `hasNextPage`, `hasPreviousPage`), `totalEnrolled`, `completedCount`.
- **Performance Requirement:** Must execute in $< 100\text{ms}$ by eliminating the N+1 query loop in `getAdminCourseEnrollments`.

### Category D: Platform Administrative Analytics (`/admin/analytics` & Overview)

#### MET-ADM-01: Catalog Health & Lifecycle Breakdown
- **Business Purpose:** Authoritative count of courses across all lifecycle stages.
- **Intended User & Auth Scope:** `admin` only.
- **Reliability:** `DIRECT`.
- **Exact Calculation:** Count of courses grouped by `status` (`PUBLISHED`, `IN_REVIEW`, `DRAFT`, `ARCHIVED`).
- **Source Tables:** `courses`.
- **Calculable from Existing Data:** **YES**.

#### MET-ADM-02: Institutional Learning Scale
- **Business Purpose:** Measures aggregate educational footprint.
- **Intended User & Auth Scope:** `admin` only.
- **Exact Calculation:**
  - Total Registered Students: $\text{COUNT}(\text{users.id})$ where user possesses role `student`.
  - Total Active Instructors: $\text{COUNT}(\text{users.id})$ where user possesses role `instructor` and authors $\ge 1$ course.
  - Platform-wide Enrollments: $\text{COUNT}(\text{enrollments.id})$.
  - Platform-wide Certificates Issued: $\text{COUNT}(\text{certificates.id})$.
  - Platform Overall Completion Rate: $\text{ROUND}((\text{Completed Enrollments} / \text{Total Enrollments}) \times 100)$.
- **Calculable from Existing Data:** **YES**.

#### MET-ADM-03: Review Queue Turnaround SLA
- **Business Purpose:** Monitors administrative response speed for course publishing approvals.
- **Intended User & Auth Scope:** `admin` only.
- **Reliability:** `AGGREGATED`.
- **Exact Calculation:**
  - Pending Review Count: $\text{COUNT}(\text{course\_review\_requests.id}) \text{ WHERE } \text{status} = \text{'PENDING'}$.
  - Avg Turnaround Time: $\text{AVG}(\text{reviewed\_at} - \text{submitted\_at}) \text{ WHERE } \text{status IN ('APPROVED', 'REJECTED')}$.
- **Calculable from Existing Data:** **YES**.

### Category E: Student Personal Engagement (`/dashboard`)

#### MET-STU-01: Personal Learning Counters
- **Business Purpose:** Replaces static zeroes on student `/dashboard` with dynamic, authoritative figures.
- **Intended User & Auth Scope:** `student` (scoped strictly to `req.user.id`).
- **Reliability:** `DIRECT`.
- **Exact Calculation:**
  - Enrolled Courses: $\text{COUNT}(\text{enrollments.id}) \text{ WHERE } \text{student\_id} = \text{actor.id} \text{ AND } \text{status} \ne \text{'CANCELLED'}$.
  - In Progress Courses: $\text{COUNT}(\text{enrollments.id}) \text{ WHERE } \text{student\_id} = \text{actor.id} \text{ AND } \text{status} = \text{'ACTIVE'}$.
  - Certificates Earned: $\text{COUNT}(\text{certificates.id}) \text{ WHERE } \text{student\_id} = \text{actor.id}$.
- **Calculable from Existing Data:** **YES**.

## 5. Architectural Verdict on Scope Feasibility

1. **Immediate High-Value Delivery:** 100% of core instructor, administrative, and student dashboard analytics (**MET-INST-01** through **MET-STU-01**) are computed **authoritatively from existing database tables**.
2. **Backward Compatibility:** Because existing tables contain historical timestamps (`enrolled_at`, `completed_at`, `last_accessed_at`), newly deployed analytics dashboards will immediately populate with full historical data on Day 1.
3. **Telemetry Deferral Resolution:** Telemetry collection and the `learning_events` table are formally deferred to Phase 7. P6.3 is 100% focused on delivering high-performance, authoritative analytics from existing transactional records and resolving `DEF-P6.2-UX-01`.
