## 1. Architectural Philosophy & Principles

Milestone P6.3 adheres strictly to the existing architectural patterns established in TechSprout:
1. **Modular Monolith Discipline:** All backend analytics capabilities reside within a dedicated `AnalyticsModule` in `apps/api/src/modules/analytics`, maintaining explicit service boundaries and clean dependency injection.
2. **Contract-First Development:** Shared types, DTOs, and validation schemas reside in `packages/contracts`, ensuring full type-safety between the NestJS backend and Next.js frontend.
3. **Authoritative Transactional Analytics:** High-performance analytical queries executed directly on existing transactional tables (`enrollments`, `lesson_progress`, `quiz_attempts`, `courses`, `users`). Provides immediate historical depth on Day 1 without external warehouses or unverified event streams.
4. **Telemetry Deferral to Phase 7:** Telemetry event collection and the append-only `learning_events` table (from `ADR-P6-003`) are deferred to Phase 7 to avoid unverified write overhead and unnecessary migration complexity.
5. **Zero-Trust Scoped Authorization:** Analytics endpoints strictly enforce resource ownership. Instructors cannot inspect cross-instructor cohorts; students have zero access to administrative or educator endpoints.
6. **Lean Frontend Visualization:** Avoid heavy, conflicting chart bundles on React 19 / Turbopack. Deliver lightweight, responsive, accessible SVG/CSS charts paired with screen-reader accessible data tables.

## 5. Database Optimization & Elimination of N+1 Queries

### 5.1 Elimination of N+1 Queries in Learner Roster
In the current implementation, `getAdminCourseEnrollments` runs $2N + 2$ queries.
The optimized architecture reduces this to **exactly 3 queries**, regardless of page limit ($O(1)$ database query count):

1. **Query 1 (Course Lesson Count):** Executed once:
   ```sql
   SELECT COUNT(lessons.id) AS total_lessons
   FROM lessons
   INNER JOIN modules ON lessons.module_id = modules.id
   WHERE modules.course_id = $1;
   ```
2. **Query 2 (Filtered Enrolled Learners with Pagination & Search):**
   ```sql
   SELECT enrollments.*, users.id AS user_id, users.name, users.email
   FROM enrollments
   INNER JOIN users ON enrollments.student_id = users.id
   WHERE enrollments.course_id = $1
     AND ($2::text IS NULL OR enrollments.status = $2)
     AND ($3::text IS NULL OR users.name ILIKE ('%' || $3 || '%') OR users.email ILIKE ('%' || $3 || '%'))
   ORDER BY enrollments.enrolled_at DESC
   LIMIT $4 OFFSET $5;
   ```
3. **Query 3 (Batch Progress Calculation):** Single grouped query using `IN (...)` for all fetched enrollment IDs:
   ```sql
   SELECT enrollment_id, COUNT(id) AS completed_lessons
   FROM lesson_progress
   WHERE enrollment_id = ANY($1::uuid[])
     AND status = 'COMPLETED'
   GROUP BY enrollment_id;
   ```
   *Performance result:* Query time drops from ~350ms to **< 25ms** for 100 learners.

### 5.2 Single-Pass Course Drop-off Query
Rather than querying lesson progress for each individual student, drop-offs are aggregated across the entire enrolled cohort in a single scan:
```sql
SELECT 
  l.id AS lesson_id,
  l.title AS lesson_title,
  l.position AS lesson_position,
  m.id AS module_id,
  m.title AS module_title,
  m.position AS module_position,
  COUNT(lp.id) FILTER (WHERE lp.status = 'COMPLETED') AS completed_count
FROM lessons l
INNER JOIN modules m ON l.module_id = m.id
LEFT JOIN lesson_progress lp ON l.id = lp.lesson_id
WHERE m.course_id = $1
GROUP BY l.id, l.title, l.position, m.id, m.title, m.position
ORDER BY m.position ASC, l.position ASC;
```

## 6. Database Migration Specification: `0008_analytics_foundation.sql`

### 6.1 Reconciled Migration Content
Telemetry event collection and the `learning_events` table are deferred to Phase 7. Migration `0008` focuses exclusively on the secondary composite performance indexes required by P6.3 analytics queries:

```sql
-- Migration 0008: Analytics Performance Indexes Foundation

-- Composite Indexes on Existing Transactional Tables
CREATE INDEX IF NOT EXISTS "enrollments_course_enrolled_at_idx" ON "enrollments" USING btree ("course_id", "enrolled_at");
CREATE INDEX IF NOT EXISTS "enrollments_status_enrolled_at_idx" ON "enrollments" USING btree ("status", "enrolled_at");
CREATE INDEX IF NOT EXISTS "lesson_progress_lesson_status_idx" ON "lesson_progress" USING btree ("lesson_id", "status");
CREATE INDEX IF NOT EXISTS "quiz_attempts_quiz_passed_idx" ON "quiz_attempts" USING btree ("quiz_id", "is_passed");
```

### 6.2 Migration Safety & Deployment Assessment
- **Transactional Migration Architecture:** The TechSprout migration runner (`apps/api/src/database/migrate.ts`) executes migrations using Drizzle ORM's PostgreSQL migrator (`drizzle-orm/node-postgres/migrator`), which executes all statements within an explicit transaction block (`BEGIN ... COMMIT`). The four index statements in migration `0008` adhere strictly to this established transactional architecture.
- **Locking Semantics (Reads Permitted, Writes Blocked):** Ordinary PostgreSQL `CREATE INDEX` acquires a `SHARE` lock on the indexed table. Concurrent `SELECT` queries remain permitted, but concurrent write operations (`INSERT`, `UPDATE`, `DELETE`) are blocked and queue until index construction completes and the transaction commits. Standard index creation is therefore read-accessible, not non-blocking.
- **`CREATE INDEX CONCURRENTLY` Incompatibility:** PostgreSQL strictly prohibits `CREATE INDEX CONCURRENTLY` inside a transaction block (PostgreSQL Error `25001`: `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`). Executing concurrent index creation would require a separately verified, non-transactional execution mechanism outside the current Drizzle runner.
- **Operational Impact & Deployment Prerequisites:** The duration of the `SHARE` lock depends on table size, database load, and storage performance (unmeasured in production; actual duration will depend on production data volume and system load). Retaining the current transactional runner is recommended because current table volumes remain modest and introducing out-of-band runners adds operational complexity. Deployments must be scheduled during standard release windows when write activity is minimal.
- **Prerequisite Alignment:** Fully compatible with migration `0007_instructor_platform_foundation.sql`.
- **Rollback Safety:** Rollback drops the 4 secondary indexes without any data loss or schema destabilization.
- **pg-mem Test Compatibility:** 100% compatible with the in-memory test runner (`createTestDatabase()`).

## 7. Caching Strategy & Redis Invariants

1. **Transactional vs. Analytical Traffic Separation:**
   - Detailed roster fetches (`/admin/courses/:id/enrollments`) are **uncached** to reflect immediate student mutations (e.g., student completes a lesson or is reactivated).
   - Portfolio overview metrics (`/instructor/analytics/overview`) and course trend analytics (`/instructor/analytics/courses/:id`) are cached in Redis with a **10-minute TTL** (`instructor:analytics:overview:<instructorId>`, `course:analytics:<courseId>:<rangeHash>`).
2. **Cache Invalidation:**
   - Event listeners in `EventsModule` listen to domain events (`ENROLLMENT_COMPLETED`, `COURSE_ENROLLED`) and invalidate the associated course and instructor cache keys asynchronously.
3. **Graceful Fallback:** If Redis is temporarily unreachable, `AnalyticsService` fails-open and executes the live SQL query directly without degrading user experience.

## 8. Frontend Visualization & Accessibility Architecture

### 8.1 Charting Technology Evaluation
- **Option A (Heavy External Library - Recharts / Chart.js):**
  - *Risks:* React 19 RC compatibility conflicts, large client JS bundle (+120KB gzipped), hydration warnings in Next.js Turbopack.
- **Option B (Zero-Dependency Accessible SVG & Tailwind Components - Approved):**
  - *Benefits:* 100% native React 19 compatibility, zero bundle overhead, pixel-perfect design system alignment, completely accessible via semantic HTML5, SVG `<title>` tags, and ARIA attributes.
  - *Components:*
    1. `TrendLineChart`: Scaled SVG polylines with hover tooltips and accessible screen-reader tables.
    2. `ProgressDistributionBar`: Segmented horizontal stacked bars visualizing cohort brackets.
    3. `DropOffTable`: Accessible data table showing drop-off percentages with visual color gradients (emerald to rose).

### 8.2 Frontend UX States
- **Loading:** Tailwind pulse skeletons matching exact card and graph dimensions.
- **Empty States:** Friendly illustration and message when course has zero enrollments (e.g., *"No students have enrolled yet. Share your course link to start tracking analytics."*).
- **Error Boundaries:** Inline alert retry buttons that do not crash the surrounding page layout.

## 9. Security, Privacy & Data Governance

### 9.1 Multi-Tenant Data Isolation
- Every instructor analytical query is parameterized with `actor.id`. The SQL `WHERE` clause strictly filters by `courses.instructor_id = $actorId`.
- Even if an instructor crafts an arbitrary `courseId` in the URL, `ResourceOwnershipGuard` interceptors reject the request before database execution (`HTTP 403 Forbidden`).

### 9.2 Small Cohort De-anonymization Prevention
- In educational privacy frameworks (FERPA / GDPR), displaying granular percentage drop-offs on tiny cohorts ($N < 5$ students) can inadvertently disclose an individual learner's academic struggles to peers or staff.
- **Invariant:** When total enrolled learners $N < 5$, the course analytics view displays an informative privacy badge: *"Cohort analytics are aggregated; minimum 5 learners recommended for statistically valid drop-off trends."* Individual student grades are never exposed on aggregate screens.
