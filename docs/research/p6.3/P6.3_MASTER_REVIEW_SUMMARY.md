## 1. Executive Summary

This master summary synthesizes the research, current-state codebase audit, architectural review, and implementation plan for **Milestone P6.3 (Learning Analytics & Engagement Engine)** in the TechSprout School LMS.

Following senior scope reconciliation:
- **Telemetry Event Logging (`learning_events` table & client event logging) is explicitly deferred to Phase 7.**
- **100% of P6.3 pedagogical metrics** (instructor portfolio overviews, course enrollment trends, learner progress distribution, drop-off hotspots, and quiz performance) are powered directly and authoritatively by existing transactional tables (`enrollments`, `lesson_progress`, `quiz_attempts`, `courses`, `users`).
- **Defect `DEF-P6.2-UX-01` is resolved** via server-side learner roster search across `users.name` and `users.email`.
- **The N+1 database query bottleneck** in learner roster fetching is eliminated, dropping query latency from ~350ms to $< 25\text{ms}$.
- **Migration `0008` introduces transactional secondary composite indexes** to optimize analytical time-series queries. The current Drizzle runner executes migrations inside an atomic transaction; ordinary PostgreSQL `CREATE INDEX` permits concurrent reads but acquires a `SHARE` lock that blocks writes (`INSERT`, `UPDATE`, `DELETE`) until the transaction commits. `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block (PostgreSQL Error `25001`) and would require a separately verified non-transactional runner. Anticipated impact depends on table size, database load, and storage performance; because table volumes remain modest, using the existing transactional runner during standard deployment windows is recommended.

## 3. Explicit Roadmap Boundaries & Exclusions

To safeguard engineering momentum and platform stability, the following boundaries are strictly frozen for P6.3:
1. **NO Telemetry Event Ingestion or `learning_events` Table:** High-frequency event ingestion and append-only event logging are **deferred to Phase 7** (alongside AI tutoring and personalized sequence models). All P6.3 metrics are derived from existing transactional records.
2. **NO Instructor Revenue Dashboards or Marketplace Payouts:** Explicitly deferred to **Phase 7 (Instructor Monetization)**. The platform retains single-vendor institutional settlement.
3. **NO AI Recommendations or Automated Drop-off Predictions:** Explicitly deferred to **Phase 7**. Structured interaction data from P6.3 must precede machine learning models.
4. **NO Second-by-Second Video Scrubbing Telemetry:** High-frequency video telemetry would flood PostgreSQL. P6.3 analyzes authoritative completion milestones.
5. **NO External Data Warehouse Dependencies:** Operates 100% within the existing NestJS and PostgreSQL 16 stack.
