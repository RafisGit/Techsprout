### 2.2 Transaction Mechanics Verification
Inspection of the installed Drizzle runtime source (`drizzle-orm/pg-core/dialect.cjs`, lines 62–73) confirms:

```javascript
// drizzle-orm/pg-core/dialect.cjs
await session.transaction(async (tx) => {
  for await (const migration of migrations) {
    if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis) {
      for (const stmt of migration.sql) {
        await tx.execute(import_sql2.sql.raw(stmt));
      }
      await tx.execute(
        import_sql2.sql`insert into ${import_sql2.sql.identifier(migrationsSchema)}.${import_sql2.sql.identifier(migrationsTable)} ("hash", "created_at") values(${migration.hash}, ${migration.folderMillis})`
      );
    }
  }
});
```

### 2.3 Runner Invariants & Constraints
1. **Mandatory Transaction Block:** Drizzle ORM unconditionally wraps all pending migration files and statements inside a single PostgreSQL transaction block:
   ```sql
   BEGIN;
   -- Statement 1
   -- Statement 2
   -- INSERT INTO "drizzle"."__drizzle_migrations" ...
   COMMIT;
   ```
2. **Zero Support for Non-Transactional DDL:** PostgreSQL strictly prohibits non-transactional statements inside transaction blocks:
   - Executing `CREATE INDEX CONCURRENTLY` inside `session.transaction` triggers PostgreSQL Error Code `25001` (`active_sql_transaction`):
     ```text
     ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
     ```
3. **No Per-Statement or Per-File Configuration:** Drizzle's `MigrationConfig` interface accepts only `migrationsFolder`, `migrationsTable`, and `migrationsSchema`. It offers no configuration hook, comment pragma, or dialect option to disable transaction wrapping for a specific migration.
4. **Existing Codebase Conventions:** Migrations `0000` through `0007` all utilize standard transactional DDL (`CREATE TABLE`, `ALTER TABLE`, and standard `CREATE INDEX`). Migration `0008` adheres to this existing architecture.

### 3.1 `enrollments_course_enrolled_at_idx`
- **Schema Alignment:** Defined in `apps/api/src/database/schema/enrollments.ts` (line 43) as `index('enrollments_course_enrolled_at_idx').on(table.courseId, table.enrolledAt)`.
- **Target Table & Columns:** Table `enrollments`. Columns: `course_id` (`uuid`), `enrolled_at` (`timestamp with time zone`). Both exist and match.
- **Demonstrated Query Justification:**
  - **Endpoint:** `GET /api/v1/instructor/analytics/courses/:courseId` (WP-03/WP-04).
  - **Query Pattern:**
    ```sql
    SELECT date_trunc('day', enrolled_at) AS date, COUNT(id) AS count
    FROM enrollments
    WHERE course_id = $1
      AND enrolled_at >= $2
      AND enrolled_at <= $3
    GROUP BY date_trunc('day', enrolled_at)
    ORDER BY date ASC;
    ```
  - **Why Existing Indexes Are Insufficient:** Existing `enrollments_course_id_idx` indexes `(course_id, status)`. It cannot satisfy a range scan on `enrolled_at`. Existing `enrollments_enrolled_at_idx` indexes only `enrolled_at`, requiring an expensive table scan + filter for specific `course_id` values.
  - **Optimization Value:** The composite `(course_id, enrolled_at)` index allows an exact equality seek on `course_id` followed by a direct range scan on `enrolled_at`, eliminating sort overhead and unnecessary heap fetches.
  - **Justification Verdict:** **FULLY JUSTIFIED**.

## 4. Locking & Deployment Assessment

### 4.1 Technical Reality of PostgreSQL Index Creation
In PostgreSQL, executing standard `CREATE INDEX`:
1. **Acquires a `SHARE` Lock:** Standard `CREATE INDEX` acquires a `SHARE` lock on the target table.
2. **Permits Reads:** Concurrent `SELECT` queries continue uninterrupted.
3. **BLOCKS Writes:** All concurrent write statements (`INSERT`, `UPDATE`, `DELETE`) are **strictly blocked** and will wait in PostgreSQL's lock queue until index creation finishes and the transaction commits.
4. **Escalation & Lock Contention Risk:** If a long-running write transaction is already holding a lock on the table when `CREATE INDEX` attempts to acquire `SHARE`, `CREATE INDEX` queues behind it. Subsequent queries (including reads) may then queue behind `CREATE INDEX` if lock escalation occurs.

### 4.2 Retraction of Planning Document Claims
Planning documents `P6.3_SCOPE_AND_IMPLEMENTATION_PLAN.md` (line 79) and `P6.3_MASTER_REVIEW_SUMMARY.md` (line 22) previously described migration 0008 as introducing **"non-blocking secondary indexes"**.
- This claim was technically inaccurate and has been formally retracted across all documentation.
- Standard `CREATE INDEX IF NOT EXISTS` statements are read-accessible but **write-blocking**.
- The actual duration of write blocking has not been measured by an observed production benchmark; duration depends directly on production data volume, database load, and storage performance.

## 5. Comparative Evaluation: Option A vs. Option B

| Dimension | Option A: Retain Ordinary Index Creation (`CREATE INDEX`) | Option B: Concurrent Index Creation (`CREATE INDEX CONCURRENTLY`) |
| :--- | :--- | :--- |
| **Execution Tooling** | Native Drizzle runner (`apps/api/src/database/migrate.ts`). | Requires external script or custom non-transactional runner bypassing Drizzle. |
| **Transaction Semantics** | Runs inside standard `BEGIN ... COMMIT` block. Atomic rollback on error. | Prohibited inside transaction blocks (PostgreSQL Error `25001`). Non-atomic. |
| **Read Availability** | 100% available (`SELECT` queries are not blocked). | 100% available (`SELECT` queries are not blocked). |
| **Write Availability** | **Temporarily blocked** (`SHARE` lock) for the duration of the build. | **Fully available** (`SHARE UPDATE EXCLUSIVE` lock allows concurrent writes). |
| **Build Duration & Impact** | Duration depends on table size, database load, and storage performance. (Unmeasured in production). | 2x – 3x longer overall (requires 2 full table scans + waiting for running transactions). |
| **Failure Mode** | Transaction cleanly rolls back. Zero catalog pollution. | Leaves `INVALID` index in catalog; requires manual operator intervention (`DROP INDEX`). |
| **Architectural Complexity** | Zero. Fits current repository conventions and CI pipelines. | High. Requires splitting migration runners or adding manual operational runbooks. |

### 5.1 Strategic Recommendation: Retain Option A
We strongly recommend **retaining Option A (Ordinary Index Creation)**:
1. **Modest Table Volumes:** Current table volume across TechSprout remains modest.
2. **Runner Integrity:** Introducing a parallel migration tool solely for `CONCURRENTLY` would bifurcate TechSprout's database migration architecture, complicate CI/CD pipelines, and introduce silent `INVALID` index risks upon transient failures.
3. **Standard Deployment Prerequisite:** Migrations must be executed during standard scheduled release windows or maintenance periods when write traffic is minimal.
