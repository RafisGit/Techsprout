## 2. Detailed Audit: WP-P8-01 — Lifecycle & Entitlements

### 2.1 State Machine Integrity & Terminal State Protection
- **Implementation:** [`apps/api/src/modules/subscriptions/subscription-lifecycle.machine.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/subscriptions/subscription-lifecycle.machine.ts)
- **State Machine Definition:**
  - `INCOMPLETE` -> `ACTIVE`, `INCOMPLETE_EXPIRED`
  - `ACTIVE` -> `PAST_DUE`, `CANCELED`, `EXPIRED`
  - `PAST_DUE` -> `ACTIVE`, `UNPAID`, `CANCELED`, `EXPIRED`
  - `UNPAID` -> `ACTIVE`, `CANCELED`, `EXPIRED`
  - `CANCELED` -> `EXPIRED`
  - `INCOMPLETE_EXPIRED` -> *Terminal* (no outbound transitions)
  - `EXPIRED` -> *Terminal* (no outbound transitions)
- **Audit Verification:**
  - `canTransitionSubscriptionStatus(from, to)` strictly enforces valid graph edges. Any illegal jump throws an unhandled state rejection.
  - Terminal states `EXPIRED` and `INCOMPLETE_EXPIRED` have empty transition sets: `[SubscriptionStatus.EXPIRED]: []`. Subscriptions in terminal states cannot be reactivated or renewed.
  - Transition from `CANCELED` allows only `EXPIRED` once the prepaid period terminates, preventing re-activation of previously canceled subscriptions without establishing a brand new checkout session.

### 2.2 Lifetime Course Purchase Precedence
- **Implementation:** [`apps/api/src/modules/subscriptions/subscription-entitlement.evaluator.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/subscriptions/subscription-entitlement.evaluator.ts)
- **Rule Verification:**
  - In `evaluateCourseAccess(context)`, `context.hasLifetimePurchase` is checked **first** before evaluating subscription status:
    ```ts
    if (context.hasLifetimePurchase) {
      return {
        hasAccess: true,
        source: 'LIFETIME_PURCHASE',
        reason: 'Direct course purchase grants permanent access regardless of subscription state',
      };
    }
    ```
  - Even if a student's subscription transitions to `PAST_DUE`, `UNPAID`, `CANCELED`, or `EXPIRED`, prior lifetime course purchases remain 100% active. Entitlement hierarchy adheres to product invariant specs.

### 2.3 Cancel-At-Period-End and Grace Period Behavior
- **Audit Remediation (FINDING-P8-H01):**
  - *Identified Gap:* If a customer set `cancelAtPeriodEnd: true`, the scheduler previously only evaluated whether `now >= sub.currentPeriodEnd`. If the 24-hour renewal window executed while `now < sub.currentPeriodEnd`, the scheduler could attempt to evaluate renewal invoicing.
  - *Correction Applied:* [`apps/api/src/modules/subscriptions/subscription-billing.service.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/subscriptions/subscription-billing.service.ts) was updated to explicitly distinguish pre-period and post-period execution:
    1. If `sub.status === 'CANCELED'` and `now >= sub.currentPeriodEnd`: transitions safely to `EXPIRED` with audit log `SUBSCRIPTION_EXPIRED`.
    2. If `sub.cancelAtPeriodEnd === true` and `now < sub.currentPeriodEnd`: safely skips renewal charge generation (`status: 'CANCELED_AT_PERIOD_END'`, `reason: 'Subscription scheduled for cancellation at period end; skipping renewal charge'`).
    3. If `sub.cancelAtPeriodEnd === true` and `now >= sub.currentPeriodEnd`: transitions status from `ACTIVE` to `CANCELED` with audit event `SUBSCRIPTION_CANCELED_AT_PERIOD_END`.
- **Dunning Grace Period Entitlement:**
  - During `PAST_DUE`, `isWithinDunningGracePeriod` provides continued access if `now <= dunningGracePeriodEnd` (7 days from initial failure). Once the grace period expires, `evaluateCourseAccess` denies access (`hasAccess: false`, `reason: 'Dunning grace period has expired; payment required'`).

### 2.4 Database Schema Constraints & Domain Rules
- **Implementation:** [`apps/api/src/database/schema/subscriptions.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/schema/subscriptions.ts)
- **Constraints Verified:**
  - `currency`: Enforced check constraint `currency IN ('BDT')` via `subscription_plans_currency_check` and `subscription_invoices_currency_check`.
  - Non-negative amounts: `price_cents >= 0` and `amount_cents >= 0` check constraints.
  - Interval constraint: `billing_interval IN ('MONTHLY', 'YEARLY')`.
  - Active subscription uniqueness: Partial unique index `unique_active_student_plan_idx` on `(student_id, plan_id)` where `status IN ('ACTIVE', 'PAST_DUE', 'UNPAID')` prevents duplicate concurrent active subscriptions for the same student on the same plan.
  - Relational Integrity: `ON DELETE RESTRICT` on foreign keys `plan_id`, `student_id`, `mandate_id` protects against accidental cascade deletions of financial records.

## 3. Audit: WP-P8-02 — Mandate Security & Provider Boundary

### 3.1 Encryption & Token Security at Rest
- **Implementation:** [`apps/api/src/modules/payments/mandates.service.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/payments/mandates.service.ts)
- **Cryptographic Standard:**
  - Algorithm: AES-256-GCM authenticated symmetric encryption with 12-byte random IV (`crypto.randomBytes(12)`).
  - Dedicated Key: Explicit environment variable `PAYMENT_TOKEN_ENCRYPTION_KEY`.
  - Dedicated Key Verification:
    ```ts
    if (!key || key.length !== 64 || !/^[0-9a-fA-F]{64}$/.test(key)) {
      throw new Error('PAYMENT_TOKEN_ENCRYPTION_KEY must be a valid 32-byte hex string (64 characters)');
    }
    if (env.AUTH_SECRET && key === env.AUTH_SECRET) {
      throw new Error('PAYMENT_TOKEN_ENCRYPTION_KEY cannot be reused from AUTH_SECRET');
    }
    ```
  - Fail-Closed: If the key is missing, improperly formatted, or reused from `AUTH_SECRET`, the service refuses to initialize or decrypt tokens.

### 3.2 Token Leakage Elimination
- **Persistence:** Only ciphertext (`gateway_token_ciphertext`) and authentication tag (`gateway_token_auth_tag`) are stored in the database.

  ```ts
  export function toMandateDto(m: SelectPaymentMandate): PaymentMandateDto {
    return {
      id: m.id,
      studentId: m.studentId,
      gateway: m.gateway,
      maskedAccount: m.maskedAccount,
      status: m.status,
      expiresAt: m.expiresAt,
      createdAt: m.createdAt,
      updatedAt: m.updatedAt,
    };
  }
  ```
- **Logging & Telemetry:** Verified zero occurrences of plaintext tokens in application logs, audit events, HTTP query strings, or error payloads.

## 4. Audit: WP-P8-03 — Renewal & Dunning Worker

### 4.1 Automated Charge Gate Assertion
- Both `processSubscriptionRenewal` and `processDunningRetries` enforce the DEC-P8-01 gate assertion before initiating any recurring debit adapter call:
  ```ts
  assertRecurringPaymentsAvailable(gate);
  ```
- Even if a cron job or manual trigger is invoked, zero requests are sent to the payment gateway without explicit, signed capability verification.

### 4.2 Distributed Locking & Row-Level Concurrency Safety
- **Two-Tier Locking Mechanism:**
  1. *Distributed Redis Lock:* Uses `SET renewal_lock:<subId> <holderId> NX EX 300` to prevent cross-worker contention across distributed containers.
  2. *Database Row-Level Lock:* Inside the SQL transaction, queries select `subscriptions` using `FOR UPDATE SKIP LOCKED`. If another transaction holds the row, the job safely skips execution without blocking connection pools.
- **Lock Recovery:**
  - Locks auto-expire after 300 seconds (5 minutes) if a worker abruptly crashes.
  - Release uses a safe Lua script verifying lock ownership (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`).

### 4.3 Idempotency & Financial Ledger Consistency
- **Audit Remediation (FINDING-P8-H02):**
  - *Identified Gap:* In `processDunningRetries`, when a dunning attempt succeeded, the subscription was restored to `ACTIVE`, but the existing `subscriptionInvoices` record created during the failed renewal cycle remained in `FAILED` status.
  - *Correction Applied:* [`apps/api/src/modules/subscriptions/subscription-billing.service.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/subscriptions/subscription-billing.service.ts) now queries the cycle invoice and updates it:
    ```ts
    if (cycleInvoice) {
      await tx
        .update(subscriptionInvoices)
        .set({
          status: 'PAID',
          paidAt: now,
        })
        .where(eq(subscriptionInvoices.id, cycleInvoice.id));
    }
    ```
- **Invoice Deduplication:** Before creating any renewal invoice, the service checks for an existing invoice for the exact `(subscriptionId, billingCycleStart)`. If an invoice exists in `PAID` or `PENDING` status, no duplicate invoice is generated.

### 4.4 Bounded Dunning Retries & Grace Period Boundaries
- **Retry Schedule:** Day 1, Day 3, Day 5, Day 7 (Max 4 attempts).
- **Exhaustion Boundary:**
  - If `dunningAttempts >= 4` or `now > dunningGracePeriodEnd`:
    - Subscription transitions from `PAST_DUE` -> `UNPAID`.
    - Audit log recorded: `SUBSCRIPTION_DUNNING_EXHAUSTED`.
    - Learner access suspended immediately.

### 4.5 Worker Resilience & Redis Fault Tolerance
- **Audit Remediation (FINDING-P8-M02):**
  - *Identified Gap:* `SubscriptionBillingWorker.createRedisConnection()` had an uncapped `retryStrategy` that could result in infinite reconnection loops in environments where Redis was down or during tests.
  - *Correction Applied:* In [`apps/api/src/modules/subscriptions/subscription-billing.worker.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/subscriptions/subscription-billing.worker.ts), retry strategy now matches `QueueService` resilience standards:
    ```ts
    retryStrategy: (times) => {
      if (this.isClosing || env.NODE_ENV === 'test' || times > 3) {
        return null;
      }
      return Math.min(times * 150, 1500);
    }
    ```
  - Worker operates safely in standby mode without unhandled rejections if Redis is offline.
