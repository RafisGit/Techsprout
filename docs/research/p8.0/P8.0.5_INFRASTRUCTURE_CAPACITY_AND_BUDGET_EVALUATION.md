## Executive Summary & Core Verdicts

Operating an enterprise recurring billing engine on a modern cloud PaaS requires deterministic guarantees across compute availability, queue durability, ACID transaction isolation, and idempotency protection. The current TechSprout production baseline ([`render.yaml`](file:///d:/Work/2026/techsprout-main/render.yaml)) and staging environment ([`render.staging.yaml`](file:///d:/Work/2026/techsprout-main/render.staging.yaml)) operate exclusively on **Render Free Tiers**. While adequate for low-volume stateless API prototyping, **this infrastructure baseline is physically incapable of running a commercial subscription service**.

| Evaluation Dimension | Core Architectural Finding | Operational Risk | Feasibility Verdict |
|---|---|---|:---:|
| **Web Service Compute** | Render Free Web spins down after 15 minutes of inactivity; 750 free instance hours/month ceiling. | In-process BullMQ schedulers (`0 2 * * *`) fail to trigger while container is asleep; wake-up latency is 50–60s. | **INCOMPATIBLE WITH FREE TIER** (Requires always-on paid compute) |
| **PostgreSQL Database** | Render Free PostgreSQL instances are **automatically deleted after 30 days**; 1GB disk ceiling. | Complete loss of customer subscriptions, invoices, and accounting ledgers; zero automated backups or PITR. | **FATAL DEFECT ON FREE TIER** (Mandates paid managed database) |
| **Key Value / Redis** | 25MB RAM ceiling with hardcoded `maxmemoryPolicy: noeviction`; no disk persistence (AOF/RDB). | Redis returns fatal `OOM` errors on retry bursts; queue state wiped on restarts; BullMQ crashes API writes. | **ACUTE OOM & DATA LOSS RISK** (Requires persistent 256MB+ tier or DB polling) |
| **Sourced Cost Floor** | Sourced directly from official Render catalog (effective August 2026 spec-based plans). | Reconciles previously proposed $24/mo floor to **$23.00/mo base** ($7 Web + $6 Postgres + $10 Key Value). | **VERIFIED & BUDGET-FEASIBLE** |
| **Payment Correctness** | Double-charge prevention cannot rely on Redis locks alone; requires deterministic PostgreSQL ledger keys. | Stalled worker restarts could double-debit Bangladeshi payment cards without deterministic gateway transaction keys. | **ARCHITECTURALLY SOLVABLE VIA DB LEDGER** |

### Core Evaluation Verdicts:
1. **Pricing Verification Verdict: VERIFIED.** Current official Render pricing confirms that always-on compute (`0.5c-512mb` at $7.00/mo), persistent PostgreSQL (`0.1c-256mb` at $6.00/mo with 1GB included storage), and persistent Key Value (`256mb` at $10.00/mo) establish an infrastructure floor of **$23.00 / month** ($24.00 / month with ~3GB storage). If background workers are physically separated into a dedicated service (Option C), the floor is **$30.00 / month**.
2. **Capacity Feasibility Verdict: FEASIBLE ON PAID TIERS; BLOCKED ON FREE TIERS.** Workload simulations across 100, 1,000, and 10,000 active subscribers demonstrate that paid Starter tiers provide $> 85\%$ memory and connection headroom at 1,000 subscribers, whereas Free tiers suffer immediate failure due to container sleep, 30-day database auto-deletion, and zero Redis persistence.
3. **Payment-Processing Reliability Verdict: CONDITIONALLY SAFE.** Redis must be treated strictly as a transient dispatch queue. PostgreSQL **must remain the sole authoritative ledger** for subscription state, invoice sequences, payment attempts, and double-entry accounting. Generating deterministic gateway transaction IDs (`merchant_tran_id = TS-SUB-${subId}-${cycleKey}`) prior to gateway dispatch guarantees zero duplicate debits under arbitrary worker restarts.
4. **DEC-P8-04 Readiness Verdict: PENDING LEADERSHIP RATIFICATION.** All technical options, mathematical workloads, failure modes, and budget line items are fully specified. The decision remains **`PENDING`** awaiting formal budget approval from the Cloud Infrastructure Owner, DevOps Lead, and Finance Lead.
5. **Phase 8 Authorization Verdict: UNAUTHORIZED / FROZEN.** No deployment or code implementation may proceed until DEC-P8-01 through DEC-P8-05 are ratified.

#### Critical Blueprint Findings:
1. **Migration-on-Boot Hazard:** In both environments, `startCommand` couples `migrate.js` and `seed.js` directly to container startup (`render.yaml:17`). Every time a container boots, restarts, or recovers from idle spin-down, it executes DDL migrations and seed scripts. Remediation PR #1 (`fix/prod-blueprint-safety-preflight`) is a **hard prerequisite** to decouple migration execution prior to introducing Subscription Migration `0012`.
2. **In-Process Worker Coupling:** There is no dedicated background worker declared in the blueprint. All background processing is embedded in the single HTTP Web Service process.
3. **Private Network Locality:** Services communicate over Render's internal Oregon private network via environment variables populated by `fromDatabase` and `fromService`. Internal network egress is free ($0.00).

The repository currently operates three background queue/worker components in `apps/api`:

```typescript
3. TelemetryPruningWorker (apps/api/src/modules/telemetry/telemetry-pruning.worker.ts)
   - Queue Name: 'techsprout-telemetry-pruning'
   - Concurrency: 1
   - Repeatable Scheduler: PRUNING_SCHEDULER_ID = 'telemetry-pruning-nightly', CRON = '0 3 * * *' (03:00 UTC daily)
   - Watchdog: Bounded exponential watchdog (2000ms base, 30000ms max delay)
   - Lifecycle: removeOnComplete: 10, removeOnFail: false (Dead-letter retention)
```

#### Key Architectural Observations:
- **Connection Count:** Each BullMQ Queue instantiates 1 IORedis connection; each BullMQ Worker instantiates 2 connections (one general command client, one blocking `BRPOPLPUSH` client). With 3 queues/workers, `apps/api` maintains **9 persistent Redis connections** in steady-state.
- **Standby Fallback Pattern:** All workers implement a graceful standby mechanism. If Redis is down or unreachable on boot, the application does not crash; it logs a warning and enters degraded standby (`status: degraded`). Notifications fall back to synchronous in-memory dispatch ([`notification-queue.service.ts:136`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/notifications/notification-queue.service.ts#L136)).
- **Dead-Letter Accumulation Risk:** `removeOnFail: false` is configured across all queues without an age or count limit (except telemetry which limits completed jobs to 10). Failed jobs remain in the `bull:*:failed` zset indefinitely.

### 1.3 Database Connection Pooling & Health Check Architecture
- **Connection Pool:** [`drizzle.provider.ts:17`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/drizzle.provider.ts#L17) initializes `new Pool({ connectionString: env.DATABASE_URL })` using default `pg` pool settings. In `node-postgres`, the default pool capacity is **`max: 10` connections** per Node process.
- **Migration & Seed Isolation:** `runMigrations()` in `migrate.ts` and `seed.js` create their own separate, transient connection pools on startup, consuming an additional 2–5 connections during boot before terminating.
- **Health Probes:** [`health.controller.ts:30-86`](file:///d:/Work/2026/techsprout-main/apps/api/src/common/health/health.controller.ts#L30-L86) exposes:
  - `GET /api/v1/health`: Executes `SELECT 1` on PostgreSQL, `PING` on Redis, and inspects `telemetryPruningWorker.getHealthDetails()`. Returns HTTP 200 with `status: "ok"` or `status: "degraded"` (if Redis is down).
  - `GET /api/v1/health/ready`: Executes `SELECT 1` on PostgreSQL only. Returns HTTP 200 `{ ready: true }`.

#### Protocol for Preventing Double-Debits Under Worker Restarts:
A critical risk in recurring payment automation is the **orphan debit**: a worker calls `ISSLCommerzClient.chargeMandate()`, the acquiring bank deducts funds from the customer's account, but before the worker can commit `status = 'PAID'` to PostgreSQL, the Render container crashes or restarts. BullMQ re-delivers the job, and an unhardened worker charges the card a second time.

To guarantee **zero double charges**, the renewal pipeline must adhere to the following strict transactional order of operations:
1. **Deterministic Transaction Key Generation:** Before contacting SSLCommerz, the worker computes a deterministic transaction key:
   $$\text{merchant\_tran\_id} = \text{TS-SUB-}\{\text{subscriptionId}\}\text{-}\{\text{cycleYearMonth}\}\text{-ATT}\{\text{attemptNumber}\}$$
   *(Example: `TS-SUB-a1b2c3d4-202611-ATT1`)*
2. **Pre-Debit Database Record:** The worker inserts a `payments` record with `status = 'INITIATED'` and `merchant_tran_id` inside PostgreSQL with a row-level lock (`SELECT ... FOR UPDATE`).
3. **Pre-Flight Validation Query:** If a worker restarts and picks up a retried job, it first queries `payments` by `merchant_tran_id`. If found in `INITIATED` state, it **does NOT charge the gateway again**. Instead, it invokes the SSLCommerz Transaction Query API (`validator/api/merchantTransIDvalidationAPI.php`) using `merchant_tran_id` to inspect if the transaction was already captured.
   - If captured: Updates `payments.status = 'COMPLETED'`, advances `subscriptions.current_period_end`, and emits the invoice.
   - If not captured: Re-initiates the debit safely with the gateway.

### Detailed Option Profiles:

#### Option A: Minimum-Cost Managed Infrastructure (Recommended for Launch)
- **Architecture:** The REST API and BullMQ background workers (`SubscriptionBillingWorker`, `NotificationQueueService`, `TelemetryPruningWorker`) run in-process within a single Starter Web Service (`0.5c-512mb`). Supported by Starter PostgreSQL (`0.1c-256mb`) and Starter Key Value (`256mb`).
- **Cost:** **$23.00 / month** ($24.00 with disk growth).
- **Evaluation:** Highly cost-effective. Eliminates container sleep and database expiration. At 1,000 subscribers, nightly renewal batches take under 1 minute at concurrency = 5, consuming $< 25\text{MB}$ RSS. Fits well within the 512MB RAM ceiling.
- **Trade-Off:** Shared CPU/memory means heavy renewal batches could briefly add 50–100ms latency to concurrent student API requests if scheduled during daytime hours. Mitigated by scheduling renewal batches at 02:00 UTC (08:00 AM BST off-peak).

#### Option B: Durable Scheduling with PostgreSQL
- **Architecture:** Replaces BullMQ for renewal billing with PostgreSQL row-level polling using `SELECT ... FOR UPDATE SKIP LOCKED`. A Render Cron Job executes every 10 minutes (`*/10 * * * *`) via CLI command `node dist/scripts/process-renewals.js`. Redis Free (`25mb`) is retained purely for ephemeral rate limiting and entitlement caching.
- **Cost:** **$14.00 / month** ($7 Web + $6 Postgres + $1 Cron).
- **Evaluation:** Maximizes durability by keeping all job state in ACID relational tables. Completely removes Redis as a billing dependency.
- **Trade-Off:** High architectural drift. The codebase already has robust BullMQ watchdog and lifecycle infrastructure (`TelemetryPruningWorker`, `NotificationQueueService`). Introducing a second, bespoke queue engine specifically for subscriptions increases technical debt and developer cognitive load.

#### Option C: Dedicated Background Worker & Persistent Queue (Recommended for Scale)
- **Architecture:** Decouples background processing into a dedicated Render Background Worker service (`type: worker`, plan `0.5c-512mb`), leaving the Web Service to serve HTTP traffic exclusively. Both connect to Starter Postgres (`0.1c-256mb`) and Starter Key Value (`256mb`).
- **Cost:** **$30.00 / month** ($7 Web + $7 Worker + $6 Postgres + $10 Key Value).
- **Evaluation:** Enterprise-grade process isolation. Heavy renewal bursts or reconciliation scans can fully saturate the worker's CPU without degrading student video playback or checkout response times.
- **Trade-Off:** Incurs an additional $7.00/month compute cost and requires managing two separate service deployments in the Render blueprint.

### Evaluator Recommendation: Phased Evolution
- **Phase 8 Initial Staging & Production Launch (0 to 1,000 Subscribers):** Adopt **Option A ($23.00/mo)**. It minimizes operational complexity, aligns 100% with existing BullMQ patterns in `apps/api`, and operates well within physical RAM/CPU margins.
- **Growth Milestone ($\ge 1,500$ Subscribers):** Transition to **Option C ($30.00/mo)** by declaring a dedicated worker service in `render.yaml` once subscription revenue comfortably covers the +$7.00/mo increment.
