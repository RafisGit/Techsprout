## 1. Executive Recommendation

Adopt **Phase 9 — Student and Administrative Dashboards** as a focused gap-closure phase. The goal is to make existing learning and marketplace capabilities visible through secure, data-backed role dashboards, not to rewrite the LMS or expand into unrelated features.

The September 2026 senior-review product guideline defines Phase 9 as a student dashboard showing active enrollments and quiz scores, plus an administrator moderation dashboard for courses and revenue. Its exit criterion is **functional role dashboards**. TechSprout has also accumulated work packages for instructor analytics, monetization, discussions and assignments, AI tutoring, telemetry, and subscription foundations. Historical reports therefore create a risk of duplicating pages or building against code that has not yet been integrated into main.

**Recommended sequence:** (1) audit routes, APIs, schemas, tests, branch lineage and deployment evidence; (2) implement only confirmed gaps in student visibility, course moderation, and read-only financial reporting; (3) apply authorization, data-lineage, audit, accessibility, and regression gates; and (4) keep production promotion independently blocked until operational release gates are verified.

Phase 9.0 research and planning can begin now. Phase 9.1 implementation should wait until PR #4 is reviewed and merged and PR #3 is rebased onto the resulting main and passes integration gates. No paid infrastructure is proposed.

## 2. Product Requirement and Architecture Interpretation

### Product source

Source: **TechSprout School LMS — Product Research and Development Guideline, Senior Review Edition, Version 2.0, September 2026.** It identifies the Phase 9 work as Student & Admin Portals. The student dashboard scope includes enrollment overview, progress percentages, past quiz scores, and account profile management. The admin scope includes course moderation and revenue visibility; the administrator persona also needs oversight of payouts, student disputes, coupon codes, and platform analytics. The Phase 9 exit gate is functional role dashboards after core services.

The source estimates eight days for a student dashboard and twenty solo working days (or ten small-team working days) for the combined Phase 8–9 payments-and-dashboards block. These figures are historical planning references, not a current commitment or a Phase 9-only estimate. Full bilingual localization is Phase 10 and certificates are Phase 11; neither is automatically in scope here.

### Current implementation architecture

The September guideline describes a Next.js route-handler/Mongoose/MongoDB design. The active repository and P8 engineering evidence instead show a monorepo with a Next.js web application, NestJS REST API under /api/v1, shared TypeScript contracts, PostgreSQL, Drizzle migrations, and Redis-backed jobs/locks. Use the guideline as the product-behavior source while preserving the current repository and approved decisions as implementation baseline. Do not introduce MongoDB/Mongoose, a second business-logic implementation, a replacement API architecture, new cloud services, or a paid provider without a separate senior-approved ADR.

Historical phase reports are leads for investigation, not proof that every route/schema is present on current main or live in production. A passing CI run, a code branch, a previous staging report, and a production deployment are different evidence types.

## 4. Proposed Scope

### Student overview

Implement or close gaps only where the baseline audit proves they are missing or defective:
- Active and completed enrollments with a meaningful empty state.
- Progress based on persisted server-side progress and existing completion rules.
- Recent quiz results only when persisted assessment results exist.
- Safe links to resume existing courses/lessons and view results where those routes exist.
- Account summary based on authenticated identity.

### Administrator course moderation

Implement or close gaps only where missing:
- Queue of courses/review requests awaiting admin action.
- Course metadata, instructor, current review state, and decision history where appropriate.
- Approve/reject/return-for-changes only when supported by the existing domain model and approved policy.
- Required rationale where the contract demands it.
- Server-side authorization, durable audit evidence, and deterministic handling of repeated or concurrent decisions.

### Read-only revenue overview

This work package is conditional on PR #4’s ledger schema and services being integrated and audited. The senior reviewer must approve metric definitions before UI implementation. Candidate metrics, only when supported by authoritative records:
- Successful collections, separately from pending and failed payments.
- Refunds.
- Platform share and instructor share under the approved accounting policy.
- Escrow/held amounts, payable amounts, and settled payouts as distinct states.

Document each metric’s formula and source. A ledger balance is not automatically gross sales or net revenue. If the ledger dependency is not integrated, defer implementation rather than querying an unmerged schema or substituting fake data.

### Cross-cutting quality

Responsive student/admin UI; accessible primary interactions; loading, empty, error, and unavailable-data states; server/API role checks; automated service/API/contract/web regression tests; keyboard navigation, meaningful labels, contrast, and readable summaries.

### Explicitly out of scope unless separately approved

- Full BN/EN localization and translated dynamic content (Phase 10).
- Certificate generation and public verification (Phase 11).
- Live classes, native mobile apps, offline encrypted video, or DRM redesign.
- New payment gateway integration or enabling automated recurring charges.
- Rebuilding verified learning player, quizzes, instructor authoring, discussions, or assignments.
- New paid hosting/databases/SaaS services or broad infrastructure changes.
- New migrations solely for dashboard convenience before existing schemas/services are inventoried.

## 5. Work Packages and Acceptance Criteria

### WP-P9-00 — Baseline Inventory and Evidence Reconciliation

Refresh remote refs; recheck PR #3/#4, CI and main; follow P8 sequencing (human review/merge PR #4 first, then rebase PR #3 and verify effective diff/CI); inventory student/admin/instructor routes, navigation, endpoints, contracts, schemas and tests; map each requirement to files/tests/deployment evidence; compare Phase 6/7 senior reports with actual branches; record dependencies and reviewer decisions.

**Acceptance:** a route/API/data-source matrix exists; duplicate features are identified; historical reports are not treated as production proof; a signed-off gap list authorizes only missing work.

### WP-P9-01 — Student Dashboard Gap Closure

Use existing services for enrollments, progress, and recent quiz results; map statuses from existing contracts; add resume/results links only to existing routes; handle empty/loading/error states; derive learner identity from authenticated server context.

**Acceptance:**
- A student sees only their own enrollments, progress, and quiz results; cross-user requests are denied at the API boundary.
- Progress and scores match persisted records and existing calculation rules.
- Empty/loading/failure/partial-data states never fabricate values.
- Tests cover active enrollment, completed enrollment, no enrollments, and denied cross-user access.
- Existing lifetime-purchase precedence and course-completion rules remain intact.

### WP-P9-02 — Administrator Course Review Workspace

Display pending review requests; reuse existing domain transitions; enforce admin roles at the API boundary; require rationale where policy says so; record review/audit evidence; handle repeated/concurrent decisions deterministically.

**Acceptance:**
- Non-admin operations receive expected 401/403 responses.
- Decisions persist through the domain service and subsequent reads reflect them.
- Invalid transitions, simultaneous decisions, and missing required reasons are handled deterministically.
- Moderation meets existing audit conventions.
- Discussion/assignment moderation retains its separate authorization and sanitization rules.

### WP-P9-03 — Read-Only Revenue Overview

After ledger integration, obtain senior approval for definitions of collections, refunds, platform/instructor share, escrow/held, payable, and settled payout. Use existing server-side accounting/reporting services and integer minor units; do not calculate finance totals independently in React. Keep the dashboard read-only; payout, refund, ledger posting, and settlement mutation are excluded. Bound date filters, paginate details, and show unknown data as unavailable rather than zero.

**Acceptance:**
- Every metric has a written formula and authoritative source.
- Reconciliation tests match synthetic payment/refund/ledger/payout fixtures, including escrow where relevant.
- Duplicate/idempotent ledger writes cannot inflate metrics; there is no financial write endpoint in this dashboard.
- Currency and units are explicit (BDT; integer minor units internally).
- Only admins access aggregates.
- Migration 0010 is not referenced until PR #4 is merged and target schema is verified.

### WP-P9-04 — Integration, Security, Accessibility, and Regression

Extend existing tests; cover synthetic fixtures, role matrices, empty/error states and core workflows; review object-level authorization, validation, pagination and data minimization; test keyboard navigation and mobile/tablet/desktop layouts; run lint, typecheck, contracts/OpenAPI validation, migration tests, regression suite, and production builds on the exact candidate SHA.

**Acceptance:** required CI jobs pass on the reviewed head, new authorization tests pass, no P0/P1 defect remains open in scope, and the handoff distinguishes code/test readiness from deployment readiness.

## 6. Technical Approach

- **Web:** extend the existing Next.js App Router and components; do not add a competing dashboard framework.
- **API:** use existing NestJS REST controllers/domain services and shared contracts. The browser must not query PostgreSQL directly.
- **Database:** continue with PostgreSQL/Drizzle. Prefer existing tables/indexes; any change needs a documented reason, reviewed migration, test, and rollback plan.
- **Identity:** derive learner ID from authenticated server context; do not trust client-supplied user IDs for self-service data.
- **Finance:** aggregate on the server, return minimum necessary fields, and never expose payment tokens or unnecessary personal data.
- **No-cost path:** use existing tooling, CI and synthetic/local fixtures. Do not provision paid services for Phase 9.
- **Telemetry/privacy:** avoid raw learner queries, payment tokens and unnecessary personal data; respect the selected telemetry privacy decision and TELEMETRY_ENABLED=false for local development/strict-privacy deployments.

## 9. Proposed Phase 9 Exit Gate

Phase 9 is development-complete only when:
1. Senior-approved scope covers confirmed gaps and excludes duplication/deferred work.
2. Student enrollment/progress/quiz data is server-derived and matches authoritative records.
3. Course moderation is functional, protected, auditable, and uses valid domain transitions.
4. Financial metrics have approved definitions, authoritative lineage, read-only access, and reconciliation tests.
5. Empty/loading/error/unavailable states, responsive UX, and accessibility checks pass.
6. Lint, typecheck, contracts/OpenAPI, migration tests, regression suite, and production builds pass on the exact candidate SHA.
7. Handoff records completed features, verified evidence, unresolved gates, and what is not deployed.

**Development completion is not production approval.** Production promotion remains blocked until database backup and isolated restore, continuity/expiry, live migration ledger, live Render startup configuration and applicable operational gates are independently verified. P8 recurring payment remains disabled until DEC-P8-01 has written merchant-specific evidence.
