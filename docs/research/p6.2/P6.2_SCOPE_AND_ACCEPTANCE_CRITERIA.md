## 1. Scope Classification Framework

To ensure engineering focus, prevent scope creep, and protect established project invariants, all investigated capabilities are classified under one of five strict statuses:

1. **`IN SCOPE — PROPOSED`:** Essential capabilities required to deliver a complete, secure, and production-grade Instructor MVP in P6.2.
2. **`DEFERRED`:** High-value capabilities intentionally scheduled for later phases (P6.3 Learning Analytics, P6.4 Discussions/Assignments, or P7 Instructor Monetization).
3. **`OUT OF SCOPE`:** Capabilities that do not align with the product mission or introduce disproportionate complexity.
4. **`BLOCKED BY DEPENDENCY`:** Items that cannot proceed until external credentials or prerequisite infrastructure are unblocked.
5. **`REQUIRES SENIOR DECISION`:** Architectural or product forks that require institutional leadership approval before implementation.

## 3. Formal Acceptance Criteria for In-Scope MVP Capabilities

### Capability 1: Instructor Route Tree & Navigation (`/instructor/*`)
- **AC-1.1:** Any user with `role === 'instructor'` accessing `/instructor/dashboard` must see the Instructor Portal with aggregated summary metrics (total courses taught, draft count, pending reviews, total enrolled students).
- **AC-1.2:** Any user without `role === 'instructor'` or `role === 'admin'` attempting to access `/instructor/*` must be intercepted and rendered a clean `403 Forbidden` access denied view.
- **AC-1.3:** The `Header.tsx` desktop navigation and mobile drawer must dynamically render an "Instructor Portal" link if `user.role === 'instructor'`, and an "Admin Portal" link if `user.role === 'admin'`.
- **AC-1.4:** The navigation tabs in `InstructorNav` must strictly link to instructor-authorized routes (`Dashboard`, `My Courses`, `Profile`). Under no circumstances may an instructor click a navigation link that results in a 403 Forbidden error.

### Capability 2: Course Authoring & Ownership Isolation
- **AC-2.1:** On `/instructor/courses`, an instructor must see only courses where `courses.instructor_id === user.id`. Administrative superusers can see all courses.
- **AC-2.2:** When an instructor creates a new course, the backend must ignore any client-supplied `instructorId` and authoritatively bind `courses.instructorId = req.user.id`.
- **AC-2.3:** If Instructor A submits a `PATCH`, `DELETE`, or module creation request targeting a course owned by Instructor B, the request must fail with `403 FORBIDDEN: FORBIDDEN`, and an audit event `UNAUTHORIZED_RESOURCE_ACCESS_ATTEMPT` must be recorded.
- **AC-2.4:** Module, lesson, and quiz management inside `/instructor/courses/[id]` must retain full editing capabilities while the course status is `DRAFT`.

### Capability 3: Course Review State Machine & Administrative Queue
- **AC-3.1:** A course in `DRAFT` status can be submitted for review via `POST /api/v1/instructor/courses/:id/submit-for-review`.
- **AC-3.2:** If the course has zero modules, zero lessons, or missing thumbnail media, submission must fail with `400 BAD_REQUEST: INCOMPLETE_CURRICULUM` detailing missing items.
- **AC-3.3:** Successful submission must transition `courses.status` to `'IN_REVIEW'`, insert a record in `course_review_requests` with `status = 'PENDING'`, and record an outbox event `CourseSubmittedForReview`.
- **AC-3.4:** While in `'IN_REVIEW'` status, all content editing endpoints (`PATCH /admin/courses/:id`, module/lesson mutations) must reject modifications with `400 BAD_REQUEST: COURSE_LOCKED_FOR_REVIEW`.
- **AC-3.5:** Administrators viewing `/admin/courses` must see an "In Review" filter badge. On course detail, administrators must have "Approve Publication" and "Reject Review" action buttons.
- **AC-3.6:** Rejecting a review requires non-empty feedback notes. Rejection transitions course status back to `'DRAFT'`, updates review request to `'REJECTED'`, and emits `CourseReviewRejected`.
- **AC-3.7:** Approving a review transitions course status to `'PUBLISHED'`, sets `courses.publishedAt = NOW()`, updates review request to `'APPROVED'`, and emits `CourseReviewApproved`.

### Capability 4: Student Roster & Progress Visibility
- **AC-4.1:** Navigating to `/instructor/courses/[id]/learners` must display a paginated list of students enrolled in that specific course.
- **AC-4.2:** Each student row must display: student name, email, enrollment date, enrollment status (`ACTIVE`, `COMPLETED`, `CANCELLED`), and completion progress percentage (`0%` to `100%`).
- **AC-4.3:** If the course has zero enrollments, an informative empty state must be rendered: *"No students have enrolled in this course yet."*
- **AC-4.4:** An instructor attempting to view the roster of a course they do not own must receive `403 FORBIDDEN`.
- **AC-4.5:** The roster page must include a "Download CSV" button that generates an RFC-4180 compliant CSV file containing the filtered learner list.

### Capability 5: Instructor Profile & Public Bio
- **AC-5.1:** Educators can navigate to `/instructor/profile` to view and update their headline, biographical summary, academic credentials, and social links (LinkedIn, GitHub, Website).
- **AC-5.2:** Profile updates must be validated using Zod (URL format checks, bio character limits max 2,000 chars).
- **AC-5.3:** The public course details page (`/courses/[slug]`) must render the instructor's headline, bio summary, and verified credentials alongside their name.

## 4. Explicit Non-Goals for P6.2

To protect delivery velocity and system integrity, the following items are strictly declared **NON-GOALS** for P6.2:

1. **No Changes to Payment or Order Engine:** P6.2 will not alter checkout flows, SSLCommerz integrations, invoice PDF generation, or refund processing.
2. **No Instructor Revenue Payouts:** Monetization, payouts, bank transfers, and revenue splitting belong to Phase P7.
3. **No Student Assignment Submission Engine:** Homework uploads, grading rubrics, and discussion boards belong to Phase P6.4.
4. **No Advanced Predictive Analytics:** Machine learning dropout predictions, cohort retention matrices, and video heatmaps belong to Phase P6.3.
5. **No Co-Instructor Sharing:** Multi-tenancy course collaboration is deferred to P7. Single instructor ownership per course remains invariant in P6.2.
