## 2. Recommended First Implementation Milestone: Phase 7.1

### Why Phase 7.1 (Learning Telemetry) Must Precede All Other Tracks:
1. **Architectural Prerequisite for AI Tutoring (P7.2):** Intelligent tutoring and proactive student interventions require granular telemetry (pause patterns, rewind hotspots, repeat quiz failures) to detect where learners struggle. Building AI models without underlying interaction data produces an ungrounded system.
2. **Immediate Remediation of Audited Vulnerabilities:** The audit confirmed that `VideoPlayer.tsx` currently overwrites progress in place and loses exit timestamps when browser tabs close. Phase 7.1 immediately delivers reliable `sendBeacon` transport and time-series logging.
3. **Zero Financial & Operational Risk:** Telemetry is append-only pedagogical data. It carries zero risk to customer payments, student credentials, or invoice ledgers, making it the safest foundation to deploy.
4. **Fast Time-to-Value:** Phase 7.1 is estimated at **6.5 – 9.5 engineering days**, enabling an agile, verified staging and production release within two standard sprint cycles.

## 3. Detailed Work Package Breakdown: Phase 7.1

### WP-P7.1-01: Telemetry Schema, Ingestion Engine & Data Retention
- **Deliverables:**
  - Drizzle schema `apps/api/src/database/schema/telemetry.ts` defining `learning_events` table.
  - Migration `0009_telemetry_foundation.sql` with non-concurrent B-tree indexes.
  - Shared contracts & Zod DTOs in `@techsprout/contracts` (`IngestTelemetryBatchDto`, `LearningEventDto`).
  - Ingestion controller `POST /api/v1/learning/events` and `POST /api/v1/learning/events/beacon`.
  - Enrollment guard validating authenticated student enrollment in `course_id`.
  - Rate limiting via `@Throttle({ default: { limit: 120, ttl: 60000 } })`.
  - Daily BullMQ pruning worker executing chunked deletion (1,000 rows/batch) of `VIDEO_CHECKPOINT` records older than 90 days.
- **Estimated Effort:** 3.0 – 4.5 Engineering Days
- **Assignee:** Backend / Database Lead
- **Risk / Uncertainty:** Low. Builds directly on established Drizzle / NestJS patterns.

### WP-P7.1-02: Client Telemetry Hook, Beacon Transport & Retention Visualizations
- **Deliverables:**
  - Client telemetry hook `apps/web/src/hooks/useLearningTelemetry.ts` with 60s throttle.
  - Refactored `apps/web/src/components/learning/VideoPlayer.tsx` dispatching `VIDEO_STARTED`, `VIDEO_PAUSED`, `VIDEO_SEEKED`, `VIDEO_CHECKPOINT`, and `VIDEO_COMPLETED`.
  - Tab unload / page-exit transport using `navigator.sendBeacon()` with `fetch(..., { keepalive: true })` fallback.
  - Backend analytics aggregation service `getCourseVideoRetention(courseId, lessonId)`.
  - Accessible SVG retention curve chart and drop-off hotspot list integrated into `/instructor/courses/[id]/analytics`.
- **Estimated Effort:** 2.5 – 3.5 Engineering Days
- **Assignee:** Full-Stack Web Engineer
- **Risk / Uncertainty:** Low. Leverages existing P6.3 SVG chart architecture.

### WP-P7.1-03: Security Hardening, Ingestion Load Testing & Release Gate
- **Deliverables:**
  - Unit and integration Vitest suites for telemetry schema, ingestion validation, and pruning logic.
  - Multi-tenant IDOR penetration suite (verifying students cannot inject telemetry for un-enrolled courses).
  - Telemetry load test verifying ingestion of 500 events/second with $< 50\text{ms}$ response latency.
  - Staging deployment verification and formal P7.1 release gate report.
- **Estimated Effort:** 1.5 – 2.5 Engineering Days
- **Assignee:** QA Lead / DevOps
- **Risk / Uncertainty:** Medium. Depends on Render staging database performance under load.

## 5. Comprehensive Test Strategy & Acceptance Criteria

### 5.1 Automated Testing Matrix
1. **Unit Tests (Vitest):**
   - Telemetry DTO validation (boundary checks on timestamps, negative seek seconds, duration overflows).
   - Event categorization and metadata parsing.
2. **Integration Tests (PostgreSQL):**
   - `learning_events` row insertion and composite index utilization.
   - Batch ingestion endpoint handling arrays of 1 to 20 events atomically.
   - 90-day pruning query executing correctly without deleting milestone records.
3. **Security & RBAC Penetration Tests:**
   - Unauthenticated access to `/api/v1/learning/events` returns HTTP 401.
   - Enrolled student in Course A attempting to submit telemetry for Course B returns HTTP 403.
   - Instructor attempting to query retention curves for another instructor's course returns HTTP 403.
4. **Load & Reliability Tests:**
   - Simulated concurrent playback from 100 virtual learners dispatching 60s heartbeats.
   - Zero database connection pool timeouts on PostgreSQL 16.

### 5.2 Measurable Acceptance Criteria (Phase 7.1 Gate)
- [ ] `POST /api/v1/learning/events` responds with HTTP 200/202 in $< 50\text{ms}$ under standard load.
- [ ] Requests from unauthenticated callers are rejected with HTTP 401.
- [ ] Requests with invalid course enrollment are rejected with HTTP 403.
- [ ] Client `VideoPlayer.tsx` dispatches $\le 1$ heartbeat per 60 seconds of steady-state playback.
- [ ] Tab closure dispatches exit beacon reliably via `navigator.sendBeacon()`.
- [ ] Retention curve endpoint aggregates 10% interval distributions in $< 100\text{ms}$.
- [ ] Scheduled BullMQ pruning worker deletes only `VIDEO_CHECKPOINT` records older than 90 days.
- [ ] Zero regression across existing 1,507 automated monorepo tests.

### Rollback Strategy for Migration 0009:
- If Migration 0009 fails or degrades PostgreSQL performance:
  1. Revert application container to previous release commit (`491b0d055f14a84bfcce45c0576c685f1017d661`).
  2. Execute rollback SQL:
     ```sql
     DROP TABLE IF EXISTS learning_events CASCADE;
     DELETE FROM drizzle.__drizzle_migrations WHERE tag = '0009_telemetry_foundation';
     ```
  3. Because `learning_events` is an isolated append-only table, rolling back does NOT impact existing core transactional tables (`users`, `courses`, `enrollments`, `orders`, `payments`).
