## 1. Executive Summary

This architecture review establishes the technical blueprints, data integrity invariants, infrastructure trade-offs, and operational risk boundaries for the candidate tracks of Phase 7.

In accordance with strict system safety guidelines:
1. **Core Payment Invariant:** The existing single-merchant SSLCommerz customer checkout model is preserved 100%. No direct customer-to-instructor routing is introduced.
2. **Infrastructure Realism:** A Render paid plan upgrade is evaluated objectively against zero-cost alternatives; cost figures are recorded as non-binding estimates.
3. **Observability Continuity:** The accepted operational limitation `WVR-P6.3-CACHE-01` (Render Free shell restriction) is accounted for in all queue and cache designs.

### Track 1: Append-Only Learning Telemetry (`learning_events`)

#### 1.1 Relational Schema Design & Indexing Strategy
To prevent write amplification while providing rapid query speeds for course retention curves, the schema isolates event data from transactional progress:

```sql
-- Migration 0009: learning_events foundation
CREATE TABLE learning_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    course_id UUID NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
    module_id UUID REFERENCES modules(id) ON DELETE SET NULL,
    lesson_id UUID REFERENCES lessons(id) ON DELETE SET NULL,
    event_type VARCHAR(50) NOT NULL,
    -- Allowed types: 'COURSE_OPENED', 'LESSON_STARTED', 'VIDEO_CHECKPOINT', 
    -- 'VIDEO_SEEKED', 'VIDEO_PAUSED', 'LESSON_COMPLETED', 'QUIZ_ATTEMPTED'
    metadata JSONB DEFAULT '{}'::jsonb NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Compound Index for Course-Level Analytical Queries:
CREATE INDEX learning_events_course_type_occurred_idx 
    ON learning_events (course_id, event_type, occurred_at DESC);

-- Compound Index for Lesson-Level Drop-Off Heatmaps:
CREATE INDEX learning_events_lesson_type_idx 
    ON learning_events (lesson_id, event_type);

-- User-Centric Streak & Activity Index:
CREATE INDEX learning_events_user_occurred_idx 
    ON learning_events (user_id, occurred_at DESC);
```

#### 1.2 Ingestion Pipeline & Buffering Trade-Offs
Three ingestion architectures were evaluated against TechSprout's Render infrastructure:

| Ingestion Architecture | Mechanism | Render Free Viability | Render Starter Viability | Latency & Contention Profile |
|---|---|:---:|:---:|---|
| **Option A: Direct PostgreSQL INSERT** | Synchronous single-row insert inside endpoint. | **Viable with connection pool (pg 8.13)** | Viable | High write lock overhead under concurrent load; ~25ms API response. |
| **Option B: BullMQ Telemetry Buffer** | Redis queue buffers events; worker flushes in micro-batches (50–100 rows). | **HIGH RISK: 25MB Redis RAM limit + noeviction** | **Recommended ($10/mo Redis)** | Decoupled HTTP 202 Accepted (<5ms); 90% reduction in DB write locks. |
| **Option C: In-Memory Node.js Buffer** | In-process array buffers events; flushes every 5s or 100 items. | **Viable (Zero Redis memory used)** | Viable | Vulnerable to 5-second telemetry loss on unexpected container restart. |

**Architectural Recommendation:**  
- **Phase 7.1 MVP (Zero-Cost Baseline):** Option A (Direct PostgreSQL INSERT) with strict client throttling (60s) and batch ingestion endpoints (`events: LearningEventDto[]`, max 20 per request).
- **Production Scale Option (Post-Upgrade):** Transition to Option B (BullMQ Micro-Batching) once Render Redis is upgraded beyond the 25MB limit.

#### 1.3 Authorization & Abuse Prevention Boundaries
1. **Enrollment Boundary:** Telemetry ingestion requires active authentication (`JwtAuthGuard`). The service validates that the authenticated student possesses an active enrollment in `course_id`. Requests from non-enrolled users are rejected with HTTP 403 Forbidden.
2. **Payload Sanitization:** Metadata JSONB is parsed via Zod to strip unrecognized keys, restricting payload size to $\le 2\text{ KB}$ per event.
3. **Ingestion Throttling:** Endpoint is rate-limited via `@Throttle({ default: { limit: 120, ttl: 60000 } })` (max 120 events/min per user).

#### 1.4 Retention & Pruning Lifecycle
To prevent unbounded PostgreSQL storage growth on Render:
- Granular `VIDEO_CHECKPOINT` rows are automatically deleted after **90 days**.
- Pedagogical milestones (`COURSE_OPENED`, `LESSON_STARTED`, `LESSON_COMPLETED`, `QUIZ_ATTEMPTED`) are retained **permanently**.
- **Pruning Worker Invariant:** The pruning job executes via BullMQ daily at 03:00 UTC using chunked batch deletion:
  ```sql
  DELETE FROM learning_events 
  WHERE id IN (
      SELECT id FROM learning_events 
      WHERE event_type = 'VIDEO_CHECKPOINT' 
        AND occurred_at < NOW() - INTERVAL '90 days' 
      LIMIT 1000
  );
  ```
  Iterating in chunks of 1,000 prevents long exclusive locks on the `learning_events` table.

### Track 2: Client Telemetry & Video Retention Analytics

#### 2.1 Client Player Enhancements (`apps/web`)
- **Hook Integration:** A reusable React hook `useLearningTelemetry` replaces ad-hoc time updates in [`VideoPlayer.tsx`](file:///d:/Work/2026/techsprout-main/apps/web/src/components/learning/VideoPlayer.tsx).
- **Throttling Invariant:** Steady-state playback heartbeats are dispatched at a fixed maximum frequency of **once every 60 seconds**.
- **Discrete Event Capturing:**
  - `VIDEO_PAUSED`: Records timestamp and current position.
  - `VIDEO_SEEKED`: Records `fromSeconds`, `toSeconds`, and seek delta (identifying student rewinds vs skips).
  - `VIDEO_COMPLETED`: Records final watch milestone.
- **Reliable Page Exit Handler:**
  To solve the unmount failure gap identified in the audit (`VideoPlayer.tsx:L131`), tab closures and page transitions trigger:
  ```typescript
  if (navigator.sendBeacon) {
    const blob = new Blob([JSON.stringify(exitEvent)], { type: 'application/json' });
    navigator.sendBeacon('/api/v1/learning/events/beacon', blob);
  } else {
    fetch('/api/v1/learning/events', {
      method: 'POST',
      body: JSON.stringify(exitEvent),
      keepalive: true,
      headers: { 'Content-Type': 'application/json' },
    });
  }
  ```

#### 2.2 Retention Analytics Computation
- **Retention Curve Formulation:** Computes learner survival across 10 decile intervals ($0\%, 10\%, \dots, 100\%$) of video duration:
  $$\text{Interval Retention \%} = \frac{\text{Unique Learners Watching Interval } i}{\text{Total Learners Who Started Lesson}} \times 100$$
- **Rewind Hotspot Algorithm:** Identifies 15-second clusters where backward seek frequency ($\Delta t < 0$) exceeds 2 standard deviations above the lecture mean, highlighting conceptually difficult segments.
- **UI Presentation:** Rendered using accessible zero-dependency SVG chart components matching the Turbopack / React 19 standards established in P6.3.

### Track 3: AI Tutoring & Contextual Learning

#### 3.1 Course Context Extraction Pipeline
1. **Source Content Aggregation:** Extracts lesson text summaries, structured syllabus markdown, instructor lecture notes, and video audio transcripts.
2. **Transcript Generation:** Video audio streams processed through cloud speech-to-text or Cloudinary automatic transcription hooks.
3. **Chunking & Token Management:** Documents chunked into 500-token overlapping blocks (100-token overlap) tagged with `course_id`, `module_id`, and `lesson_id`.

#### 3.2 Vector Embedding Storage Trade-Offs

| Vector Storage Approach | Advantages | Disadvantages | Render Free Feasibility |
|---|---|---|:---:|
| **Option A: PostgreSQL `pgvector`** | Keeps data within Render PostgreSQL; single transactional tier; joins with `courses`. | High RAM usage; requires `vector` extension support on Render; HNSW index memory overhead. | **Requires Verification** (Plan dependent) |
| **Option B: Managed SaaS (Pinecone / Qdrant)** | Serverless; zero load on Render DB; instant semantic search. | Third-party dependency; separate API keys; cross-system sync complexity. | **High (Free tier available)** |
| **Option C: Hybrid Full-Text Search (`tsvector`)** | 100% supported on PostgreSQL 16; zero extra plugins or cost. | Keyword-based rather than semantic; misses conversational paraphrasing. | **100% Viable** |

**Architectural Recommendation:**  
Evaluate `pgvector` availability on Render during P7.2 research. If unobservable or resource-prohibitive on Render Free/Starter, use Option C (PostgreSQL full-text search) as Phase 1 baseline or a serverless embedding index.

#### 3.3 Guardrails, Grounding & Safety Boundaries
- **Strict Grounding Prompt:** The AI tutor system prompt forbids answering out-of-domain queries. If the answer cannot be retrieved from syllabus context chunks with cosine similarity $\ge 0.75$, the model declares: *"This topic is not covered in your enrolled course materials. Please consult your instructor in the course forum."*
- **Authorization Boundary:** A student cannot query the AI tutor for a course unless `enrollments.status = 'ACTIVE'` for that specific user.
- **Cost Runaway Defense:** Hard throttled to 10 queries per student per hour.

### Track 4: Instructor Monetization & Marketplace Ledger

#### 4.1 Preservation of Existing Payment & Gateway Invariants
- **Non-Negotiable Invariant:** TechSprout maintains its **single-merchant SSLCommerz checkout model**. All student checkout transactions route exclusively through the institutional merchant account.
- **Zero Real-Time Gateways:** SSLCommerz does not support programmatic multi-party split payments in Bangladesh. TechSprout will NOT attempt split gateway routing.
- **Minor Units Precision:** All ledger balances, transaction amounts, and payouts are calculated and stored in **integer minor units (poisha/cents)**. Floating-point arithmetic is strictly forbidden.

#### 4.2 Double-Entry Accounting Ledger Design
The financial model uses an append-only double-entry ledger where money cannot be created or destroyed:

```sql
-- Migration 0010: instructor monetization foundation
CREATE TABLE instructor_wallets (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    instructor_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    balance_cents BIGINT NOT NULL DEFAULT 0,
    pending_balance_cents BIGINT NOT NULL DEFAULT 0,
    lifetime_earnings_cents BIGINT NOT NULL DEFAULT 0,
    currency VARCHAR(3) NOT NULL DEFAULT 'BDT',
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT instructor_wallet_user_uq UNIQUE (instructor_id),
    CONSTRAINT positive_balance_check CHECK (balance_cents >= 0),
    CONSTRAINT positive_pending_check CHECK (pending_balance_cents >= 0)
);

CREATE TYPE ledger_entry_type AS ENUM (
    'CREDIT_ENROLLMENT',      -- Earned share from student purchase
    'DEBIT_PAYOUT',           -- Disbursed to instructor bank/MFS
    'DEBIT_REFUND_CLAWBACK',  -- Deducted due to student refund
    'ESCROW_SETTLED',         -- Moved from pending to available
    'ADJUSTMENT'              -- Administrative audit correction
);

CREATE TABLE wallet_ledger_entries (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    wallet_id UUID NOT NULL REFERENCES instructor_wallets(id) ON DELETE RESTRICT,
    entry_type ledger_entry_type NOT NULL,
    amount_cents BIGINT NOT NULL,
    balance_after_cents BIGINT NOT NULL,
    reference_type VARCHAR(50) NOT NULL, -- 'ORDER_ITEM', 'PAYOUT_REQUEST', 'REFUND'
    reference_id UUID NOT NULL,
    description TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX wallet_ledger_wallet_idx ON wallet_ledger_entries (wallet_id, created_at DESC);
```

#### 4.3 Settlement Rules & Escrow Hold Period
1. **Split Allocation:** When an order is paid (`OrderPaid` domain event), the platform fee (e.g. 20%) is deducted, and the instructor's net share (80%) is credited to `pending_balance_cents`.
2. **14-Day Refund Window (Escrow):** Funds remain in `pending_balance_cents` for 14 calendar days (matching the institutional refund policy).
3. **Automated Settlement:** A scheduled worker releases funds from `pending_balance_cents` to `balance_cents` on Day 15 if no refund request was initiated.
4. **Refund Clawback:** If a refund is processed during the 14-day window, the pending credit is reversed without affecting available balance. If refunded post-settlement, a debit is recorded against available balance.

#### 4.4 Withdrawal Requests & Administrative Controls
- Instructors submit withdrawal requests via `POST /api/v1/instructor/payouts` specifying amount and MFS destination (bKash, Nagad, or Bank Wire).
- The requested amount is immediately debited from available balance and placed in `in_flight` hold.
- Platform administrators review and approve payouts through `/admin/payouts`.
- Automated notification sent via P6.1 notification engine when payout is marked `SETTLED`.

## 3. Infrastructure Limits, Cost Alternatives & Monitoring

### 3.1 Render Cloud Infrastructure Matrix

| Cloud Resource | Render Free Plan (Current) | Render Starter Upgrade (Candidate) | Technical Impact on Phase 7 |
|---|---|---|---|
| **API Compute** | Free ($0/mo)<br>Spins down after 15m idle;<br>No container shell access. | **Starter (~$7/mo)**<br>Always-on instance;<br>Full web terminal access. | Free tier causes dropped beacons on cold start; Starter guarantees 24/7 worker uptime and closes `WVR-P6.3-CACHE-01`. |
| **Managed Redis** | Free ($0/mo)<br>25 MB RAM limit;<br>`maxmemory: noeviction`. | **Starter (~$10/mo)**<br>256 MB+ RAM;<br>Configurable eviction. | Free tier cannot buffer high-volume telemetry without OOM risk. Requires direct Postgres ingestion or Starter upgrade. |
| **PostgreSQL 16** | Free ($0/mo)<br>1 GB storage limit;<br>50 max connections. | **Starter (~$7/mo)**<br>Persistent disk;<br>Higher connection pool. | Free tier requires strict 90-day pruning to prevent disk exhaustion. |
| **Total Cost Estimate** | **$0 / month** | **~$7 to $24 / month** | *All figures are non-binding estimates based on public cloud pricing.* |

### 3.2 Zero-Cost Alternative Feasibility Assessment
Can Phase 7 execute safely without paid infrastructure upgrades?
- **Yes, for Phase 7.1 Telemetry MVP**, under these strict design constraints:
  1. Use **Option A (Direct PostgreSQL INSERT)** with connection pooling rather than Redis queue buffering.
  2. Enforce a **60-second client throttle** on playback heartbeats.
  3. Implement **90-day pruning** to keep `learning_events` table under 200,000 rows (~50 MB disk).
  4. Accept that cold starts (15-min idle) may delay initial telemetry dispatches by up to 50 seconds.
- **No, for Production Scale / Commercial Launch:** An upgrade to Render Starter compute ($7/mo) is necessary to ensure continuous BullMQ background execution.

## 5. Security & Operational Risk Register

| Risk ID | Threat / Failure Scenario | Severity | Likelihood | Concrete Mitigation Strategy |
|---|---|:---:|:---:|---|
| **RSK-P7-01** | Database write exhaustion from concurrent video heartbeats | **HIGH** | **HIGH** | 60s client-side throttle; batch payload API; connection pooling; 90-day pruning cron. |
| **RSK-P7-02** | Redis Out-Of-Memory (OOM) crash on Render Free plan (25MB limit) | **HIGH** | **MED** | Bypass Redis for telemetry in MVP; keep telemetry queues off Free Redis; strict `maxmemory` monitoring. |
