## 3. Reconciled Memory Accounting Audit

### 3.1 Discrepancy Identification in Previous Draft
The preceding draft report contained an internal mathematical inconsistency:
- It listed: Base OS/Engine = **42 MB**, `shared_buffers` = **64 MB**, Connections = **55 MB**, and `maintenance_work_mem` = **32 MB or 64 MB**.
- However, it reported the sums as **153 MB** (at 32 MB) and **185 MB** (at 64 MB).
- **Discrepancy Cause:** The calculation script used an idle connection baseline ($10 \times 1.5\text{ MB} = \mathbf{15.0\text{ MB}}$), but the markdown text erroneously labeled the connection row as `55.0 MB` (which included 40 MB of active `work_mem`).
  - Correct sum with 15 MB idle connections: $42 + 64 + 15 + 32 = \mathbf{153.0\text{ MB}}$, and $42 + 64 + 15 + 64 = \mathbf{185.0\text{ MB}}$.
  - Correct sum with 55 MB active connections: $42 + 64 + 55 + 32 = \mathbf{193.0\text{ MB}}$, and $42 + 64 + 55 + 64 = \mathbf{225.0\text{ MB}}$.

### 3.2 Formal Reconciled Formula & Term Breakdown
Total PostgreSQL resident memory is modeled by the following component formula:

$$\text{RAM}_{\text{total}} = \text{RAM}_{\text{OS\_base}} + \text{RAM}_{\text{shared\_buffers}} + \text{RAM}_{\text{connections}} + \text{RAM}_{\text{maintenance}}$$

```text
1. RAM_OS_base = 42.0 MB
   - Evidence: PostgreSQL master postmaster process (~10 MB), background writer, checkpointer,
     WAL writer, autovacuum launcher (~20 MB), and OS kernel page tables / network socket buffers (~12 MB).

2. RAM_shared_buffers = 64.0 MB
   - Evidence: PostgreSQL postgresql.conf parameter set to 64MB (25% of 256 MB container RAM).
     Fixed shared memory segment mapped by all backends.

3. RAM_connections = 15.0 MB (Idle) to 55.0 MB (Peak Concurrent Queries)
   - Component A (Backend Base Memory): 10 connections * 1.5 MB/process = 15.0 MB.
     Each connection spawns a dedicated OS process with private memory (stack, catalog cache, libpq).
   - Component B (Active Query work_mem): 10 connections * 4.0 MB work_mem = 40.0 MB.
     work_mem is allocated dynamically during active in-flight sorts, hashes, or vector distance evaluations.
   - When connections are idle: RAM_connections = 15.0 MB.
   - When all 10 connections execute concurrent active queries: RAM_connections = 15.0 + 40.0 = 55.0 MB.

4. RAM_maintenance = 32.0 MB or 64.0 MB (during CREATE INDEX ... USING hnsw)
   - Allocated by the maintenance worker process during HNSW graph construction.
   - 32 MB: Minimum feasible setting in PostgreSQL (high risk of spilling graph construction to disk).
   - 64 MB: Official recommended setting by pgvector authors to prevent HNSW build failure.
```

### 3.3 Assumptions & Limitations of the Scenario Model
To ensure complete technical precision, the scenario model's assumptions and operational boundaries are explicitly detailed:
1. **Multiple `work_mem` Allocations per Query Plan:** In PostgreSQL query execution, `work_mem` is not a single allocation per connection or per query; rather, it is allocated separately for each operational plan node requiring sorting, hash tables (e.g., hash joins, hash aggregates), or bitmap operations. A single complex query with joins and sorts can allocate `work_mem` multiple times concurrently. Consequently, modeling 10 active connections at $10 \times 4.0\text{ MB} = 40.0\text{ MB}$ represents an optimistic lower bound for active queries. Multi-node query plans under real traffic would consume considerably more heap memory.
2. **Dynamic Extension Heap Allocations:** `pgvector` allocates internal heap structures (such as `hnsw.ef_search` candidate priority queues, vector distance computation scratch buffers, and SIMD scratchpads) within backend process memory. These dynamic allocations are private to each backend and are not constrained by `shared_buffers`.
3. **Index Build Maintenance Memory Spilling:** Modeling `maintenance_work_mem = 32 MB` represents a lower-bound constraint. While it reduces nominal RAM usage, pgvector documentation recommends a minimum of 64 MB for HNSW graph creation on multidimensional embeddings. In practice, 32 MB risks spilling intermediate graph construction structures to disk or aborting the build on larger corpora.
4. **Operating System Page Cache & Fragmentation:** The formula estimates process resident set size (RSS) and shared buffers, but does not simulate OS page cache churn, socket buffers under burst network concurrency, or memory fragmentation in the process heap allocator.
5. **Absence of In-Database Experimental Verification:** Because no real pgvector PoC executed in a live database, all memory figures in this report are analytical scenario projections. Actual pgvector memory usage, concurrency overhead, and container OOM safety remain **UNVERIFIED**.
6. **Scope of Memory Gate Conclusion:** This analysis does **not** claim that every possible pgvector configuration has been proven to fail the memory gate. For instance, a dedicated maintenance window with `maintenance_work_mem = 32 MB` and zero concurrent client connections is mathematically modeled to fit at 142.5 MB. Rather, the model demonstrates that under active concurrency or standard recommended 64 MB build settings, the 179.2 MB ceiling is exceeded.

### 3.5 Memory Audit Conclusion
- **64 MB Maintenance Scenarios Exceed Ceiling:** Under the pgvector recommended index-build configuration (`maintenance_work_mem = 64 MB`), total resident RAM is modeled at **185.0 MB** during idle connections and **225.0 MB** during active concurrency. Both scenarios exceed the 179.2 MB ceiling.
- **32 MB Active-Concurrency Scenario Exceeds Ceiling:** When active client queries coincide with an index build under `maintenance_work_mem = 32 MB`, total RAM reaches **193.0 MB**, exceeding the 179.2 MB ceiling.
- **32 MB Isolated/Idle Scenarios Estimated to Fit (Unverified):** The modeled 32 MB isolated build (142.5 MB) and 32 MB idle-connection build (153.0 MB) are mathematically estimated to fit within the 179.2 MB ceiling, but remain **NOT experimentally verified in-database**.
- **Not All Configurations Fail:** The audit does not claim that every conceivable pgvector configuration fails the memory gate; rather, under active client load or recommended maintenance parameters, the 179.2 MB limit is breached.
- **Unverified Status:** Actual pgvector memory usage, allocator overhead, and container OOM safety remain **UNVERIFIED** due to the absence of an empirical in-database extension benchmark.

### 4.2 Critical Findings from Modeled Evaluation
1. **The Subword Fragmentation Flaw on Misspellings:**  
   Pure dense semantic models tokenize corrupt input words into subwords (`dokker` $\rightarrow$ `_dok`, `ker`). This causes embedding vectors to drift into arbitrary semantic regions, dropping Misspelling NDCG@5 to **0.5858** (compared to **0.7890** achieved by lexical `pg_trgm` in Configuration D).
2. **Pure Vector Does Not Meet the 0.85 Recall Target:**  
   In offline simulation, pure dense embeddings achieved a modeled Recall@5 of only **0.6266** (well below the mandatory **$\ge 0.85$** threshold). Dense similarity ranks conceptually related lessons higher, but does not guarantee all 4–5 curriculum prerequisites appear in the top 5 results.
3. **Lexical Config C Comparison:**  
   In the preceding lexical benchmark, Configuration C achieved Recall@5 of **0.7448** (failing the $\ge 0.85$ gate) with NDCG@5 of **0.8863**. Neither lexical search nor offline simulated vector search satisfies the complete acceptance criteria.
4. **Quantization Reality:**  
   `halfvec(384)` (16-bit float) is supported in `pgvector 0.7.0+` and halves on-disk storage from 327 kB to 177 kB. However, scalar INT8 quantization is not natively supported in standard released pgvector versions.
