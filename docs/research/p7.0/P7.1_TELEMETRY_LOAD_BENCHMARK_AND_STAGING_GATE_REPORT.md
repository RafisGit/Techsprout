### Explicitly Accepted Best-Effort Telemetry Limitations
In accordance with senior architectural decisions (`DEC-P7-01`, `DEC-P7-02`, and `ADR-P7-001`), the telemetry subsystem is formally established as **purely observational** and operates under the following confirmed best-effort boundaries:

1. **Non-Atomic LocalStorage Fallback:**  
   `localStorage` timestamp storage (`ts_disp_<resourceId>`) is a best-effort coordination heuristic for same-origin tabs in the same browser profile when the Web Locks API (`navigator.locks`) is unavailable. It is not an atomic mutual exclusion lock; simultaneous dispatches occurring at the exact same millisecond before either tab writes to storage can race.
2. **Cross-Device & Cross-Profile Isolation:**  
   Client coordination cannot synchronize across separate physical devices (e.g., student phone vs. laptop), incognito/private sessions, or distinct browser profiles. The server rate limit remains the sole authoritative arbiter.
3. **Server Rate-Limit Supremacy:**  
   Terminal exit beacons (`pagehide`, `beforeunload`, unmount) are not exempt from backend rate limits (2 requests per 60s per user/lesson). If a user rapidly opens/closes multiple lessons or tabs within 60 seconds, excess requests will receive HTTP 429 (`RATE_LIMIT_EXCEEDED`).
4. **Process Termination & Overflow Loss:**  
   In-memory events buffered in `queueRef` are lost during abrupt process termination (OS kill, out-of-memory browser termination, battery failure) before unload events fire. When queue overflow exceeds capacity (50 events), non-essential playback events are shed; dropped lifecycle markers emit diagnostic warnings but cannot be guaranteed delivery.
5. **SendBeacon Queue Acceptance vs. Persistence:**  
   A return value of `true` from `navigator.sendBeacon()` indicates only that the user agent scheduled the HTTP POST request in its networking queue; it does not guarantee delivery, network completion, or server database persistence.

> [!IMPORTANT]
> Guaranteed or lossless telemetry delivery is not claimed. Telemetry is purely observational and analytical; it does not modify course progress completion, certificates, or financial ledgers.

## 4. Review of Concurrent Exit Beacon Test Coverage

A rigorous inspection of test `2.1 should process 20 concurrent beacon requests with p95 latency < 250ms and 100% success` in [`telemetry-load-benchmark.spec.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/test/telemetry-load-benchmark.spec.ts#L472-L527) establishes the exact scope of what was tested:

```typescript
const beaconStudentsCount = 20;
const beaconBatches = studentIds.slice(0, beaconStudentsCount).map(() => ({
  events: [ ... ],
}));

const responses = await Promise.all(
  beaconBatches.map(async (batch, idx) => {
    return request(app.getHttpServer())
      .post('/api/v1/learning/events/beacon')

      .set('Content-Type', 'text/plain;charset=UTF-8')
      .send(JSON.stringify(batch));
  })

```

### 4.2 Findings on Test Coverage
1. **Distinct Authenticated Users Exercised:**  
   The benchmark dispatches 20 requests using `studentCookies[idx]`, where each index $0 \le idx < 20$ represents a **distinct authenticated student** (`synth_student_001` through `synth_student_020`).
2. **Distinct Rate-Limit Keys:**  
   Each request is evaluated against a unique rate-limit key `${userId}:${lessonId}`. Because all 20 requests originate from 20 different user IDs, 20 independent rate-limit buckets were used. Each user made exactly 1 request (well below the limit of 2 requests per 60 seconds).
3. **What Was NOT Exercised in Test 2.1:**  
   Test 2.1 did **not** exercise a shared-key rate-limit contention scenario (e.g., 20 concurrent tabs or rapid exit beacons originating from the *same* student on the *same* lesson).
4. **Behavior Under Shared-Key Contention:**  
   If multiple tabs of the same student attempt to send exit beacons simultaneously for the same lesson, the backend rate limit treats them uniformly:
   - Request 1: HTTP 200 (Allowed)
   - Request 2: HTTP 200 (Allowed)
   - Request 3+: HTTP 429 (`RATE_LIMIT_EXCEEDED`, Rejected)
   This exact shared-key behavior was verified separately in Test 3.1.
5. **No Backend Rate Limit Modifications:**  
   The backend rate limit remains strictly configured at **2 requests per 60 seconds** per `(userId, lessonId)` pair, as mandated by ADR-P7-001. No modifications were made.

### 6.3 Database Migration Locking Behavior & Concurrency Analysis
The forward migration [`0009_telemetry_foundation.sql`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/migrations/0009_telemetry_foundation.sql) exhibits the following exact PostgreSQL lock behaviors:
1. **Table Creation:** `CREATE TABLE IF NOT EXISTS "learning_events"` acquires an `AccessExclusiveLock` on the newly created `learning_events` table. Because the table is brand new, no other transactions hold locks on it, resulting in zero lock wait time.
2. **Foreign Key Constraints:** Attaching foreign keys (`course_id` $\rightarrow$ `courses`, `module_id` $\rightarrow$ `modules`, `lesson_id` $\rightarrow$ `lessons`) acquires:
   - `SHARE ROW EXCLUSIVE` lock on the **referencing** table (`learning_events`).
   - **`SHARE ROW EXCLUSIVE` lock on the referenced core tables (`courses`, `modules`, `lessons`)**:  
     In PostgreSQL, adding a foreign-key constraint explicitly requires a `SHARE ROW EXCLUSIVE` lock on referenced tables. This lock mode **directly conflicts with `ROW EXCLUSIVE`**, which is the lock mode acquired by all `INSERT`, `UPDATE`, and `DELETE` commands, as well as `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, and `ACCESS EXCLUSIVE`.
   - **Operational Write Contention Impact:** While foreign key constraints are being attached, any concurrent `INSERT`, `UPDATE`, or `DELETE` on `courses`, `modules`, or `lessons` will be blocked until the migration transaction completes. Conversely, if an active write transaction is currently executing against `courses`, `modules`, or `lessons`, the `ALTER TABLE` statement will wait in the lock queue, which can block subsequent writes to those tables (lock queue convoy).
   - **Unmeasured Staging Duration:** Although the new `learning_events` table is empty and constraint validation against it is virtually instantaneous, the actual lock acquisition and lock queue wait duration on referenced tables has **NOT been measured on the staging database under live concurrency**. It must **not** be claimed that foreign key creation is lock-free or guarantees zero write contention.
3. **Index Creation:** Creating non-concurrent B-tree indexes (`CREATE INDEX IF NOT EXISTS ... ON "learning_events"`) acquires a `ShareLock` on `learning_events`. This blocks concurrent writes to `learning_events` during index creation, but does not acquire locks on any other tables.
