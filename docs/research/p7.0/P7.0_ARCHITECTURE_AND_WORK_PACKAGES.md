### Candidate WP-P7-01: Learning Telemetry & `learning_events`

- **Actual Unmet Requirement:** Capture an append-only time-series of student interactions (`COURSE_OPENED`, `LESSON_STARTED`, `VIDEO_CHECKPOINT`, `LESSON_COMPLETED`, `QUIZ_ATTEMPTED`) to track drop-off curves, struggle hotspots, and provide sequential interaction history for future AI models.
- **Existing Reusable Components:** Drizzle ORM, PostgreSQL connection pool in `DatabaseModule`, Zod request validation pipeline, `AuthGuard` JWT verification, `AuditService`.
- **New Data & APIs Needed:**
  - Relational table `learning_events` via Migration `0009_learning_events.sql`.
  - Batch ingestion endpoint: `POST /api/v1/learning/events`.
  - Exit beacon endpoint: `POST /api/v1/learning/events/beacon` (`text/plain` and `application/json` payload parsing for `navigator.sendBeacon`).
  - Automated 90-day retention pruning cron job for high-frequency video checkpoints.
- **Dependencies:** Migration 0008 (P6.3 baseline).
- **Security & Privacy Risks:**
  - Telemetry flood and spoofing: Client-side throttling (60s in `VideoPlayer.tsx`) is strictly **supplemental defense-in-depth** and can be trivially bypassed or disabled by scripted clients. The backend requires five mandatory server-side controls for P7.1:
    1. *Server-Side Rate Limiting:* Enforce per-user / per-lesson throttling (e.g., max 2 requests per 60s per `(userId, lessonId)`).
    2. *Authentication & Enrollment Entitlement Authorization:* Verify authorized active enrollment and entitlement for `req.user.id` on every batch request, validating both paid course enrollments and legitimate free/zero-payable courses where supported by existing business rules (rejecting unauthorized attempts with HTTP 403).
    3. *Payload-Size Validation:* Enforce batch ceilings (maximum 50 events per batch, maximum 32KB request body size) via strict Zod schema validation.
    4. *Duplicate-Event Idempotency vs. Broader Replay Protection:* Client-generated `eventId` UUIDs enforce strict idempotency semantics:
       - *Same event ID and same payload:* Idempotent duplicate handling (HTTP 200/204 with exactly 0 duplicate rows inserted into `learning_events`).
       - *Same event ID and different payload:* Reject or report an idempotency conflict (HTTP 409 Conflict) without modifying existing records or inserting duplicates.
       However, client-generated UUIDs **do not provide broader replay or abuse protection** (an attacker can generate fresh UUIDs). Broader replay and abuse protection requires server-side temporal bounding, progress duration caps, and server-side rate limits.
    5. *Server-Authoritative Invariant Preservation:* Telemetry ingestion is strictly observational and analytical; it must **never** independently award lesson completion, course completion, or certificates, nor alter financial ledger balances or weaken existing server-authoritative learning and financial invariants. All completion logic and certificate generation remain strictly controlled by server-authoritative domain services.
  - PII leakage in payloads: *Mitigation:* `metadata` JSONB schema strictly typed; zero student personal identifiers, payment tokens, or raw credentials allowed in telemetry payloads.
- **Telemetry Privacy Architecture (APPROVED via ADR-P7-001):**
  On October 17, 2026, Senior Engineering Leadership formally ratified [`ADR-P7-001`](file:///d:/Work/2026/techsprout-main/docs/architecture/adr/ADR-P7-001-learning-telemetry-privacy-and-fts.md), approving **Anonymized/Hashed Telemetry with Local-First Aggregation (PII Stripping at Ingestion)**. Earlier draft alternatives (hard delete CASCADE, nullable SET NULL, and synthetic account pseudonymization) are superseded.
  - *Zero Raw Search / Payload Persistence:* Raw student search queries and client payloads are never stored in `learning_events`, application logs, Redis caches, or error reports.
  - *Allowlisting & Boundary Stripping:* Strict Zod schema allowlisting strips all unapproved fields, client fingerprints, and IP addresses at the ingestion boundary before persistence.
  - *Rotating Daily Salt Hashing:* User and session IDs are hashed using $\text{HMAC-SHA256}(\text{userId}, \text{SALT}_{\text{UTC\_DAY}})$. The salt rotates on UTC day boundaries and is held purely in process memory; raw IDs and salts are never persisted alongside telemetry records.
  - *Pseudonymity Disclosure:* Rotating-salt hashes are formally recognized as pseudonymous identifiers. Daily rotation limits cross-day learner linkage; zero stable cross-day tracking identifiers are introduced.
  - *Kill Switch:* Environment flag `TELEMETRY_ENABLED=false` disables all telemetry capture, transmission, and background processing immediately.
  - *Observational Invariant:* Telemetry is purely observational; it must never independently award completion or certificates or modify financial balances.
- **Migration & Performance Risks (ASSUMPTIONS):** Standard transactional `CREATE INDEX` during Migration 0009 acquires a `SHARE` lock; because the table is newly created and empty, lock duration is estimated at $< 50\text{ms}$ *(classified as an ASSUMPTION pending empirical staging measurement)*.
- **Cost Assumptions & Pricing Realism:** $0/mo additional infrastructure if using direct PostgreSQL batch inserts within Render Free tier. If upgraded to Render paid tiers, official pricing distinguishes Web Service compute ($7.00/mo Starter) from PostgreSQL compute (`0.1c-256mb` at $6.00/mo vs `0.5c-1g` at $19.00/mo), with 1GB SSD storage included in database compute and additional storage billed at $0.30/GB/month. (All prices are indicative; actual deployed-plan pricing remains unverified without dashboard or invoice evidence; infrastructure modifications remain strictly prohibited).
- **Explicit & Testable Security Acceptance Criteria:**
  - `AC-P7-01-SEC-01 (Duplicate Idempotency - Same Payload):` Sending a duplicate payload with an identical `eventId` and matching payload attributes returns HTTP 200/204 with exactly 0 duplicate rows inserted into `learning_events`.
  - `AC-P7-01-SEC-02 (Idempotency Conflict - Different Payload):` Sending a request with an existing `eventId` but conflicting/different payload attributes (e.g., altered `event_type`, `user_id`, or `occurred_at`) returns HTTP 409 Conflict without modifying existing records or inserting duplicates.
  - `AC-P7-01-SEC-03 (Rate Limiting):` Exceeding 2 batch requests in 60s for the same `(userId, lessonId)` returns HTTP 429 Too Many Requests, regardless of whether new client UUIDs are generated.
  - `AC-P7-01-SEC-04 (Temporal Bounding):` Submitting events with `occurred_at` > 30s in the future or > 24 hours in the past returns HTTP 400 Bad Request.
  - `AC-P7-01-SEC-05 (Duration Cap):` Submitting `watch_position_seconds` exceeding verified lesson video duration returns HTTP 400 Bad Request.
  - `AC-P7-01-SEC-06 (Enrollment & Entitlement Authorization):` Submissions from authenticated users lacking active, authorized course enrollment and entitlement (validating both paid enrollments and legitimate free/zero-payable courses supported by existing business rules) return HTTP 403 Forbidden.
  - `AC-P7-01-SEC-07 (Payload Bounding):` Batches with > 50 events or request body > 32KB are rejected with HTTP 400 Bad Request.
  - `AC-P7-01-SEC-08 (Server-Authoritative Invariant Preservation):` Telemetry events must never independently award lesson completion, course completion, or certificates, nor modify financial ledger balances. All progress state transitions, completion criteria, and certificate issuance remain strictly server-authoritative through domain services ([`ProgressService`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/progress/progress.service.ts), [`CertificateService`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/certificates/certificates.service.ts)).
- **Release Prerequisites:**
  - Senior approval of ADR `DEC-P7-01` (Buffering Model) and Privacy Policy selection.
  - Senior leadership confirmation of actual live production PostgreSQL plan, creation date, and expiration status via Render dashboard or billing invoice evidence (STATUS: PENDING).

## 2. In-Depth Architectural Trade-Off Evaluations

### 2.1 Telemetry Ingestion Buffering (DEC-P7-01)
- **Problem:** Video heartbeats generate 10–50 events per active student per minute. Direct individual row inserts cause connection pool exhaustion and write contention on PostgreSQL.
- **Options Evaluated:**
  - *Option A (Direct PostgreSQL Multi-Row Batch INSERT):* Client batches up to 10 events; server executes a single `INSERT INTO learning_events VALUES (...), (...);`. Connection pooling managed via existing `pg.Pool`.
  - *Option B (BullMQ Queue Buffering into Redis):* Server immediately pushes events into BullMQ; background worker micro-batches writes to PostgreSQL.
  - *Option C (In-Memory Node.js Buffer):* In-memory array flushed every 5 seconds.
- **Evaluation:**
  - Option C is rejected because Render Free containers spin down after 15 minutes of idle time, and sudden container restarts destroy unflushed in-memory data.
  - Option B is the enterprise gold standard, but **Render Free Redis has a 25MB RAM limit with `noeviction` policy**. Sustained video scrubbing queues risk exhausting 25MB, triggering Redis crashes.
  - Option A is safe, highly performant for TechSprout's scale, and introduces zero memory risk on Redis.
- **Recommendation:** **Option A for MVP (Phase 7.1)**. Transition to **Option B** only after upgrading Redis to Render Starter ($10/mo, 256MB+ RAM).

### 2.2 Client Video Scrub Transport Protocol (DEC-P7-02)
- **Problem:** Browser tab closure and page navigation cancel pending standard `axios.post()` promises in `VideoPlayer.tsx`, resulting in lost completion checkpoints.
- **Options Evaluated:**
  - *Option A (Standard fetch / axios):* Status quo. Fails on tab close.
  - *Option B (navigator.sendBeacon + fetch keepalive fallback):* Uses `navigator.sendBeacon('/api/v1/learning/events/beacon', payload)` on `visibilitychange` and unmount. If `sendBeacon` is unavailable, falls back to `fetch(url, { keepalive: true })`.
  - *Option C (WebSockets):* Persistent bidirectional socket. Overkill for periodic telemetry; high connection state overhead on Render Free tier.
- **Recommendation:** **Option B (`navigator.sendBeacon` + `fetch keepalive`)**. Fully solves unmount data loss with zero socket overhead.

### 2.3 Telemetry Data Retention & Pruning Strategy (DEC-P7-03)
- **Problem:** Render Free PostgreSQL has a 1GB disk limit. Capturing video heartbeats indefinitely will exhaust storage within 6–12 months.
- **Options Evaluated:**
  - *Option A (Infinite Retention):* Guaranteed disk overflow on Free tier.
  - *Option B (Tiered Retention with 90-Day Chunked Pruning):* Fine-grained `VIDEO_CHECKPOINT` events are pruned after 90 days. Milestone events (`COURSE_OPENED`, `LESSON_COMPLETED`, `QUIZ_ATTEMPTED`, `CERTIFICATE_EARNED`) are retained permanently. Pruning runs nightly in chunks of 5,000 rows to avoid table locks.
  - *Option C (Zero Heartbeat Persistence):* Do not persist heartbeats at all. Defeats the purpose of video retention analytics.
- **Recommendation:** **Option B (90-day checkpoint pruning)**.

### 2.4 AI Tutoring: Vector Retrieval vs Simpler Alternatives (DEC-P7-04)
- **Context & Corpus Size Analysis:**
  TechSprout currently has **11 published courses, ~100 total lessons, and an estimated total text corpus of ~50,000 words**.
- **Options Evaluated:**
  1. *Option 1 (Simpler Alternative: PostgreSQL Full-Text Search):*  
     PostgreSQL 16 native `tsvector` and `tsquery` with `websearch_to_tsquery('english', query)`. Uses existing database, consumes 0MB extra RAM, requires no additional extensions, and retrieval latency is estimated at $< 10\text{ms}$ *(classified as an ASSUMPTION pending empirical staging benchmark)*.
  2. *Option 2 (PostgreSQL `pgvector` Extension):*  
     Stores 768-dimensional embeddings (e.g., text-embedding-004). Generates dense vector similarity (`<=>` cosine distance). Requires `CREATE EXTENSION vector;` and HNSW/IVFFlat index. Consumes estimated ~30–50MB RAM for index maintenance *(ASSUMPTION)*. On Render Free (512MB RAM shared), index building risks container OOM kills.
  3. *Option 3 (Managed Serverless Vector SaaS - Pinecone / Qdrant Cloud):*  
     External SaaS. Free tier available, but introduces external network latency, multi-system synchronization lag, and egress complexity.
- **Recommendation & Ratified Criteria (ADR-P7-001):** **Benchmark Option 1 (Full-Text Search) first**. For a 50,000-word educational corpus organized by course and lesson, native PostgreSQL FTS (`tsvector` / GIN index) must be evaluated against explicit pass/fail acceptance criteria:
  - *Query Latency:* $p95 < 50\text{ms}$ on representative workload.
  - *Relevance Accuracy:* $\text{NDCG@5} \ge 0.80$ and $\text{Recall@5} \ge 0.85$ across a standardized 30-query test set.
  - *Reporting:* Both warm- and cold-cache distributions must be reported; synthetic/sanitized data only; zero production PII or raw search strings captured.
  - *The pgvector Memory Gate:* If native FTS fails, `pgvector` evaluation is strictly gated on empirical evidence that its index build and query memory fit within the actual free-tier database RAM ceiling with **at least 30% memory headroom** and zero container OOM failures. If this cannot be demonstrated, stop and escalate; no automatic infrastructure upgrades.

### 2.5 Marketplace Monetization & Financial Ledger (DEC-P7-05 & DEC-P7-06)
- **Model:** Internal double-entry accounting ledger.
- **Gateway Invariant:** Single-merchant SSLCommerz. All student payments enter TechSprout's platform account.
- **Escrow Hold Period:** 14-day hold in `pending_balance_cents`. Matches the platform refund policy. Instructors cannot withdraw funds until the refund window has closed.
- **Disbursement:** Payout requests submitted via UI $\rightarrow$ Verified by Admin $\rightarrow$ Disbursed manually or via batch MFS (bKash/Nagad) $\rightarrow$ Admin marks settled.
