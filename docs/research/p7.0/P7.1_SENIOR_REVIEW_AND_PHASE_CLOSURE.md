## 1. Executive Summary & Implemented Subsystems

Phase 7.1 delivers the foundational data and learning analytics pipeline for the TechSprout platform, implementing WP-P7-01 (Append-Only Telemetry Ingestion), WP-P7-02 (Video Telemetry & Retention Analytics), and the authorized staging subset of WP-P7-06.

### 1.1 Database Schema Foundation (WP-P7-01)
- **Table:** `learning_events` defined in [`apps/api/src/database/schema/telemetry.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/schema/telemetry.ts) using Drizzle ORM and applied via migration [`0009_telemetry_foundation.sql`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/migrations/0009_telemetry_foundation.sql).
- **Structure:**
  - `id`: UUID primary key.
  - `user_id`: `VARCHAR(64)` storing a pseudonymous HMAC-SHA256 hash produced using the approved daily-salt design (`HMAC-SHA256(studentId, dailySalt)`).
  - `course_id`: UUID foreign key referencing `courses(id)` with `ON DELETE CASCADE`.
  - `module_id`: UUID nullable foreign key referencing `modules(id)` with `ON DELETE SET NULL`.
  - `lesson_id`: UUID nullable foreign key referencing `lessons(id)` with `ON DELETE SET NULL`.
  - *No Foreign Key to Users Table:* Because `user_id` stores a cryptographically pseudonymized hash rather than a direct relational user ID, there is intentionally no foreign key constraint to the `users` table.
  - `event_type`: `VARCHAR(50)` restricted to approved enum values (`VIDEO_STARTED`, `VIDEO_CHECKPOINT`, `VIDEO_PAUSED`, `VIDEO_SEEKED`, `VIDEO_COMPLETED`, `LESSON_COMPLETED`, `QUIZ_ATTEMPTED`, `CERTIFICATE_EARNED`).
  - `metadata`: `JSONB` with strict per-event validation (e.g., `watchPositionSeconds`, `playbackRate`).
  - `occurred_at`: `TIMESTAMPTZ` recording client event occurrence time.
  - `created_at`: `TIMESTAMPTZ` default `now()` recording server write time.
- **Deduplication & Indexing:**
  - **Application-Level Idempotent Deduplication:** PostgreSQL does not enforce deduplication through a composite unique constraint. Instead, deduplication is enforced at the application service layer ([`TelemetryService`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/telemetry/telemetry.service.ts)) using the client-provided event ID mapped to primary key `id`. Matching payloads with identical attributes are deduplicated as idempotent retries (`deduplicatedCount++`), whereas submissions conflicting with an existing event ID return HTTP 409 `IDEMPOTENCY_CONFLICT`.
  - **Physical Indexes:** Migration 0009 creates four actual two-column btree indexes:
    - `learning_events_course_occurred_idx`: `(course_id, occurred_at)` for course-level analytics windowing.
    - `learning_events_user_occurred_idx`: `(user_id, occurred_at)` for learner event timeline queries.
    - `learning_events_lesson_event_idx`: `(lesson_id, event_type)` for lesson engagement decile aggregations.
    - `learning_events_type_occurred_idx`: `(event_type, occurred_at)` for background chunked retention pruning.

### 1.2 Ingestion API & Security Guards (WP-P7-01)
- **Endpoints:**
  - `POST /api/v1/learning/events`: Authenticated JSON batch ingestion endpoint.
  - `POST /api/v1/learning/events/beacon`: Dedicated endpoint utilizing custom [`text-body-parser.middleware.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/common/http/text-body-parser.middleware.ts) supporting `navigator.sendBeacon` (`Content-Type: text/plain`) upon browser unload.
- **Security & Validation Controls:**
  - **Strict Allowlisting:** Zod schemas compiled with `.strict()`; requests containing unapproved metadata or forbidden raw fields (`userEmail`, `studentName`, `searchQuery`) are rejected immediately with HTTP 400 `VALIDATION_ERROR`.
  - **Batch & Payload Ceilings:** Strict enforcement of maximum 50 events per batch and maximum 32KB body size (oversized payloads rejected with HTTP 400 `PAYLOAD_TOO_LARGE`).
  - **Temporal Anti-Clock-Skew Guard:** Events with `occurred_at > now() + 30 seconds` are rejected with HTTP 400 `TEMPORAL_BOUND_FUTURE`.
  - **Zero-Trust Ownership & Enrollment:** Ingestion requires valid JWT/session authentication (`JwtAuthGuard`) and verifies active course enrollment (`CourseEnrollmentGuard`). Unenrolled submissions return HTTP 403 `ENROLLMENT_REQUIRED`.
  - **Sliding-Window Rate Limiting:** Enforced via Redis 7 sorted sets in [`TelemetryService`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/telemetry/telemetry.service.ts), allowing a maximum of **2 requests per 60 seconds** per `(studentId, lessonId)` pair. Excess dispatches return HTTP 429 `RATE_LIMIT_EXCEEDED`.

### 1.3 Cryptographic Privacy Architecture (ADR-P7-001)
- **Salt Rotation & Pseudonymity:** [`TelemetryPrivacyService`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/telemetry/telemetry-privacy.service.ts) generates a 256-bit cryptographically secure daily salt held strictly in process memory.
- **Transformation:** The raw student identifier is transformed via `HMAC-SHA256(studentId, dailySalt)` and stored in the physical `user_id` column (`VARCHAR(64)`). Raw student UUIDs, email addresses, and IP addresses are stripped at the ingestion boundary and are never persisted.
- **Cross-Day Linkage Limits:** Rotating the salt daily permanently breaks cross-day learner correlation, complying with GDPR/FERPA pseudonymous data principles.

### 1.4 Client Telemetry Integration (WP-P7-02)
- **React Hook:** [`useLearningTelemetry.ts`](file:///d:/Work/2026/techsprout-main/apps/web/src/hooks/useLearningTelemetry.ts) in `apps/web`.
- **Multi-Tab Concurrency:** Uses Web Locks API (`navigator.locks`) with `localStorage` fallback to prevent duplicate dispatches across concurrent browser tabs.
- **Bounded Buffer & Prioritized Eviction:** Maintains an in-memory queue capped at 100 events. If queue capacity is reached, Tier 1 completion milestones (`VIDEO_COMPLETED`, `LESSON_COMPLETED`) are preserved, while Tier 3 interaction events (`VIDEO_PAUSED`, `VIDEO_SEEKED`) and redundant `VIDEO_CHECKPOINT` events are coalesced or pruned.
- **Fixed Throttling & Beacon Reserve:** [`VideoPlayer.tsx`](file:///d:/Work/2026/techsprout-main/apps/web/src/components/learning/VideoPlayer.tsx) enforces 60-second fixed dispatch intervals, reserving the second server rate-limit slot specifically for exit beacon transport. A 90% video watch progress threshold triggers the `VIDEO_COMPLETED` milestone.

### 1.5 Instructor Retention Analytics & UI (WP-P7-02)
- **API Endpoint:** `GET /api/v1/instructor/analytics/courses/:courseId/retention` in [`instructor-analytics.controller.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/analytics/instructor-analytics.controller.ts), protected by role guards (`INSTRUCTOR`, `ADMIN`) and course ownership verification.

### 1.6 BullMQ Retention Pruning Worker (WP-P7-01 / WP-P7-06 Subset)
- **Worker Architecture:** [`TelemetryPruningWorker`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/telemetry/telemetry-pruning.worker.ts) using BullMQ on Redis 7. Queue: `techsprout-telemetry-pruning`, Job: `prune-video-checkpoints`.
- **Deterministic Scheduling:** Registered with deterministic scheduler ID `telemetry-pruning-nightly` and cron pattern `0 3 * * *` (03:00 UTC).
- **Concurrency & Chunking:** Worker concurrency is strictly 1 to eliminate lock contention. Executes chunked batch deletions of 5,000 rows (`DELETE ... WHERE id IN (SELECT id ... LIMIT 5000)`), releasing table locks between batches.
- **Retention Scope:** Targets `VIDEO_CHECKPOINT` records where `occurred_at < now() - 90 days`. Milestone completion events are retained permanently.
- **Observability:** Integrates into `GET /api/v1/health`, exposing worker connection state, scheduler registration, and `lastPruningRun` metrics.

## 5. Critical Engineering Disclosure: Rate Limiting & Latency Representation

> [!WARNING]
> **STATISTICAL DISCLOSURE FOR SENIOR REVIEW:**  
> Total-request latency percentiles must **NOT** be misrepresented as successful-request-only latency.

1. **Why Rate Limiting Was Triggered:**  
   The load test submitted 30 write operations (18 batch + 12 beacon) across 4 lessons using 4 concurrent workers in 4.89 seconds. Because the backend rate limit is strictly configured at **2 requests per 60 seconds per student/lesson** (mandated by ADR-P7-001), 22 write operations exceeded the threshold and were intercepted by Redis sliding-window protection.
2. **Impact on Latency Percentiles:**  
   - HTTP 429 responses return early from NestJS application memory after querying Redis sorted sets (`ZADD`, `ZCARD`), requiring only **~240–280 ms** of round-trip network time and bypassing PostgreSQL completely.
   - The reported overall percentiles ($p50 = 247\text{ms}$, $p95 = 781\text{ms}$, $p99 = 793\text{ms}$) reflect the **entire 60-request population**, which includes these 22 early-returning 429 responses.
   - Successful database writes (`POST /learning/events` returning HTTP 200) exhibited latencies between 250ms and 781ms during concurrent analytical reads.
   - The triggering of 22 HTTP 429 responses demonstrates that the sliding-window rate limiter functions effectively under rapid multi-tab dispatch, protecting PostgreSQL from write contention. However, the senior authority must evaluate these percentiles with full awareness of the population composition.

### 6.2 Technical Clarification on Deletion Behavior
> [!IMPORTANT]
> **A zero-deletion run does NOT independently demonstrate actual deletion behavior for expired records.**

  WHERE event_type = 'VIDEO_CHECKPOINT' AND occurred_at < (now() - interval '90 days')

  Because no records in staging are older than 90 days, `candidateRows.length === 0`.
- **What Is Proven:** The live run proves that the BullMQ cron scheduler triggers precisely at 03:00 UTC, establishes a database connection, evaluates the retention query, and records completion diagnostics without throwing exceptions or crashing the container.

## 7. Privacy, Kill Switches & Operational Controls

### 7.1 Backend Kill Switch (`TELEMETRY_ENABLED`)
- **Mechanism:** Evaluated dynamically in [`TelemetryService.isTelemetryEnabled()`](file:///d:/Work/2026/techsprout-main/apps/api/src/modules/telemetry/telemetry.service.ts).
- **Ingestion Protection:** When set to `false`, `/api/v1/learning/events` and `/beacon` immediately return HTTP 200 with `{ ingestedCount: 0, deduplicatedCount: 0 }` without writing to PostgreSQL.
- **Worker Protection:** Automatically invokes `removeJobScheduler('telemetry-pruning-nightly')` on the BullMQ queue and skips any active pruning tasks.

### 7.2 Frontend Kill Switch (`NEXT_PUBLIC_TELEMETRY_ENABLED`) & Build Dependency
- **Mechanism:** Evaluated in [`useLearningTelemetry.ts`](file:///d:/Work/2026/techsprout-main/apps/web/src/hooks/useLearningTelemetry.ts#L225-L228):
  ```typescript
  const isTelemetryEnabled =
    typeof process !== 'undefined' &&
    process.env.NEXT_PUBLIC_TELEMETRY_ENABLED !== 'false' &&
    process.env.TELEMETRY_ENABLED !== 'false';
  ```
- **Next.js Build-Time Inlining Reality:**  
  In Next.js App Router, `NEXT_PUBLIC_*` environment variables are statically embedded into client JavaScript bundles at compile time.  
  *Operational Requirement:* Setting `NEXT_PUBLIC_TELEMETRY_ENABLED=false` in the Vercel dashboard has **zero effect** on active client emissions until a **fresh Vercel build and deployment** is completed.
- **Runbook Documentation:** Both backend and frontend kill switches, along with this build dependency, are formally recorded in the staging runbook ([`P7.1_TELEMETRY_LOAD_BENCHMARK_AND_STAGING_GATE_REPORT.md`](file:///d:/Work/2026/techsprout-main/docs/research/p7.0/P7.1_TELEMETRY_LOAD_BENCHMARK_AND_STAGING_GATE_REPORT.md), §6.4).

   Render Free Web Services spin down after 15 minutes of inactivity. When spun down, incoming requests experience a 30–50s cold start, and BullMQ cron triggers cannot fire unless kept awake. Production deployment requires upgrading to Render Starter Web Service ($7/mo) and Redis Starter ($10/mo) to guarantee 24/7 background worker execution.
2. **Expired Record Deletion on Live Staging:**  
   As disclosed in §6, physical row deletion on staging remains unverified because all records are recent. An optional follow-up test fixture may be authorized by leadership if physical deletion proof is strictly required.
3. **Outbox Dual-Write Architecture:**  
   As identified in the P7.0 audit, `OutboxService` remains an uncoordinated, best-effort dual-write pattern. Telemetry ingestion bypasses Outbox by writing directly to `learning_events`, but platform-wide event outbox reliability remains a backlog technical debt item.
4. **Follow-Up Actions:**
   - Formalize paid infrastructure provisioning plan prior to production release.
   - Maintain client-side error telemetry monitoring during initial production rollout.
