#### 1.2 Unmount Exit Defect (Data Loss Vulnerability)
- **Vulnerability Identified:** [`VideoPlayer.tsx:L131-141`](file:///d:/Work/2026/techsprout-main/apps/web/src/components/learning/VideoPlayer.tsx#L131-L141):
  ```typescript
  useEffect(() => {
    return () => {
      if (videoRef.current) {
        const time = videoRef.current.currentTime;
        if (Math.abs(time - lastCheckpointTimeRef.current) >= 1) {
          saveProgressCheckpoint(courseId, lessonId, Math.floor(time)).catch(() => {});
        }
      }
    };
  }, [courseId, lessonId]);
  ```
- **Finding:** The cleanup function calls `saveProgressCheckpoint()`, which issues a standard `axios.post()` Promise. When a user closes the browser tab, navigates to another site, or refreshes the page, the browser cancels asynchronous `fetch`/`XMLHttpRequest` requests before the server handshake completes.
- **Classification:** `VERIFIED GAP`. Requires `navigator.sendBeacon()` or `fetch(..., { keepalive: true })`.

#### 1.5 Telemetry Schema Design & Privacy Architecture (APPROVED via ADR-P7-001)
The architectural trade-offs between schema nullability constraints, analytical utility, and student privacy erasure were formally evaluated and resolved on October 17, 2026, by Senior Engineering Leadership via [`ADR-P7-001`](file:///d:/Work/2026/techsprout-main/docs/architecture/adr/ADR-P7-001-learning-telemetry-privacy-and-fts.md).
- **Historical Inconsistency Resolved:** The contradiction between `user_id NOT NULL` and erasure nullification (`SET NULL`) was superseded. The three preliminary alternatives (unconditional hard deletion via CASCADE, standalone nullable `SET NULL`, and static sentinel account pseudonymization) were rejected as general solutions.
- **Ratified Approach:** **Anonymized/Hashed Telemetry with Local-First Aggregation (PII Stripping at Ingestion)**.
  - *Zero Raw Search / Payload Persistence:* Raw student search strings and client request payloads are never stored in telemetry tables, application logs, analytics caches, or error reports.
  - *Ingestion-Boundary Allowlisting:* Strict Zod schema validation strips unapproved properties, device fingerprints, and PII immediately upon arrival.
  - *Rotating Daily Salt Hashing:* User identifiers are transformed via $\text{HMAC-SHA256}(\text{userId}, \text{SALT}_{\text{UTC\_DAY}})$, with salts held purely in memory and rotated at UTC midnight.
  - *Pseudonymity Disclosure:* Rotating-salt hashes are formally recognized as pseudonymous identifiers; daily rotation limits cross-day learner linkage, and zero stable cross-day tracking identifiers are introduced.
  - *Kill Switch:* Environment flag `TELEMETRY_ENABLED=false` provides immediate operational shutdown of all telemetry ingestion, transmission, and background jobs.
  - *Observational Invariant:* Telemetry remains strictly observational; it never independently awards completion or certificates or alters financial balances.
- **Governance Status:** **RESOLVED — RATIFIED via ADR-P7-001 (October 17, 2026)**. Full implementation details are recorded in [`ADR-P7-001`](file:///d:/Work/2026/techsprout-main/docs/architecture/adr/ADR-P7-001-learning-telemetry-privacy-and-fts.md) and [`P7.0_SENIOR_DECISION_RECORD.md`](file:///d:/Work/2026/techsprout-main/docs/research/p7.0/P7.0_SENIOR_DECISION_RECORD.md).

#### 3.3 Migration Runner Mechanics & Indexing Constraints
- **Runner File:** [`apps/api/src/database/migrate.ts`](file:///d:/Work/2026/techsprout-main/apps/api/src/database/migrate.ts)
- **Execution:** Uses Drizzle's `migrate(db, { migrationsFolder })`.
- **Critical PostgreSQL Invariant:** Drizzle's migration runner automatically executes every `.sql` file inside a single transactional block (`BEGIN ... COMMIT`).
- **Index Implication:** PostgreSQL Error `25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.
- **Finding:** Any database index added via Drizzle migrations **must use standard transactional `CREATE INDEX`**. Standard `CREATE INDEX` acquires a `SHARE` lock on the target table (allows reads, blocks concurrent writes).

  - For large active tables, migrations must be executed during low-traffic deployment windows.

#### 4.3 Request Throttling & Abuse Prevention
- **Global Throttling:** Configured in `AppModule` ([`apps/api/src/app.module.ts:L40-45`](file:///d:/Work/2026/techsprout-main/apps/api/src/app.module.ts#L40-L45)) using NestJS `@nestjs/throttler`.
  - Rate Limit: 100 requests per 60,000ms (1 minute) per IP address.
- **Route-Level Throttling:** Used on sensitive auth endpoints (OTP generation, checkout initialization).
- **Per-User / Per-Lesson Telemetry Throttling:** **NOT IMPLEMENTED**. There is zero server-side rate limiting on `(userId, lessonId)` in `apps/api`. Client-side throttling in `VideoPlayer.tsx` (60s) is strictly **supplemental defense-in-depth** and can be trivially bypassed or disabled by scripted clients.
- **Mandatory Server-Side Controls for Phase 7.1:** Client-side throttling is non-authoritative. The ingestion backend requires five mandatory server-side controls:
  1. *Server-Side Per-User / Per-Lesson Throttling:* Enforce a strict rate ceiling (e.g., max 2 requests per 60 seconds per `(userId, lessonId)`).
  2. *Authentication & Enrollment Entitlement Authorization:* Verify authorized active enrollment and entitlement for `req.user.id` on every batch ingestion and beacon request, validating both paid course enrollments and legitimate free/zero-payable courses where supported by existing business rules (rejecting unauthorized attempts with HTTP 403).
  3. *Payload-Size Validation:* Enforce batch ceilings (e.g., maximum 50 events per batch, maximum 32KB request body size) via strict Zod schema validation.
  4. *Duplicate-Event Idempotency vs Broader Replay Protection:* Client-generated `eventId` UUIDs enforce strict idempotency semantics:
     - *Same event ID and same payload:* Idempotent duplicate handling (HTTP 200/204 with exactly 0 duplicate rows inserted into `learning_events`).
     - *Same event ID and different payload:* Reject or report an idempotency conflict (HTTP 409 Conflict) without modifying existing records or inserting duplicates.
     However, client-generated UUIDs **do not provide broader replay or abuse protection** (because malicious scripts can easily generate fresh UUIDs). Broader replay and forgery protection requires server-side temporal bounding (rejecting events with `occurred_at` > 30s in the future or > 24h in the past), progress monotonicity and duration caps (`watch_position_seconds` capped at verified lesson video duration), and server-side per-user rate limiting.
  5. *Server-Authoritative Invariant Preservation:* Telemetry ingestion is strictly observational and analytical; it must **never** independently award lesson completion, course completion, or certificates, nor alter financial ledger balances or weaken existing server-authoritative learning and financial invariants. All completion logic and certificate generation remain strictly controlled by server-authoritative domain services.
