## 1. Executive Summary & Benchmark Verdict

Pursuant to senior engineering authorization for a research-only hybrid search experiment, this report evaluates whether PostgreSQL-native `pg_trgm` fuzzy matching and controlled query relaxation can bridge the relevance and zero-result gaps identified in the original Full-Text Search (FTS) baseline.

The experiment was conducted on an expanded synthetic curriculum corpus of **53,960 words** (472,478 characters) across **11 courses** and **100 lessons**, executed within an isolated, disposable PostgreSQL 14 instance mirroring the Render Free database tier (0.1 shared vCPU, 256 MB RAM ceiling, 64 MB `shared_buffers`, 1 GB storage).

### Key Architectural Findings:
1. **NDCG@5 Breakthrough (0.8633 vs 0.80 target):** Configuration C (Strict FTS + Query Relaxation + `pg_trgm` Fallback) elevates ranking accuracy from 0.5100 to **0.8633**, successfully passing the senior relevance gate. 2. **Complete Elimination of Zero-Result Drops (10/32 $\rightarrow$ 0/32):** Both Configuration B and Configuration C completely eliminated all 10 unexplained zero-result queries. 3. **Sub-5ms Latency at Scale ($p95 = 4.13\text{ ms}$ at C=10):** Even with two-tiered fallback execution and multi-query disjunction, Configuration C achieves a $p95$ of **4.13 ms** under sustained 10-client concurrency (>3,100 queries/sec throughput), beating the 50 ms SLA by more than **12x**.
4. **Recall Capped at 0.7115 (Failure vs 0.85 Target):** Despite extensive query relaxation and trigram matching, overall Recall@5 reached **0.7115**, missing the strict 0.85 threshold. In technical educational curriculums, related prerequisite concepts are scattered across disparate modules; lexical and trigram techniques excel at retrieving the exact primary match (Grade 3), but cannot discover loosely related conceptual prerequisites (Grade 1/2) without dense semantic vector embeddings.

### 3.2 Database Schema & Index Design
The temporary benchmark table incorporated both English Full-Text Search vectors and Trigram targets:

```sql
CREATE TABLE benchmark_lessons (
  id SERIAL PRIMARY KEY,
  course_id INT NOT NULL,
  course_title TEXT NOT NULL,
  module_title TEXT NOT NULL,
  lesson_id INT NOT NULL,
  lesson_title TEXT NOT NULL,
  lesson_content TEXT NOT NULL,
  keywords TEXT[] NOT NULL,
```

1. **`search_vector` (`tsvector`):** Generated using PostgreSQL's standard `english` dictionary with positional weighting:

   - `benchmark_lessons_search_idx`: `USING gin(search_vector)` (Build duration: **10.52 ms**, Size: **216 kB**).
   - `benchmark_lessons_trgm_idx`: `USING gin(trgm_text gin_trgm_ops)` (Build duration: **6.71 ms**, Size: **152 kB**).

## 4. Search Configurations & Ranking Rules

Three distinct search architectures were evaluated under identical conditions:

### Configuration A — Existing PostgreSQL FTS Baseline (Control)
- **Mechanism:** Strict conjunctive parsing via `websearch_to_tsquery('english', $1)`.
- **Ranking:** Cover-density ranking via `ts_rank_cd(search_vector, query)`.
- **Execution:**
  ```sql
  SELECT lesson_id, course_title, lesson_title,
         ts_rank_cd(search_vector, websearch_to_tsquery('english', $1)) AS rank
  FROM benchmark_lessons
  WHERE search_vector @@ websearch_to_tsquery('english', $1)
  ORDER BY rank DESC
  LIMIT 5;
  ```
- **Limitation:** Requires all query terms to be present as stemmed lexemes. Fails instantly on misspellings, hyphenated/slashed compound tokens (`ci/cd`), and conversational natural-language queries.

### Configuration B — FTS with `pg_trgm` Fuzzy Fallback
- **Mechanism:**
  1. Primary execution executes strict FTS (`websearch_to_tsquery`).
  2. If strict FTS returns $\ge 1$ rows, those rows are returned immediately.
  3. If strict FTS returns exactly $0$ rows, trigger `pg_trgm` fuzzy fallback over `trgm_text`.
- **Ranking:** Trigram word similarity via `word_similarity($1, trgm_text)`.
- **Threshold Calibration:** Tested candidate thresholds $[0.25, 0.30, 0.35, 0.40, 0.45]$. Threshold **0.30** was selected as optimal: it captured 8/8 misspelling queries while restricting average false-positive retrieval to $<2.5$ rows per query.
- **Execution:**
  ```sql
  SELECT lesson_id, course_title, lesson_title,
         word_similarity($1, trgm_text) AS sim
  FROM benchmark_lessons
  WHERE word_similarity($1, trgm_text) >= 0.30
  ORDER BY sim DESC
  LIMIT 5;
  ```

### Configuration C — FTS with Controlled Query Relaxation & Trigram Fallback (Hybrid)
- **Mechanism:** A multi-tier retrieval pipeline that combines strict precision, term relaxation, and fuzzy error recovery:
  1. **Tier 1 (Strict FTS):** Execute `websearch_to_tsquery('english', $1)`. If 5 rows are retrieved, return immediately. Exact matches are never displaced by relaxed or fuzzy results.
  2. **Tier 2 (Controlled Relaxation):** If $< 5$ rows are retrieved:
     - Safely normalize query text (lowercase, strip special punctuation).
     - Filter out nonessential conversational stop words:  
       `['how', 'to', 'what', 'is', 'are', 'why', 'for', 'in', 'on', 'at', 'the', 'a', 'an', 'of', 'with', 'and', 'or', 'does', 'differ', 'from', 'best', 'practices', 'guide', 'strategy', 'strategies', 'setting', 'up', 'build', 'building', 'using', 'prevent', 'implement', 'calculating', 'configuring', 'managing', 'under', 'across', 'end']`.
     - Extract core technical tokens.
     - Execute bounded disjunctive query with term weighting:  
       `to_tsquery('english', core_tokens.join(' | '))` ordered by `ts_rank_cd DESC`.
     - Deduplicate and append new lessons up to the 5-result limit.
  3. **Tier 3 (Trigram Fallback):** If $< 5$ rows remain (or if Tiers 1 and 2 yielded 0 rows):
     - Execute `word_similarity($1, trgm_text) >= 0.30` ordered by `sim DESC`.
     - Deduplicate and append new lessons up to the 5-result limit.
  4. **Deterministic Merging:** Result tiers are strictly preserved (Tier 1 $\rightarrow$ Tier 2 $\rightarrow$ Tier 3), guaranteeing that exact lexical matches always dominate top ranks.

### 6.2 Key Qualitative Explanations

#### 1. Resolution of the CI/CD Tokenization Defect (Q16: 0.00 $\rightarrow$ 0.96 NDCG)
- **Problem in Baseline FTS:** Lesson 46 is entitled `"Setting up Automated CI/CD Pipelines with GitHub Actions"`. PostgreSQL's `to_tsvector` parses `CI/CD` with a slash as a file-path token (`'ci/cd':4`). However, user queries written as `CI CD` (separated by space) produce `'ci' & 'cd'`. Because `'ci'` and `'cd'` are not indexed as standalone tokens, pure FTS returned **0 rows**.
- **Resolution in Config B & C:** Trigram matching evaluates 3-character character n-grams (`ci/`, `i/c`, `/cd` vs ` ci`, `ci `, ` cd`). Trigram similarity between the query and lesson title reached **1.0 (100% match)**, immediately placing Lesson 46 at Rank 1.

#### 2. Resolution of the Misspelling Catastrophe (Category 3: 0.00 $\rightarrow$ 0.73 NDCG)
- **Problem in Baseline FTS:** Pure FTS dictionary stemming has zero phonetic or Levenshtein tolerance. Searches like `dokker multistage build` or `drizle sql injecton` produced a 100% failure rate across all 8 test queries.
- **Resolution in Config B & C:** The `pg_trgm` GIN index over `trgm_text` resolved 7 out of 8 misspelling queries with top-1 precision:
  - `dokker multistage build` $\rightarrow$ Lesson 19 (`word_similarity = 0.600`, NDCG: **0.75**)
  - `drizle sql injecton` $\rightarrow$ Lesson 64 (`word_similarity = 0.680`, NDCG: **1.00**)
  - `sslcommerz paymnt gatway` $\rightarrow$ Lesson 82 (`word_similarity = 0.679`, NDCG: **0.88**)
  - `react useCalback dependancy` $\rightarrow$ Lesson 4 (`word_similarity = 0.500`, NDCG: **0.93**)

#### 3. Why Recall@5 Failed (0.7115 vs 0.85 Target)
- In curriculum search, users searching for a high-level concept like `"full-stack authentication architecture from frontend cookies to backend guards"` (Q25) have 5 relevant lessons in the ground truth across frontend cookies, JWT rotation, NestJS guards, and session revocation.
- Configuration C retrieves the exact Grade 3 match (Lesson 9) and 2 sibling lessons (Lessons 6 and 31), but slots 4 and 5 are occupied by other high-ranking terms. Retrieving 3 out of 5 relevant lessons yields $\text{Recall@5} = 3/5 = 0.60$.
- **Fundamental Bound:** Without dense semantic embeddings that capture latent semantic relations across disparate terminology (e.g. connecting `"cookie proxy"` to `"session revocation"` without keyword overlap), lexical and trigram matching cannot reach 0.85 recall on broad cross-module queries.

## 7. Performance & Load Benchmarking (Concurrency 1, 5, 10)

### 7.1 Workload Configuration & Cold Cache Measurements
Workloads were evaluated across sequential queries (C=1: 500 requests) and concurrent pools (C=5: 1,000 requests; C=10: 1,000 requests) with randomized sampling across all 32 benchmark queries.

- **Cold-Cache Initial Query Sample (Unprimed execution immediately after index build):**

## 9. Limitations, Recommendations & Decision Gate

### 9.1 Technical Limitations Identified
1. **The Semantic Recall Gap (Recall@5 = 0.7115):**  
   While query relaxation and trigram matching elevate Recall@5 from 0.2328 to 0.7115 (+205% improvement), they cannot reach the approved 0.85 target. Lexical tokenization cannot map conceptually adjacent topics (e.g., mapping `"outbox pattern"` to `"change data capture"` or `"distributed transactions"` without keyword co-occurrence).
2. **Q24 Anomaly (`asynchronus nodejs error handlng`):**  
   In the synthetic curriculum, Lesson 26 covers graceful shutdown and signal handling in Node.js, while Lesson 30 covers NestJS exception filters. Because neither lesson explicitly contained both "asynchronous" and "error handling" in the lesson title, trigram matching matched Lesson 87 ("Floating-Point Error Prevention") due to the word "Error". This produced $0.00$ NDCG for Q24 because Lesson 87 was not in the ground-truth map for Node.js async errors.
3. **Application Complexity in NestJS:**  
   Configuration C requires a multi-stage query builder in NestJS (Strict FTS $\rightarrow$ Relaxation $\rightarrow$ Trigram Fallback $\rightarrow$ In-Memory Deduplication). While highly performant ($< 4.2\text{ ms}$), it adds query building logic compared to a single vector search query.

### 9.2 Recommendation for Senior Architecture Review

Before determining whether to authorize `pgvector`, senior leadership should consider the following architectural trade-offs:

1. **Option 1 (Approve Hybrid Configuration C with Calibrated Recall Threshold):**
   - **Rationale:** Configuration C achieved **0.8633 NDCG@5** (exceeding the 0.80 target), **zero dropped queries** (0/32), **4.13 ms p95 latency** (exceeding the 50 ms target), and **1.49 MB memory footprint** (>70% headroom on the 256 MB free-tier limit).
   - In production educational platforms, NDCG@5 (putting the right lesson at Rank 1) is substantially more critical to student satisfaction than Recall@5 (retrieving all 5 related lessons in the top 5 slots).
   - If senior leadership approves adjusting the Recall@5 acceptance threshold from 0.85 to 0.70 for pure relational search, Configuration C can be ratified without purchasing infrastructure or introducing vector database overhead.

2. **Option 2 (Proceed to Controlled `pgvector` Proof-of-Concept):**
   - **Rationale:** If senior leadership strictly mandates Recall@5 $\ge 0.85$, relational lexical search is mathematically insufficient.
   - **Gate Requirement:** Under [`ADR-P7-001`](file:///d:/Work/2026/techsprout-main/docs/architecture/adr/ADR-P7-001-learning-telemetry-privacy-and-fts.md), any evaluation of `pgvector` requires formal verification that:
     1. Vector embedding dimensions (e.g., 384-dim vs 1536-dim) and HNSW index memory fit safely within Render's 256 MB RAM ceiling with at least 30% verified headroom.
     2. Cold-start embedding generation and API latencies remain within latency budgets.
